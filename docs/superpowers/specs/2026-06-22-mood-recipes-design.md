# Mood Recipes — переносимый «вайб» дизайн-системы

**Status:** design (approved) · **Date:** 2026-06-22 · **Topic:** mood-recipes

## Проблема

Между референсом-картинкой и кодом стоит **текстовый пересказ**: скриншот →
строка в `references-index.md` → токены. Пересказ роняет всё, что не влезло в
слова. В результате:

- В дизайн-систему мода переходят цвета и шрифты, но **приёмы коллажа**
  (ромбы-маркеры, glow-зоны, волнистые разделители, круглые маски, контурный
  заголовок) — теряются.
- Композиция сохраняется только для hero (`compositions/hero.yaml`), остальные
  блоки собираются плоским шаблоном-генератором `build_composed.py`.
- Приёмы, делавшие старые проекты глубокими, живут в памяти/session-хуках/истории
  чата, а не в файле мода → не воспроизводятся, не переносятся.

Зашитый вручную HTML (как hero в `Тест/`) даёт красоту, но **нулевую
воспроизводимость** — это разовый актив, привязанный к конкретным текстам.

## Граница переиспользования (ключевая идея)

Дизайн-система состоит из двух слоёв с противоположной переносимостью:

| Слой | Что это | Переносимость | Где хранить |
|---|---|---|---|
| **Вайб** | цвет, шрифт, motion, **приёмы декора** | высокая, ~1:1 | токены + `recipes.yaml` |
| **Раскладка** | как блоки лежат, что наезжает, где акцент | низкая (= вайб × конкретные блоки) | выводится агентом под прототип |

**Переиспользуем вайб. Раскладку выводим заново под каждый прототип.** Попытка
переиспользовать раскладку — корень текущего дефекта.

## Решение: `recipes.yaml` — четвёртый файл мода

```
05_ДИЗАЙН-СИСТЕМА/moods/<mood>/
  palette.css       ← цвет      (есть)
  typography.css    ← шрифт     (есть)
  motion.css        ← движение  (есть)
  objects.yaml      ← роли      (есть)
  recipes.yaml      ← НОВЫЙ: приёмы коллажа/декора как переносимый актив
```

### Что recipes содержит — ТОЛЬКО приёмы мода

«Как этот мод делает красоту», в отрыве от контента, в терминах `lp-`классов и
CSS-токенов (из palette/typography), чтобы воспроизводилось одинаково:

- *маркер списка* — форма + правило заливки (важное/нейтральное)
- *акцент-зона* — подложка + glow
- *панель-карточка* — фон, скруг, контур выделенной
- *заголовок-якорь* — какое слово акцентится и как
- *разделитель блоков* — переход между секциями (прямой/волна/смена градиента)
- *маски/декор пустот* — круглые маски, ромбы/листья/конфетти по углам

### Чего recipes НЕ содержит

Ни текстов, ни слотов, ни «какие блоки» — это даёт **прототип**. Поэтому recipes
переносится на любой проект на этом моде без изменений (правило трёх источников:
вид=референс/recipes, структура=прототип, красота=правила коллажа).

## Кто читает recipes (этап 07c compose)

```
prototype-NN.yaml  ──┐ (структура: блоки, тексты, слоты)
                     ├──▶  АГЕНТ рисует composed.html
recipes.yaml       ──┤ (приёмы мода)
референс глазами   ──┘ (1 раз на проект: как приёмы лягут на эти блоки)
```

- recipes **не рендерится кодом** — направляет руку агента («память мода в файле»).
- `build_composed.py` выводится из цепочки рисования красоты (может остаться для
  механической подстановки текстов).
- Правило зашивается в `agents/block-composer.md` и `commands/landing-compose.md`:
  «перед рисованием прочитай `moods/<active>/recipes.yaml`, применяй приёмы».

## Контракт с этапом 08 / Lazy Blocks (НЕ ломаем)

Агент рисует красиво, но обязан сохранить три контракта, иначе stage-08 падает:

1. **Слоты `{{slot:name}}`** — весь редактируемый текст через плейсхолдеры, не
   зашитым текстом (`docs/standards/block-template-format.md` §2). Тогда 08 делает
   из слота поле Lazy Blocks, клиент правит в wp-admin.
2. **Фрагмент + предсказуемый `lp-`класс** — каждый блок = один
   `<section class="lp-...">`, по классу 08-линтер находит блок
   (`probe_selector`, `docs/standards/stage-08-spec-lint.md`).
3. **Структурные правила линтера** — кол-во `<li>` = кол-во полей, инлайн-SVG
   требует `icon_svg` и т.д.

Красота (ромбы, glow, волны) — **обёртка вокруг** предсказуемой слот-структуры,
не замена ей. Противоречие «красиво vs редактируемо» снимается тем, что приёмы
записаны как slot-aware, а структура остаётся за прототипом.

## Тест переносимости — на fresh-green (реф 29)

**Цель:** доказать, что recipes переносит вайб — агент по `recipes.yaml`
зелёного мода + те же тексты прототипа нарисует блоки в характере реф 29
(волны, pink-CTA `#E0379A`, italic-акцент, круглые маски), а не плоско и не в
характере dark-mint.

Приёмы fresh-green, снятые глазами с реф 29 (01/02/04.jpg):
- разделитель = **волнистый SVG-переход** (не прямая линия) — ключевой приём
- CTA = pink-кнопка `#E0379A` (не зелёная)
- заголовок-якорь = второе слово italic + зелёный/золотой
- акцент-зона = сочно-зелёная заливка, обёрнутая волнами сверху+снизу
- маска = круглый аватар в зелёном кольце
- декор = колоски/листья/конфетти по пустотам, золотой вторичный акцент

**Шаги:**
1. Написать `moods/fresh-green/recipes.yaml` (приёмы выше).
2. Агент рисует 3 блока (hero + stats + problem→solution) из `prototype-01.yaml`
   по recipes → `composed-test-greenrecipes.html` (новый файл, ничего не трогаем).
3. Проверка глазами: узнаётся ли вайб реф 29 — **без** просмотра рефа во время
   рисования (рисуем только по recipes). Это тест воспроизводимости.
4. Проверка слот-контракта: `{{slot}}`, `lp-`классы, фрагменты-секции на месте.

**Критерий успеха:** блок узнаваемо «зелёный реф 29» по recipes + слоты на месте.

**Оговорка:** это тест ПОДХОДА, не продакшн. Тексты финансовые на зелёном моде —
для теста переносимости приёмов норм (проверяем вид, не смысл).

## Out of scope

- Починка `build_composed.py` (выводится из рисования красоты).
- `compositions/*.yaml` для всех блоков (раскладка — отдельный слой, не recipes).
- Генератор-рендерер recipes→HTML (recipes читает агент, не код).
- Перенос на остальные моды (после успеха теста — отдельный шаг).
