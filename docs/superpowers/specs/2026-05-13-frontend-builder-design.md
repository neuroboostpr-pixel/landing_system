## 1. Цель

Stage-08 pipeline сегодня даёт **механику** (Lazy Blocks зарегистрированы, контент редактируется в Gutenberg, шаблоны эмитят BEM-классы по `block-spec.yaml`), но не даёт **визуал**: `main.css` не содержит правил для классов из DESIGN.md §5, `block.php`-скелеты не реализуют per-block layout (2-col Hero, FAQ accordion, Pricing badge).

`frontend-builder` — новый agent, который переводит DESIGN.md в реальный визуальный код: добавляет per-block CSS в DESIGN.md §5 и переписывает каждый `block.php` под wireframe.

## 2. Форма и место в workflow

`frontend-builder` — **claude-agent** (markdown в `agents/frontend-builder.md`), вызывается **отдельной командой `/landing-style`**.

Место в workflow:

```
... → /landing-build  (механика: theme + блоки + контент в Gutenberg)
      → GATE: hard checks (HTTP 200, блоки зарегистрированы)
      → /landing-style (визуал: per-block CSS в DESIGN.md §5 + block.php rewrite)
      → GATE: hard checks + manual visual approve
      → /landing-qa / /landing-deploy
```

Symmetric с другими `/landing-*` стадиями. В `.landing-state.yaml` добавляется ключ `style: pending|approved`.

## 3. Контракт inputs / outputs

### Inputs (read-only)
- `05_ДИЗАЙН-СИСТЕМА/DESIGN.md` — wireframes §5, токены §2, layout §3-§4, motion §7, a11y §8, state-machines §9
- `04_БРЕНД/brand-kit.md` — дополнительный контекст бренда
- `01a_АНАЛИЗ_НИШИ/landing-structure.md` — контракт блоков
- `08_КОД/block-spec.yaml` — список блоков, controls, BEM-классы (`css_class`, `element`, `wrapper_open_html`, `href_from`)
- `08_КОД/wp-theme/blocks/lazyblock-<slug>/block.php` — skeleton от pipeline (как референс)

### Outputs (frontend-builder пишет)
- `05_ДИЗАЙН-СИСТЕМА/DESIGN.md` §5 — добавляет fenced ```css блоки с реальными rule-bodies per-block, включая media queries
- `08_КОД/wp-theme/blocks/lazyblock-<slug>/block.php` — переписывает с marker-комментарием в шапке:
  ```php
  <?php
  // AUTO-GENERATED by frontend-builder.
  // Edits will be overwritten. Modify DESIGN.md §5 or block-spec.yaml instead.
  ```

### Outputs (pipeline после frontend-builder)
- `08_КОД/wp-theme/assets/css/main.css` — перегенерирован из обновлённой DESIGN.md через изолированный CSS-extract шаг

### Чего frontend-builder НЕ трогает
- DESIGN.md §1-§4, §6-§9 (designer-only)
- `block-spec.yaml` (manager-only)
- `style.css` (токены §2 неизменны)
- `functions.php`, `index.php`, `lzb/init` registration
- `page-content.html` seed
- `assets/js/*` (zero-JS by default)
- `landing-structure.md`, `brand-kit.md`, `tokens.json`

## 4. Архитектурные решения

| # | Вопрос | Решение |
|---|--------|---------|
| 1 | Где живут per-block CSS-правила? | В DESIGN.md §5 fenced ```css блоками, подхватывается `design_extractor` в `main.css`. Single source of truth — DESIGN.md. |
| 2 | Что пишет frontend-builder в `block.php`? | Полностью переписывает skeleton по wireframe из DESIGN.md §5. Pipeline-skeleton остаётся как bootstrap. |
| 3 | Идемпотентность / regen | Перезаписывает `block.php` без вопросов. Marker-комментарий в шапке делает контракт явным: ручные правки запрещены. |
| 4 | Форма агента и точка вызова | Claude-agent + отдельная команда `/landing-style` (не фаза в `/landing-build`). Свой gate, свой approve. |
| 5 | Granularity | Поблочно, последовательно. Флаг `--block <slug>` для regenerate одного блока. |
| 6 | Gate-check | Hard checks автоматом + manual visual approve manager'ом в `.landing-state.yaml`. |
| 7 | Mobile / responsive | Читает DESIGN.md (§3.3 + §5), реализует ровно описанное. Никаких собственных решений. |
| 8 | Cross-cutting CSS (forms, motion, a11y) | Живёт в DESIGN.md §3-§9, обрабатывается существующим `design_extractor` в `main.css`. frontend-builder только использует классы. |
| 9 | JavaScript | Zero-JS by default. Нативный HTML/CSS (`<details>`, `position:sticky`, checkbox-hack). Если совсем нельзя — TODO-комментарий в выводе, не код. |
| 10 | Re-run extractor | Изолированный CSS-extract шаг pipeline (рефакторинг `generate-theme.py` на под-шаги). `/landing-style` дёргает только `extract-rules-to-main-css.py`. |

## 5. Алгоритм `/landing-style`

```
1. Pre-checks (hard gate):
   - .landing-state.yaml: stage "build" = approved
   - DESIGN.md существует, §2 и §5 непустые
   - block-spec.yaml существует, ≥1 блок
   - wp-theme/blocks/lazyblock-*/block.php skeleton'ы существуют

2. Загрузить inputs в память агента:
   - DESIGN.md (полный), brand-kit, landing-structure, block-spec.yaml

3. Для каждого блока в block-spec.yaml (последовательно):
   a. Извлечь из DESIGN.md §5 секцию конкретного блока (wireframe ASCII + описание классов)
   b. LLM-вызов: вход = wireframe + brand context + block-spec для этого блока + skeleton block.php;
      выход = (i) fenced ```css блок для §5.<slug>, (ii) переписанный block.php
   c. Записать fenced CSS в DESIGN.md §5 в дедикейтед подсекцию для этого блока
   d. Перезаписать block.php с marker-шапкой
   e. Лог: "block <slug>: ok"

4. Post-processing:
   - Запустить scripts/extract-rules-to-main-css.py
   - Получить обновлённый assets/css/main.css
   - НЕ трогать style.css, functions.php, index.php

5. Hard gate-check (scripts/gate-check.sh style):
   - Для каждого блока: в DESIGN.md §5 есть fenced ```css секция
   - Каждый block.php содержит marker frontend-builder
   - main.css mtime > DESIGN.md edit time
   - HTTP 200 на test-стенде (если live)
   - error_log пуст по PHP-fatals

6. Manual approve gate:
   - Сообщение manager'у: "Открой <preview URL>, проверь визуал.
     Approve → .landing-state.yaml stage 'style' = approved"
   - Опционально: предложить /landing-qa между hard checks и manual approve
```

### Флаги команды
- `/landing-style` — все блоки
- `/landing-style --block <slug>` — один блок

## 6. Рефакторинг pipeline (зависимость)

`/landing-style` требует, чтобы CSS-extraction из DESIGN.md можно было вызывать отдельно от scaffold темы. Текущий `scripts/generate-theme.py` делает всё одним вызовом.

### Целевая структура `scripts/`
- `generate-theme.py` — оркестратор, дёргает все шаги; поведение для `/landing-build` не меняется
- `generate-theme-scaffold.py` — создаёт `index.php`, `functions.php` база, директории
- `extract-tokens-to-style-css.py` — читает DESIGN.md §2 → пишет `style.css`
- `extract-rules-to-main-css.py` — читает DESIGN.md §3-§9 → пишет `main.css`
- остальные шаги (`generate-lzb-templates`, `generate-lzb-registration`, `generate-css-patches`, `generate-page-content`) — без изменений

`/landing-style` дёргает только `extract-rules-to-main-css.py`. `style.css` не пересоздаётся.

### Backwards compat
`generate-theme.py` остаётся точкой входа для `/landing-build` и продолжает дёргать все шаги. Внешний контракт не меняется.

### Порядок CSS в main.css
`tokens → primitives → cross-cutting → per-block`. Extractor должен гарантировать порядок секций.

## 9. Критерии приёмки («passable» на neuroupgrade-v2)

- Hero отображается с 2-col grid на desktop, стеком на mobile
- Pricing отображает 3 карточки с middle "popular" badge
- FAQ работает как accordion (`<details>/<summary>`)
- Brand-токены применены (`--bg-base`, `--accent-coral` видны в computed styles)
- HTTP 200, нет PHP-fatals, нет console errors
- Manager judgment passes (не pixel-perfect)

## 10. Открытые вопросы / unknowns

1. **Формат fenced CSS в DESIGN.md §5.** Соглашение: отдельный заголовок `### CSS` под каждым блоком? Префикс? — уточним при writing-plans на основе текущей структуры DESIGN.md в neuroupgrade-v2.
2. **Decomposition cost `generate-theme.py`.** Если зависимости между шагами окажутся жёсткими, разделение может потребовать больше работы. План должен начинаться с research-задачи «прочитать generate-theme.py, оценить cost».
3. **CSS-conflict в main.css.** Порядок секций должен быть `tokens → primitives → cross-cutting → per-block`. Extract-скрипт это гарантирует, но нужен тест.
4. **Скорость.** 12 блоков × LLM-вызов ≈ несколько минут. Acceptable, но в плане учесть.

## 11. Out of scope

- Pixel-perfect соответствие референсам moodboard'а
- Автоматический visual diff (нет reference для diff'а)
- JS-интеракции сложнее CSS-only (отдельная будущая стадия, если понадобится)
- Изменения в DESIGN.md §1-§4, §6-§9 (designer responsibility, stage-05)
- Изменения в `block-spec.yaml` (manager responsibility)
