## СТРУКТУРА РАБОТЫ ЭТАПОВ (как этапы связаны)

Флоу начинается с **онбординга** (системная настройка + создание проекта), затем
оркестратор ведёт через этапы блок-системы **05 → 07a → 07 → 07a → 07b → 07c →
08**. Поток данных и команд от онбординга:

```
ОНБОРДИНГ
  /landing-setup ──► ~/.landing-system/setup_complete   (разовая настройка: env, API-ключи)
       │              (без него /landing-* не запускаются)
       ▼
  /landing-start ──► ~/Lendings/<slug>/ (18 подпапок) + материалы клиента
       │              (wizard: прототип/фото/логотип/референсы → раскладывает по папкам)
       │              финиширует подсказкой ↓
       ▼
  /landing-go ──► читает .landing-state.yaml → диспатчит следующий этап (оркестратор)
       │
       ▼
05 Дизайн-система ──tokens.json──┐
   (/landing-design)             │ (цвета/шрифты проекта)
                                 ▼
07a Прототип ──prototype.yaml──► 07a Wireframe ──selections.yaml──► 07b Compose ──► 08 Build
   (/landing-prototype)            (/landing-wireframe)              (/landing-compose)  (WordPress-тема)
        │                               ▲                                 ▲                ▲
        │                               │ кандидаты из                    │ блоки из        │ mood/паттерны
        ▼                          block-library/catalog.yaml        block-library         из _styles
07 Контент (опц.)                                                                     (/landing-build)
   (/landing-content)
   prototype.yaml → content.md
                                                                  07c Фото ──► (реальные <img> в compose)
```

**Связи этапов (что → куда передаёт):**

| Этап | Команда | Вход | Выход | Кому передаёт |
|---|---|---|---|---|
| Онбординг (система) | `/landing-setup` | env, API-ключи | `setup_complete` | разблокирует все `/landing-*` |
| Онбординг (проект) | `/landing-start` | материалы клиента (прототип/фото/логотип/референсы) | папка проекта + разложенные материалы | `/landing-go` (запуск конвейера) |
| Оркестратор | `/landing-go` | `.landing-state.yaml` | диспатч следующего этапа | этапы 05…08 по очереди |
| 05 Дизайн-система | `/landing-design` | бренд | `tokens.json` (цвета/шрифты) | 07a wireframe (превью), 07b compose, 08 build |
| 07a Прототип | `/landing-prototype` | source (docx/pdf/png/md) из 07a онбординга | `prototype.yaml` + fidelity-отчёт | 07 контент, 07a wireframe |
| 07 Контент (опц.) | `/landing-content` | `prototype.yaml` | `content.md`, SEO-копия | копирайт (вне блок-системы) |
| 07a Wireframe | `/landing-wireframe` | `prototype.yaml` + `catalog.yaml` + `tokens.json` | `wireframe.html`, `selections.yaml` | 07b compose |
| 07b Compose | `/landing-compose` | `selections.yaml` + `prototype.yaml` + `tokens.json` (+ фото 07c) | `composed.html` | 08 build |
| 07c Фото | `/landing-photos` | клиентские фото (из онбординга) | обработанные `<img>` | 07b compose (подстановка) |
| 08 Build | `/landing-build` | composed + tokens + mood | WordPress-тема (CSS, паттерны, дизайн-система) | деплой |

> **Онбординг** — точка входа: `/landing-setup` (один раз на систему) →
> `/landing-start` (на каждый проект: создаёт структуру и собирает материалы) →
> `/landing-go` (ведёт по этапам). Материалы, собранные на онбординге (прототип в
> `07_ПРОТОТИП/source/`, фото в `07c_PHOTOS/inbox/`), — это вход для
> соответствующих этапов.

**Вне потока проекта** — наполнение общей библиотеки (не привязано к конкретному
лендингу): `/landing-import-blocks` (добавить блок из скриншота), генерация
каталога/галереи, нормализаторы. Библиотека (`block-library/`) — общий ресурс,
который читают этапы 07a/07b.

## ФЛОУ `/landing-go` (оркестратор)

`/landing-go` — единая точка входа в конвейер после онбординга. Не делает работу
сам, а **диспетчер**: читает `<project>/.landing-state.yaml`, находит следующий
этап и передаёт его соответствующему агенту/команде.

### Как определяется следующий этап

`scripts/landing-go-next-stage.py` хранит жёсткий порядок `STAGE_ORDER` (20
этапов) и выбирает первый этап по приоритету:

1. первый `in_progress` (продолжаем начатое),
2. иначе первый `failed` (чинит упавший гейт),
3. иначе первый `locked` (открывает следующий),
4. если всё `approved`/`n/a` → `DONE`.

`STAGE_ORDER` в скрипте:

```
00_brief → 01_context → 01a_niche_analysis → 02_assets →
03_references → 04_brand → 05_design → 06_stack → 07_content →
07a_prototype → 07b_wireframe → 07c_composed →
07d_photos → 07e_visuals → 07f_composed_final →
08_build → 09_deploy → 10_qa → 11_analytics → 12_seo
```

### Prototype-first: что пропускается

При запуске с прототипом в `07_ПРОТОТИП/source/` оркестратор сразу помечает 4
upstream-этапа как `n/a` (`scripts/gate-state.sh set ... n/a`):
`00_brief`, `01_context`, `01a_niche_analysis`, `02_assets`. Бриф/ниша выводятся
из прототипа, материалы клиента уже собраны на онбординге.

### Этапы, которые `/landing-go` РЕАЛЬНО ведёт (prototype-first)

| Этап | Команда/агент | Тип |
|---|---|---|
| 07a_prototype | `/landing-prototype` (prototype-importer) | авто |
| 03_references | references-curator | маркетолог |
| 04_brand | brand-architect | маркетолог + AI |
| 05_design | design-system-generator | маркетолог + AI |
| 06_stack | stack-planner | авто |
| 07_content | content-writer | авто |
| 07b_wireframe | `/landing-wireframe` | маркетолог выбирает |
| 07c_composed | `/landing-compose` | авто |
| 07d_photos ⇆ 07e_visuals | `/landing-photos` ‖ `/landing-visuals` | **параллельно** (2 субагента) |
| 07f_composed_final | `/landing-compose` | авто |
| 08_build | wp-builder | авто |

### Захватывает ли `/landing-go` ВСЕ этапы — расхождения

**Нет, есть пробелы между тремя источниками** (`stage-gates.yaml` ↔
`landing-go-next-stage.py::STAGE_ORDER` ↔ таблица в `commands/landing-go.md`):

| Этап | В stage-gates.yaml | В STAGE_ORDER скрипта | В таблице landing-go.md | Проблема |
|---|---|---|---|---|
| `01_context` | ❌ нет | ✅ есть | ❌ нет | этап есть в state и в скрипте, но **нет гейта** — gate-check для него не определён |
| `03b_visual_concept` | ✅ есть (hard lock) | ❌ нет | ❌ нет | гейт существует и блокирует, но оркестратор **до него не доходит** (нет в STAGE_ORDER) → конвейер может встать |
| `08b_style` | ✅ есть | ❌ нет | ❌ нет | пост-build этап стиля фронтенда есть в гейтах и state, но не в диспатче |

> **Вывод:** `/landing-go` ведёт ~15 этапов из 20 определённых. Три этапа
> (`01_context`, `03b_visual_concept`, `08b_style`) рассинхронизированы между
> источником гейтов, скриптом-диспетчером и документацией команды. Это **новый
> backlog-пункт B17** (см. часть V) — единый список этапов должен быть один
> источник истины (как `taxonomy.yaml` для блоков).

**Вне `/landing-go`** (отдельные команды, не часть конвейера): `/landing-segment`,
`/landing-clone` (multisite), `/landing-import-blocks` (наполнение библиотеки),
`/landing-audit` (SEO-аудит после деплоя).

## АРТЕФАКТЫ `/landing-start` — что создаётся и нужно ли это

`/landing-start` (wizard, PR-E) копирует шаблон `template/` целиком в
`~/Lendings/<slug>/` через `skills/landing-project-init/scripts/init.sh`, затем

сразу** (не лениво по мере надобности).

- **Настоящего мусора почти нет:** все stage-папки 00–12 имеют потребителя.

  single-site проектов это пустой скелет, который оправдан только при multisite.
  Можно создавать его лениво при первом `/landing-segment` (backlog **B19**).
- **В prototype-first** 4 upstream-папки (`00`,`01`,`01a`,`02`) создаются, но
  помечаются `n/a` — формально не мусор (могут понадобиться в classic-режиме), но
  для proto-first это визуальный шум. Решение — не удалять, а маркировать в
  state как `n/a` (уже делается).
- **Расхождение имён:** `03_REFERENCIAS` (исп.) и `03b_КОНЦЕПТ` ломают
  кириллический нейминг остальных папок — косметический долг (**B18**).

### 1. Таксономия блоков (B34) — двухуровневая, метки на русском

Блоки классифицируются по двум уровням: **категория** (роль блока на странице) и
**подкатегория/variant** (семантический подтип). Источник истины —
`block-library/taxonomy.yaml`.

**Обязательное условие: все элементы таксономии, видимые в интерфейсе, — на
русском.** Технический слаг английский (`header`, `social-proof`), но у каждой
категории и подкатегории есть `label_ru` — именно он показывается в галерее и
wireframe. Пример из taxonomy.yaml:

| Слаг (технический) | label_ru (в интерфейсе) |
|---|---|
| header | Шапка / Навигация **(обязательная, см. ниже)** |
| hero | Первый экран |
| features | Преимущества |
| content | Контент (→ «о продукте», «проблема → решение», «как это работает», «контакты / реквизиты») |
| social-proof | Соц. доказательства (→ «отзывы», «наши клиенты», «рейтинги», «цифры», «кейсы», «упоминания в медиа», «команда») |
| trust | Доверие (→ «сертификаты», «гарантии», «безопасность») |
| pricing | Цены (→ «карточки тарифов», «сравнительные таблицы») |
| forms | Формы (→ «сбор email», «многошаговая», «квиз», «бронирование») |
| faq | FAQ |
| extra | Дополнительно (→ «баннер», «бегущая строка») |
| footer | Подвал **(обязательная, см. ниже)** |

**12 категорий, 6 из них с подкатегориями.** Порядок в интерфейсе задаётся полем
`order`. Загрузчик `scripts/lib/taxonomy.py` — единственный способ получить метки
и валидировать; никаких хардкод-словарей категорий в коде или HTML.

**Категория «Дополнительно» (`extra`) — независимая от структуры страницы.**
Это блоки, которые не встроены в основной поток (баннер, бегущая строка) и могут
появляться где угодно. Бывшая отдельная категория `marquee` (Бегущая строка)
упразднена — бегущая строка стала вариантом `marquee` внутри «Дополнительно»,
рядом с вариантом `banner` (промо-полоса/CTA-баннер). Это закрывает потерю
баннера при B34 (см. B11 ниже).

**Обязательные категории «Шапка» (`header`) и «Подвал» (`footer`).** Эти два
блока **всегда присутствуют** на странице (нельзя отключить в wireframe), даже
если визуально пустые — в них часто ставят виджеты, меню, контакты, юр-блоки,
cookie-баннер. В библиотеке должны быть **минимальные/пустые варианты** шапки и
подвала (контент-заглушка), чтобы блок существовал как контейнер под виджеты,
даже когда контента у клиента нет. Это отличает их от остальных блоков, которые
B12 позволяет включать/отключать.

**Где живёт категория:** в `meta.yaml` блока (семантика). Имя папки — лишь
физический путь и может отличаться (блок в папке `quiz/`, а категория `forms`,
подкатегория `квиз`). Категории «Контент» и «Дополнительно» существуют только
семантически, без своих папок (блоки лежат в `content/`, `marquee/` и т.п.).

`catalog.yaml` (version 3) хранит у каждого блока слаги `category`/`variant` (для
фильтрации) + `folder`/`path` (для ассетов); метки берутся из taxonomy при показе.

Удалены папки `cta/` (CTA — это роль форм, не категория) и `gallery/`.

>   галерейные блоки распределяются по семантике (соц-док/контент).

### 2. Формат шаблона блока (B35)

Канон: `docs/standards/block-template-format.md`. `template.html` — это

Все цвета и шрифты блока — через переменные `var(--lp-*)`, не хардкод. Реальные

### 4. Точность парсинга прототипа — единое правило для ВСЕХ форматов (B37, расширено)

**Главное правило:** при парсинге любого прототипа (docx, pdf, png, скриншот,
md) в `prototype.yaml` должно дойти **не менее 90% контента источника, без
выдуманной структуры**. Отклонения допустимы ТОЛЬКО если они явно прописаны в
комментариях клиента к прототипу — и только в рамках этих комментариев.

Эталон для любого формата — извлечённый текст: docx через python-docx (с
таблицами), текстовый pdf через pypdf, **скан-pdf / png / скриншот через OCR**,
md как есть. Затем сверка покрытия и проверка на типовые выдумки (меню
Home/About/Services/Contact, абстрактные цены, Lorem ipsum). Гейт этапа 07a не
закрывается при потере >10% или выдумке.

Комментарии клиента разработчику складываются в секцию `client_notes:`,
техно-метаданные — в `source_meta:`. Они не входят в `sections`, поэтому не
рендерятся как блоки, но сохраняются как рекомендации. Это единственный легальный
источник отклонений от «всё как в источнике».

> ### 🔒 ПРАВИЛО (нормативное): референсы ВСЕГДА скриншотом и/или текстовым описанием от клиента
>
> **Источник дизайн-референса = скриншот и/или текстовое описание ОТ КЛИЕНТА.**
> URL живого сайта — только вспомогательный, НИКОГДА не единственный источник.
>
> **Почему (доказано на прогоне 2026-06-04, журнал T11/T12):**
> - Живой сайт может быть недоступен агенту: anti-bot/CDN (Mercedes за CloudFront
>   → headless-браузер получил `403`), авторизация, гео-блок, JS-рендер.
> - `WebFetch` отдаёт лишь **текстовый пересказ** страницы (без пикселей) и может
>   **ввести в заблуждение**: для Mercedes он сказал «белый/sans/прямоугольные
>   кнопки», а по реальному скриншоту палитра = чёрный cinematic + сериф + синие
>   пилюли. Дизайн-система, собранная по тексту, оказалась неверной и была
>   переделана по пикселям скриншота.
>
> **Обязательные требования к флоу:**
> 1. На этапе сбора референсов (03_РЕФЕРЕНСЫ / дизайн-система) у клиента
>    запрашиваются **скриншоты** референса и/или **текстовое описание** желаемого
>    стиля. Это вход первого класса, наравне с прототипом.
> 2. Если дан только URL — агент **пытается** открыть (WebFetch + headless-скрин),
>    но при недоступности/сомнении **обязан запросить у клиента скриншот**, а НЕ
>    «забить на референс» и не выдумывать стиль. Молчаливый пропуск референса —
>    дефект.
> 3. **Палитра/типографика снимаются с ВИЗУАЛА (пиксели скриншота), а не с
>    текстового описания сайта.** Текстовый бриф допустим только как дополнение к
>    картинке, не как замена.
> 4. Разобранный референс сохраняется как `analysis.yaml` (приёмы/палитра-роли/
>    формы), чтобы не анализировать картинку повторно (связь с B24).
>
> **Связано:** T11/T12 (журнал теста, часть V-bis), B22 (premium≠чужие допущения),
> B24 (хранилище эталонов дизайна), часть III-ter (алгоритм создания дизайна).

> ### 🔒 ПРАВИЛО (нормативное): дизайн-система ≠ раскладка. Три источника, три роли
>
> При создании коллаж-дизайна по референсу строго разделяются ТРИ вещи —
> смешивать их нельзя (доказано на прогоне 2026-06-04, журнал T13/T14):
>
> | Что | Откуда берётся | Что включает |
> |-----|----------------|--------------|
> | **(А) Дизайн-система** | из **референса** (по скриншоту/пикселям) | палитра и роли цветов, типографика, стиль кнопок/тегов/полей, радиусы, тени, отступы-токены, характер, движение. ТОЛЬКО «чем рисуем». |
> | **(Б) Структура и раскладка** | из **прототипа** (1:1) | какие блоки, их порядок, что внутри блока, выравнивание элементов, наличие/отсутствие элементов, тексты, кнопки. «Что где стоит». |
> | **(В) Коллаж-приёмы** | алгоритм **III-ter** | блобы, наезжающие слои, cut-out, волны, числа-якоря, росчерк — добавляются как ГЛУБИНА поверх раскладки (Б), но НЕ меняют саму раскладку и НЕ добавляют структурных элементов, которых нет в прототипе. |
>
> **Запрещено:**
> - брать **раскладку/композицию** у референса (порядок блоков, выравнивание,
>   зигзаги, hero-композицию). Это берётся ТОЛЬКО из прототипа.
> - **добавлять структурные элементы**, которых нет в прототипе (выдуманные
>   chip'ы, бейджи, блоки, кнопки) — это галлюцинация структуры, так же
>   недопустима, как выдуманный текст (B37).
>
> **Проверка:** перед compose агент сверяет раскладку с прототипом поблочно
> (порядок, выравнивание, состав элементов) — расхождение = дефект, чинить до
> деплоя. Коллаж-глубина допустима только в рамках раскладки прототипа.
>
> **Связано:** T13/T14 (часть V-bis), B37 (structure-fidelity), часть III-ter.

> ### 🔒 ПРАВИЛО (нормативное): создание SVG — векторизация исходника, codex НЕ для бренд-знаков
>
> Когда лендингу нужны иконки/логотипы в SVG, выбор способа зависит от того,
> ТОЧНЫЙ ли это знак или абстрактная графика (доказано на прогоне 2026-06-04, T17):
>
> | Что нужно | Способ | Почему |
> |-----------|--------|--------|
> | **Логотип бренда / точный знак** (Li Auto, Zeekr, Xiaomi, ROX, Lynk & Co…) | **Векторизация исходника** (`vtracer`/`potrace` из PNG/JPG; если уже SVG — взять как есть) | Логотип нельзя выдумывать — это узнаваемый знак. codex рисует ПОХОЖУЮ выдумку, не точную копию. |
> | **Абстрактная иконка / инфографика** (без бренд-знаков) | codex image_gen ИЛИ Lucide (готовые иконки) | Тут точность к оригиналу не нужна, генерация допустима. |
> | **Декоративная фигура** (blob, волна) | CSS (`border-radius`) или `_shapes/*.svg` | Геометрия, не картинка. |
>
> **Пошаговый флоу векторизации логотипа (канон):**
> 1. **Получить исходник от клиента** (PNG/JPG/SVG). Если исходника нет — НЕ
>    генерировать в codex, а запросить файл у клиента (как с ROX). Текст-марк —
>    только временный плейсхолдер.
> 2. **Если уже SVG** — взять как есть (пропустить трассировку).
> 3. **Если растр** — сделать бинарную маску: объект (логотип) = тёмный, фон =
>    белый. Для PNG-на-прозрачном — маска из альфы (`alpha>40 → объект`); для
>    JPG-на-фоне — threshold по яркости. Проверить долю объекта (норм ~5–25%,
>    не ~85% — иначе перепутана полярность и трассируется фон).
> 4. **Трассировать**: `vtracer.convert_image_to_svg_py(..., colormode='binary',
>    filter_speckle=8–20, path_precision=1–3)`. Больше `filter_speckle`/меньше
>    `path_precision` = чище и легче файл.
> 5. **Нормализовать SVG** (обязательно, иначе не отрендерится/не масштабируется):
>    - добавить `viewBox="0 0 W H"`, **убрать** жёсткие `width`/`height` (иначе
>      лого рендерится в натуральный размер и переполняет контейнер невидимо);
>    - заменить `fill` (`#000000`/`black`/`white`) на **`currentColor`**, чтобы
>      цвет управлялся из дизайн-системы.
> 6. **Подключить — ПРЕДПОЧТИТЕЛЬНО inline `<svg>`** с `fill:currentColor`
>    (цвет из дизайн-системы). ⚠️ **НЕ через `mask-image: url(local.svg)`** —
>    браузеры блокируют загрузку локального SVG в `mask`/`background` по `file://`,
>    и лого **исчезает при открытии файла напрямую** (на сервере работает, локально
>    нет — частая ловушка, доказано T17). Inline-`<svg>` рендерится везде (file:// и
>    сервер). Цена — вес путей в HTML (держать `path_precision` низким, см. шаг 4).
> 7. **Проверить рендером** на тёмном И светлом фоне (лого не должно «пропадать»
>    из-за совпадения fill с фоном — частая ошибка чёрного-на-тёмном).
> 8. **Хранить** как отдельные `.svg` в `assets/logos/` (не inline-раздувать HTML
>    тяжёлыми путями). На WordPress — по asset-pipeline (inline SVG → textarea-attr
>    через `wp_kses`, или файл в теме).
> 9. **Единый оптический размер набора SVG** (когда несколько SVG стоят рядом в
>    ОДНОМ блоке — **логотипы, иконки фич, бейджи, декор-знаки и т.п.**; не только
>    лого). Разные SVG имеют РАЗНЫЕ соотношения сторон (Zeekr 4:1, Xiaomi 2:1,
>    Lynk&Co 1.8:1; иконки — квадратные…) и разную плотность чернил, поэтому
>    **нельзя задавать одинаковую высоту/ширину в px** — это даёт визуально разный
>    размер (T19). **Это правило применяется к ЛЮБОМУ набору SVG в блоке**, а не
>    только к бренд-логотипам: иконки услуг, иконки в фичелистах, соц-иконки,
>    декоративные знаки — всё, что стоит рядом и должно «весить» одинаково.
>    Базовый случай (близкие пропорции) — общий бокс + fit по большей стороне:
>    ```css
>    .icon{height:auto;max-height:26px;max-width:120px}
>    .icon svg{height:auto;width:auto;max-height:26px;max-width:120px;display:block}
>    ```
>    Лого-иконки (квадратные, Xiaomi/Li-symbol) и широкие wordmark'ы (Zeekr/ROX)
>    тогда занимают один оптический «коридор».
>
>    ⚠️ **Высоты/ширины МАЛО — нормировать по ПЛОЩАДИ ЧЕРНИЛ (алгоритм A).**
>    Применимо к ЛЮБОМУ набору SVG в блоке (лого/иконки/бейджи/декор), не только
>    к логотипам. «Оптически ровно» = **одинаковая визуальная масса**, а масса —
>    это площадь закрашенных пикселей (а не высота и не ширина). Разброс площади
>    чернил в наборе бывает ~10× (замер логотипов: Li 13161, Zeekr 26506,
>    Xiaomi 7137, ROX 55784, Lynk&Co 5234 при общей высоте бокса 200px; для иконок
>    разброс обычно меньше, но принцип тот же) — поэтому любая одномерная подгонка
>    (height-px / width / высота-чернил) НЕ сходится. Найдено через brainstorm, T19.
>    **Канон (алгоритм A — равная площадь чернил + потолок высоты):**
>    ```python
>    # Вход: N логотипов-SVG. Цель: у всех одинаковая визуальная масса.
>    # 1) Рендер-замер. Каждый лого отрендерить headless на ЕДИНУЮ высоту бокса
>    #    BOX=200px (fill #000 на белом), снять PIL'ом:
>    #       S[b]  = число тёмных пикселей  (площадь чернил)
>    #       h[b]  = высота bbox тёмных пикселей  (для потолка)
>    # 2) Целевая площадь — БЕЗ эталона-на-глаз: медиана по набору
>    #       S0 = median(S[b] for b in logos)
>    # 3) Масштаб каждого лого так, чтобы площадь стала S0.
>    #    Площадь растёт как квадрат линейного масштаба ⇒
>    #       scale[b] = sqrt(S0 / S[b])
>    #       box[b]   = BOX * scale[b]          # высота svg-бокса (промежуточная)
>    # 4) Потолок высоты — чтобы лого с высоким символом (Zeekr/ROX) не разъехались:
>    #       ink_h[b] = h[b] * box[b]/BOX        # итоговая высота чернил
>    #       cap      = median(ink_h) * 1.35
>    #       если ink_h[b] > cap:  box[b] = cap * BOX / h[b]
>    # 5) Привести к карточному размеру: нормировать так, чтобы СРЕДНИЙ box[b]
>    #    равнялся целевой высоте в карточке (напр. 34px):
>    #       k = 34 / mean(box[b]);   final_h[b] = round(box[b] * k)
>    # 6) В CSS: .brand-logo[data-b="X"] svg{height: final_h[X]px; width:auto}
>    ```
>    Пример результата (этот проект, 5 авто-брендов): Li 34 / Zeekr 19 /
>    Xiaomi 46 / ROX 17 / Lynk&Co 54 px — визуально ровная масса, проверено
>    рендером dark-on-white. Всё по пикселям, ноль «на глаз» (правило «без тестов
>    выводов не делаем»). Подход выбран через brainstorming-skill после 4 неудачных
>    одномерных попыток.
>
> **Запрещено:** генерировать логотипы реальных брендов через codex — это даёт
> неточный/выдуманный знак. codex — только для абстрактной графики без бренд-знаков.
>
> **Связано:** T16/T17 (часть V-bis), `docs/asset-pipeline.md` (SVG в WP), B10 (`_shapes/`).

## ЧАСТЬ III — АЛГОРИТМЫ (по шагам, человеческим языком)

### 3.1. Импорт прототипа клиента — `/landing-prototype`

1. Маркетолог кладёт файл прототипа в `07_ПРОТОТИП/source/` (docx, pdf, png или
   md) и запускает команду.
2. Агент `prototype-importer` определяет формат и **извлекает эталонный текст**:
   - docx — скриптом `extract-docx-text.py` (берёт и параграфы, и таблицы, где
     обычно лежат цены тарифов);
   - текстовый pdf — `extract-pdf-text.py`;
   - скан-pdf / png / скриншот — через OCR (vision);
   - md — берётся как есть.
3. **Структурирование — раскладка текста по полям.** Из эталонного текста агент
   собирает `prototype.yaml`, **используя только реальный текст источника**.
   Каждая секция (`sections[].id`) содержит список под-блоков
   (`blocks[]`), и каждый под-блок получает `type` + поля по своей роли:
   - заголовок секции → под-блок `type: heading`, поле `text` (+ `highlight` для
     акцентной части);
   - абзац-описание → `type: paragraph`, поле `text`;
   - надзаголовок-плашка → `type: info_badge`, поля `label` + `value`;
   - кнопка → `type: cta_button`, поля `text` + `action`;
   - повторяющиеся элементы (модули, тарифы, преимущества) → по под-блоку на
     элемент (`type: module`/`tariff_card`/…) с полями `title`/`price`/`text`…;
   - изображение → слот в `slots[]` (`type: photo`).
   Имена полей фиксированы (`text`, `highlight`, `label`, `value`, `title`,
   `price`, …) — позже именно по ним идёт маппинг в слоты блоков (см. 3.1.2).
   Комментарии клиента уводятся в `client_notes`, метаданные — в `source_meta`.

   **Пример (секция hero реального прототипа):**
   ```yaml
   - id: hero
     blocks:
       - {type: heading,    text: "НЕЙРОКРЕАТОР", highlight: "Практический онлайн-курс по ИИ-визуалу"}
       - {type: paragraph,  text: "Научитесь создавать визуальный контент с ИИ…"}
       - {type: info_badge, label: "Старт", value: "27 июня"}
       - {type: cta_button, text: "Хочу на курс", action: cta}
   ```
   То есть: «НЕЙРОКРЕАТОР» лёг в `heading.text`, подзаголовок — в
   `heading.highlight`, описание — в `paragraph.text`, плашка «Старт 27 июня» — в
   `info_badge.label/value`, кнопка — в `cta_button.text`. Дальше (этап
   wireframe) эти поля раскладываются в слоты блока: `heading.text`→`{{slot:title}}`,
   `info_badge`→`{{slot:eyebrow}}`, `cta_button.text`→`{{slot:primary-cta-label}}`.
4. Если в прототипе есть квиз — `enrich-quiz-funnel.py` достраивает его до полной
   воронки.
5. **Проверка точности** (`verify-prototype-fidelity.py`): сверяет, что ≥90%
   текста источника дошло до yaml и нет типовых выдумок. Пишет
   `fidelity-report.md`.
6. Гейт этапа 07a (`gate-prototype-fidelity.py`) не пропускает дальше, если
   точность ниже порога или есть выдумки — маркетолог видит, что потеряно, и
   правит.

#### 3.1.1. Полная цепочка данных прототипа (какие этапы затрагивает)

Данные прототипа проходят через несколько этапов, на каждом — своё
преобразование:

| Этап | Вход | Что делает | Выход |
|---|---|---|---|
| 07a извлечение | source (docx/pdf/png/md) | приведение к **единому текстовому эталону** (см. ниже) | `source-extracted.txt`/`.json` |
| 07a структурирование | эталонный текст | агент собирает секции/блоки только из текста | `prototype.yaml` |
| 07a fidelity | yaml + эталон | проверка ≥90% + анти-выдумка | `fidelity-report.md`, гейт |
| 07 контент (опц.) | `prototype.yaml`/`.md` | `/landing-content` извлекает тексты по блокам для копирайта/SEO | `content.md`, `seo-copy.md` |
| 07a wireframe | `prototype.yaml` | **маппинг** секций→категории→кандидаты, подстановка контента в превью | `wireframe.html`, `selections.yaml` |
| 07b compose | `prototype.yaml` + selections | подстановка контента/токенов в выбранные блоки | `composed.html` |

**Единый текстовый эталон по форматам:** docx → `extract-docx-text.py`
(параграфы + таблицы в порядке документа); текстовый pdf → `extract-pdf-text.py`;
скан-pdf/png/скриншот → OCR (vision); md → как есть. Цель — любой формат даёт
один и тот же эталонный текст, по которому считается fidelity (правило ≥90% —
едино для всех форматов).

#### 3.1.2. Маппинг прототип → блоки — ТРИ уровня (как происходит)

Превращение `prototype.yaml` в заполненные блоки — это три последовательных
маппинга. Сейчас они **размазаны по 4 словарям в 2 файлах** (render-wireframe.py
и inject-content.py).

**Уровень 1 — секция прототипа → категория блока** (`SECTION_TO_CATALOG_TYPE` +
`SECTION_TO_VARIANT` в render-wireframe.py). `section.id` (бизнес-смысл:
`header`, `hero`, `curriculum`, `tariffs`…) переводится в B34-категорию
(`header`, `hero`, `content/process`, `pricing`…). Неизвестный `section.id` →
по умолчанию `features` (молча, без предупреждения — хрупко).

**Уровень 2 — подблоки секции → поля/список** (`merge_section_blocks` в
inject-content.py). Подблоки секции (`logo`/`menu`/`button`/`heading`/
`paragraph`/`info_badge`/`module`/`tariff_card`…) собираются:
- единичные (`_SINGULAR_SUBTYPES`): heading→title, paragraph→subhead,
  button→cta, info_badge→eyebrow+badges;
- повторяющиеся (module/feature/card/tariff…) → `items[]`.
Хрупко: второй `heading` в секции молча теряется; в `items[]` смешиваются разные
типы без признака-дискриминатора.

**Уровень 3 — слот блока → значение прототипа** (`SLOT_MAPPING` + `resolve_slot`
+ item-regex в inject-content.py). Имя `{{slot:name}}` ищет значение в данных
блока по списку кандидатов: `title` → `[title, headline, heading, text]`,
`cta` → `[cta.text, cta_primary…]`, `feature-1-title` → `items[0].title`,
`brand-name` → `[brand, logo, text…]`. Первый непустой кандидат выигрывает.
Хрупко: порядок кандидатов фиксирован (нет контекста); слот в `src/srcset`
всегда даёт картинку-плейсхолдер, даже если по имени это текст.

#### 3.1.3. Как свести к единой системе маппинга (предложение)

Сейчас 4 источника маппинга (section→category, subblock→field, slot→field,
item-regex) и нет единого списка допустимых `section.id` (есть только
`VALID_BLOCK_TYPES` в `validate-prototype.py`, и он НЕ совпадает с
`SECTION_TO_CATALOG_TYPE`). Предложение (backlog B13):

- **Один декларативный файл** `mapping.yaml` (source of truth) с тремя секциями:
  `section_to_catalog` (id→{категория, variant, приоритет}), `subblock_types`
  (type→{поле, повторяющийся?, алиасы}), `slot_mappings` (слот→{пути,
  is_media}). Код читает его, как `taxonomy.py` читает `taxonomy.yaml`.
- **Валидация `section.id`** против списка: неизвестный → явное
  предупреждение/ошибка (а не молчаливый `features`).
- **Согласовать** `VALID_BLOCK_TYPES` и `SECTION_TO_CATALOG_TYPE` (сейчас
  расходятся: `problem-solution`, `banner`, `urgency` есть в одном, нет в другом
  — это и теряет блоки, см. B11).
- Дискриминатор типа в `items[]`, контекст у `slot_mappings`.

### 3.2. Добавление блока в библиотеку — `/landing-import-blocks`

1. На вход — URL страницы или скриншот блока (из чата или файла). Для URL сначала
   делается скриншот (`take-page-screenshot.py`).
2. **Vision-анализ картинки.** Вход — растровое изображение (PNG/скриншот), а не
   текст или код, поэтому структуру блока нельзя достать парсером — её надо
   «увидеть»: где заголовок, где кнопка, где сетка карточек, какой layout. Это
   делает **текущая модель проекта** (она поддерживает vision) по промпту
   `structure-analysis.md`: по пикселям описывает блоки в JSON — категория,
   layout, слоты. **Codex для этого НЕ используется** — codex в системе нужен
   только для генерации изображений. **(Здесь сейчас два пункта backlog: B1 —
   промпт знает устаревшую таксономию; B16 — анализ переведён на codex-vision,
   надо вернуть на текущую модель проекта.)**
3. По каждому блоку считается сигнатура (`type|layout|[slots]|bg`) и проверяется
   дубль в каталоге (`check_duplicates.py`). При дубле — вопрос «добавить?».
4. Для новых блоков **текущая модель проекта** генерирует нейтральный
   `template.html`-фрагмент с `{{slot}}`-плейсхолдерами (по промпту
   `block-generation.md`). Codex — не для этого.
5. Каталог обновляется (`update-catalog.py`), галерея перегенерируется
   (`generate-gallery.py`).

### 3.3. Сборка wireframe — `/landing-wireframe`

1. Команда читает `prototype.yaml` проекта, каталог блоков и (если есть) токены
   дизайн-системы этапа 05.
2. Для каждой секции прототипа собираются её данные без потерь (повторяющиеся
   подблоки → список элементов, кнопки → CTA, бейджи → надзаголовок).
3. Для секции подбираются блоки-кандидаты её категории (и подкатегории, если
   задана) — `match-candidates.py` возвращает все подходящие.
4. В каждый кандидат подставляется реальный контент прототипа
   (`inject-content.py`): тексты в `{{slot}}`, картинки-плейсхолдеры в слоты
   изображений.
5. Каждый блок оборачивается в превью: сначала нейтральные дефолты и
   preview-правки, затем сам блок, затем mood и токены проекта — так, чтобы
   фирменные цвета/шрифты **переопределяли** дефолты блока. Блок рендерится при
   ширине 1280px и масштабируется — без искажений вёрстки.
6. Готовый `wireframe.html` + `candidates.yaml`. Маркетолог выбирает варианты и
   скачивает `selections.yaml`.

### 3.4. Сборка финальной страницы — `/landing-compose`

1. Читаются выбор маркетолога (`selections.yaml`), прототип, токены
   дизайн-системы и каталог.
2. По каждому выбранному блоку (десктоп и мобайл):
   - подставляются цвета/шрифты проекта в переменные `var(--lp-*)`
     (`inject-tokens.py`), при выбранном mood — его палитра;
   - подставляется текст прототипа и реальные фото (этап 07c) / визуалы
     (07d) в слоты (`inject-content.py`).
3. Блоки склеиваются в порядке, выбранном маркетологом → `composed.html`
   (+ мобильная версия + лог подстановки).

## ЧАСТЬ III-bis — ПОЧЕМУ ОДИН composed ПРЕМИАЛЬНЫЙ, А ДРУГОЙ «НА КОЛЕНКЕ»

Разбор на двух реальных результатах: эталон
`dubai-avto-liza/07b_COMPOSED/composed-brutalist.html` (выглядит премиально) и
`neurokreator/07b_COMPOSED/composed.html` (выглядит как студенческая верстка).
Цель — формализовать, **чего не хватает** второму, чтобы compose стабильно давал
премиум. Это вход для отдельного PR качества (backlog B21).

### Замеренная разница (один и тот же движок compose)

| Признак | dubai (премиум) | neurokreator (слабый) | Почему важно |
|---|---|---|---|
| Строк CSS (дизайн-система) | ~1360 | ~290 | премиум = проработанная система, а не минимум |
| Кастомный шрифт | Inter 400–900 (Google Fonts, 6 весов) | системный `-apple-system` | системный шрифт «по умолчанию» = дешёвый вид |
| `clamp()` (fluid typography) | 19 | **0** | фикс-px заголовки не дышат между экранами |
| `IntersectionObserver` (reveal-on-scroll) | 2 (есть) | **0** | без анимации появления страница «мёртвая» |
| `.reveal` анимации | да, с задержками `delay-1..5` | **нет** | премиум разворачивается по мере скролла |
| `backdrop-filter` (стекло на nav) | 6 | **0** | липкая шапка со стеклом = признак качества |
| `@keyframes` | pulse-dot, паралакс и др. | 1 (простой fadeIn) | живые микро-детали |
| Реальные фото (`assets/photos`) | 41 | 1 (только hero) | контентные секции с фото vs пустые карточки |
| Иконки | продуманный набор + SVG | Lucide-заглушки + **эмодзи в `<h3>`** (🎯💰⚡👔) | **эмодзи в заголовках — главный маркер «на коленке»** |
| OG/SEO-мета, favicon | полный набор (og:*, twitter, theme-color, SVG-favicon) | только title | premium = production-ready голова документа |
| Hero | фон-фото + двойной градиент-overlay + паралакс | плоский градиентный прямоугольник-заглушка | hero задаёт первое впечатление |
| Декоративные слои | shape-фигуры, свечения, highlight-маркер текста | нет | плоскость = дёшево |

### Что именно делает dubai премиальным (чек-лист премиум-композа)

1. **Дизайн-система, а не просто стили.** Богатый `:root`: шкала радиусов
   (`--radius-sm..pill`), теней (`--shadow-yel/grn/card/card-h`), длительностей
   (`--dur-fast/dur/dur-slow`) и ease-кривых (`--ease`, `--ease-brutal`). У
   neurokreator — плоский набор цветов + 4 тени, без системы движения.
2. **Fluid-типографика на `clamp()`** для всех заголовков (`h-display`,
   `h-section`, `h-card`) + `text-wrap: balance/pretty`, `letter-spacing`,
   `line-height: 0.9` для display. neurokreator — фикс `56px/40px/20px`.
3. **Кастомный брендовый шрифт** (Inter 6 весов с preconnect). Системный шрифт
   мгновенно читается как «не дизайнили».
4. **Движение:** reveal-on-scroll через `IntersectionObserver` + ступенчатые
   задержки, pulse-индикатор «в наличии», паралакс hero, hover-лифты с тенями.
   У neurokreator движения почти нет.
5. **Глубина и слои:** фон-фото + многослойные градиент-overlay, свечения
   (`radial-gradient`), наклонный жёлтый highlight-маркер слов, стекло на nav
   (`backdrop-filter: blur+saturate`). neurokreator — плоские заливки.
6. **Реальный контент-фото в секциях** (41 фото), а не серые карточки с текстом.
7. **Production-голова:** OG/Twitter-мета, theme-color, color-scheme, SVG-favicon
   инлайном, preconnect к шрифтам.
8. **Ноль эмодзи в заголовках.** Премиум использует иконочную систему (SVG/набор),
   эмодзи в `<h3>` (🎯💰⚡) — сильнейший сигнал «собрано наспех».

### Чего НЕ хватает neurokreator (= что чинить в compose)

- **`style_mood`/дизайн-система не применилась в полном объёме** — компоновался
  на «нейтральных дефолтах» блоков (плоские серые карточки), а не на богатой
  системе. Связано с B9 (mood должен давать палитру+типографику+движение, а не
  только цвета).
- **Нет уровня движения** — compose не добавляет reveal-on-scroll/observer (это
  должно идти из mood/паттернов `_patterns/animation-*`, см. раздел про
  `_patterns`, сейчас они подключаются только на этапе 08, не в 07b).
- **Эмодзи как иконки** — в слотах вместо иконочной системы стоят эмодзи. Нужен
  запрет эмодзи в заголовочных слотах + подстановка из икон/визуал-пайплайна
  (07d) или Lucide.
- **Фикс-типографика** — блоки используют px, а не `clamp()`. Норма B36 покрывает
  цвета/шрифты-переменные, но **не fluid-шкалу** — расширить.
- **Пустые визуальные секции** — мало реальных фото (07c) и визуалов (07d);
  карточки голые. Пайплайн фото/визуалов не наполнил слоты.
- **Бедная `<head>`** — нет OG/SEO/favicon (это добавляется на этапе 08 build, но
  для премиум-превью 07b стоит иметь хотя бы favicon+шрифты).

### Вывод

Разница **не в движке compose** (он один), а в том, что у dubai была применена
полноценная дизайн-система (mood) с типографикой и движением + наполненные
фото/визуал-слоты, а у neurokreator compose упал на нейтральные дефолты блоков и
пустые слоты. Премиум = **дизайн-система (палитра+типографика+движение) ×
наполненный контент (фото/визуалы/иконки без эмодзи) × production-голова**.
Формализуется в премиум-чеклист 07b (расширить
`scripts/verify-composed-premium.sh`) и backlog **B21**.

> **ВАЖНО (правка 2026-06-03): премиум ≠ тёмный фон.** Единственный premium-эталон
> 07b (dubai) — тёмный, и это читается как «премиум обязан быть тёмным». Это
> ошибка: 4 из 5 пользовательских референсов-эталонов — СВЕТЛЫЕ. Премиальность
> даёт **композиционная глубина**, а не цвет фона (см. часть III-ter и backlog
> B22). Термин `dark_premium` в `config/niche-visual-rules.yaml` относится к фону
> ФОТОСТУДИИ, не к цвету сайта. Уже ломало проект (lixiang-dubai3, BACKLOG).

## ЧАСТЬ III-ter — АЛГОРИТМ СОЗДАНИЯ ДИЗАЙНА (воспроизводимый, без референсов)

> Зафиксировано по запросу пользователя 2026-06-03: «зафиксируй свой алгоритм
> работы при создании дизайна… думай о том, что референсов может не быть, как бы
> ты добавил все эффекты, что сейчас есть» + «шаги нужны универсальные, не
> зависящие от дизайн-системы».
>
> **Иерархия (важно):** у каждого проекта ВСЕГДА есть **дизайн-система** (этап 05,
> `tokens.json` — палитра/шрифты/токены). **mood** (`_styles/`) — это
> ОПЦИОНАЛЬНЫЙ готовый пресет дизайн-системы, один из вариантов; может
> использоваться, а может и нет. Алгоритм описывает **ЧТО** делать (роли, приёмы),
> а **КАК** (цвет/шрифт/форма/радиус/анимация) — берёт из **дизайн-системы
> проекта** (а если выбран mood — из него). Один алгоритм → разный вид под разную
> дизайн-систему. Без визуальных референсов. Визуальные эталоны живут в
> `docs/design-references/` (НЕ в проектах).

### Что такое «цепляет» (определение премиальности — критерий пользователя)

Премиальность = **композиционная ГЛУБИНА / КОЛЛАЖ**, НЕ тёмный фон и НЕ обилие
анимаций. Признаки (по эталонам пользователя в `docs/design-references/`, 4 из 5
светлые):

1. **Взаимопроникновение слоёв** — герой/объект вырезан и ВЫХОДИТ за границы
   блока, перекрывает соседнюю секцию (не «фото в прямоугольнике встык»).
2. **Декоративные формы и фон-объекты** — форма-подложка под фото, разделитель-
   форма между секциями вместо прямой линии, реквизит-сцена на фоне, паттерны.
3. **Крупные цифры-якоря** в рамке с акцентным цветом.
4. **Акцент-шрифт** — выделяющийся шрифт поверх основного + росчерки/подчёркивания.
5. **Вырезанные фото с эмоцией** на цветных подложках, не сток в боксе.
6. Контраст-секция допустима как приём ритма (1 из N), а не как «премиум=тёмное».

### Универсальный алгоритм (8 шагов; конкретику даёт дизайн-система, не алгоритм)

Вход: `prototype.yaml` (контент) + **дизайн-система проекта** (`tokens.json`; если
выбран mood — берётся его пресет) + опц. фото/визуалы. Алгоритм НЕ хардкодит
значения — он запрашивает их у дизайн-системы по ролям.

**Шаг 1. Развести фоновые роли из палитры дизайн-системы.** Взять минимум 2-3
фоновых тона (база / вторичный / контраст) и акцент. Чередовать секции между
базой и вторичным тоном. Правило: **никогда не оставлять «голый» дефолтный фон
без вторичного тона** — иначе «недоделано». (Конкретные hex — из дизайн-системы.)

**Шаг 2. Применить типографику дизайн-системы.** Основной шрифт (тело) +
**акцент-роль** (если дизайн-система задаёт второй/декоративный шрифт — для
росчерков/eyebrow). Размеры — **fluid** (`clamp(min, vw, max)`), не фикс-px; шкала
и character (uppercase / letter-spacing / line-height) — из дизайн-системы.
Заголовки крупные. Если акцент-шрифта нет — роль «акцент» берёт начертание/вес
основного.

**Шаг 3. Найти «цифры-якоря» в контенте.** Просканировать prototype на числа
(кол-во пунктов, лет опыта, %, цены, сроки). Вынести 3-4 в **полосу-якорь** +
1-2 как **floating-бейджи** поверх hero-фото. Стиль рамки/контраста — из дизайн-
системы. Если чисел нет — взять из оффера (гарантия, срок, кол-во шагов).

**Шаг 4. Hero как КОЛЛАЖ (не 2 колонки встык).** Фото героя вырезать **формой из
`_shapes/`**, положить на **форму-подложку** акцентного тона. Сверху —
floating-цифры (шаг 3) `position:absolute`, наезжающие за край фото. Фон-сцена:
свечение/кольцо/точки акцентом. Какую форму и насколько резкие/мягкие скругления
— **задаёт дизайн-система** (её характер), не алгоритм. Eyebrow — акцент-ролью.

**Шаг 5. Разделители секций — форма, не прямая.** Между секциями разного фона —
**форма-разделитель из `_shapes/`** (волна / кривая / зигзаг — выбор задаёт
дизайн-система), а не прямая граница. Даёт «перетекание» вместо «нарезки».

**Шаг 6. Карточки — с глубиной, не плоские.** Каждая карточка: декор-форма
акцентом в углу (из `_shapes/`, мелкая), иконка в акцентной плашке, hover-лифт.
Сетки — ломать ритм (masonry/разный span), не ровная решётка. Иконки — **только
SVG/набор или картинки**, НИКОГДА эмодзи в заголовках.

**Шаг 7. Один контраст-акцент.** Ровно ОДНА секция — на контрастной подложке
дизайн-системы (насыщенный/тёмный тон) для ритма. Это приём, не тема. Финальный
CTA — на акцентном фоне с декор-формами по краям.

**Шаг 8. Движение и production-голова.** Уровень движения — **из дизайн-системы**
(reveal-on-scroll, стекло на nav, pulse и т.п.; дизайн-система может его
приглушать). В `<head>`: шрифты (preconnect),
OG/Twitter-мета, favicon, theme-color.

### Принцип выбора объектов (что куда ставить — БЕЗ референса)

Детерминированные правила «контекст → роль объекта». **Конкретная форма берётся
из `_shapes/`, её выбор задаёт дизайн-система**, а не жёсткий хардкод:

| Контекст в контенте | Роль объекта | Источник |
|---|---|---|
| hero с фото человека | форма-подложка под фото + floating-цифры | `_shapes/` (тип — из дизайн-системы) |
| граница двух секций разного фона | форма-разделитель | `_shapes/` (волна/кривая/зигзаг — из дизайн-системы) |
| блок с метриками/числами | полоса цифр-якорей на контрасте | layout + стиль дизайн-системы |
| карточка (features/why) | декор-форма в углу + иконка-в-плашке | `_shapes/` мелкая |
| ключевое слово в заголовке/lead | росчерк-подчёркивание | `_shapes/` / акцент-роль дизайн-системы |
| eyebrow секции | акцент-шрифт (если задан дизайн-системой) | типографика дизайн-системы |
| финальный CTA | акцентный фон + декор-формы | дизайн-система + `_shapes/` |
| ровно 1 секция на странице | контраст-подложка | вариант дизайн-системы |

**Правило плотности:** не более ~1 декор-объекта на смысловую зону, иначе
«шумно» (порог может уточнять дизайн-система). Формы — **всегда из `_shapes/`**,
НЕ рисовать руками.

### Критическое ограничение (честно): чего у системы НЕТ

- **Это пока НЕ автоматизировано.** Эталон-доказательство собран РУКАМИ как
  цельный HTML; формы нарисованы inline (т.к. `_shapes/` не подключён — B10).
  Движок compose так НЕ умеет — клеит готовые блоки встык без коллаж-логики.
- **Чтобы алгоритм работал в системе**, его шаги надо встроить в коллаж-блоки +
  подключить `_shapes/` (B10) + расширить дизайн-систему ролями «акцент-шрифт /
  формы / уровень движения» (B9/B21). Тогда «КАК» полностью уходит в дизайн-
  систему, а compose применяет 8 шагов автоматически. См. B10/B21/B23.
- **Цельный HTML НЕ редактируем в WP** — для wp-admin режется на блоки с
  `{{slot}}` → Lazy Blocks (часть III-quater).

### Хранение эталонов дизайна — «разобрать один раз» (B24)

**Проблема:** если эталоны хранить как голые картинки, агент КАЖДЫЙ раз заново
анализирует изображение «на глаз» → медленно, дорого, нестабильно. **Решение:**
картинку разбирают ОДИН раз в машино-читаемый `analysis.yaml`; дальше система
читает yaml, а не картинку.

**Процесс (подтверждён пользователем):** пользователь кладёт картинку-эталон →
агент один раз пишет `analysis.yaml` (приёмы/формы/палитра-роли) → этот разбор —
источник истины. Картинка остаётся как исходник, но повторно не анализируется.

**Где живёт (НЕ в проектах — в landing-системе):**

```
docs/design-references/
├── README.md                 # как добавлять, схема analysis.yaml
├── catalog.yaml              # индекс всех эталонов (ниша → приёмы) для подбора
└── <ref-id>/                 # один эталон = папка
    ├── source.{jpg,png}      # исходная картинка пользователя
    └── analysis.yaml         # РАЗОБРАННЫЕ приёмы (машино-читаемо)
```

**Схема `analysis.yaml`** (что извлекаем из картинки один раз):

```yaml
id: grooming-petcare
niche: "услуги / уход"          # для подбора по нише проекта
bg_mode: light                  # light | dark | contrast-mix
techniques:                     # приёмы коллажа (словарь из алгоритма III-ter)
  - hero_photo_cutout_overflow  # вырезанное фото выходит за блок
  - blob_under_photo
  - number_anchors              # есть полоса/бейджи цифр-якорей
  - wave_dividers               # форма-разделитель между секциями
  - accent_script_underline     # рукописный росчерк-подчёркивание
shapes_used: [blob, wave]       # связь с каталогом блобов (см. ниже)
palette_roles:                  # роли (не конкретные hex — они из дизайн-системы)
  base: light
  secondary: warm-tint
  accent: brand
number_anchors_example: [6, 4, 2000]   # как пример подачи цифр
notes: "что именно цепляет — словами пользователя"
```

`catalog.yaml` — индекс: `id → {niche, bg_mode, techniques}`, чтобы агент
подбирал релевантный эталон по нише проекта и применял его `techniques` через
алгоритм III-ter.

### Каталог блобов / декор-форм — отдельное хранилище (B25)

Декоративные формы (blob, волны, кляксы, кольца, росчерки) — **отдельный каталог**
с превью и метаданными, НЕ смешивать с эталонами-лендингами. Базируется на
существующем `block-library/_shapes/` + `_shapes/catalog.yaml`, но **дополняется
полем контекста** — для какого приёма/места форма предназначена:

```yaml
# _shapes/catalog.yaml — дополнить каждую форму
- id: blob
  name_ru: "клякса"
  category: organic
  contexts: [hero_photo_underlay, card_corner_accent]   # НОВОЕ: где применять
  svg_vars: ["{color}", "{opacity}"]
- id: waves
  name_ru: "волна"
  category: organic
  contexts: [section_divider]                            # НОВОЕ
```

Тогда алгоритм III-ter (таблица «контекст → роль объекта») подбирает форму
**автоматически по полю `contexts`**, а не «рисует руками» и не угадывает.
Хранилище нужно подключить к compose И build (это B10).

**Итог связки:** картинка → `analysis.yaml` (приёмы) → алгоритм III-ter
применяет приёмы → формы берутся из каталога блобов по `contexts` → дизайн-система
даёт цвет/шрифт/радиус. Ни на одном шаге не нужно повторно анализировать картинку.

## ЧАСТЬ III-quater — РЕДАКТИРУЕМОСТЬ В WORDPRESS (коллаж + Lazy Blocks)

> Зафиксировано 2026-06-03. Требование пользователя: **клиент должен править
> тексты/фото сам в wp-admin.** Значит финал ОБЯЗАН быть набором блоков, а не
> цельным HTML.

### Как slot становится редактируемым полем (цепочка этапа 08)

```
{{slot:name}} в template.html  →  block-spec.yaml (контракт: name/type/label)
  →  generate-lzb-templates.py (block.php с get_field/esc_html)
  →  Lazy Blocks регистрирует контрол  →  поле в wp-admin (Gutenberg inspector)
```

Маппинг: `{{slot:contacts_heading}}` → `block-spec.yaml::controls[name: contacts_heading, type: text]`
→ `<?php echo esc_html($attributes['contacts_heading']); ?>` → текстовое поле
«Заголовок» в панели справа.

### Core-блоки vs Lazy Blocks — почему именно Lazy

| | Core-блоки (Heading/Paragraph/Image) | Lazy Blocks (кастом с полями) |
|---|---|---|
| Правка | клик по тексту на странице | поле в inspector справа |
| Коллаж/формы/глубина | **разваливается в столбик** | **сохраняется** (зашита в блок) |
| Клиент ломает вёрстку | легко | нет (правит только поля) |
| Путь системы | ❌ | ✅ (миграция ACF→Lazy Blocks, [[project-stage08-lazy-blocks-decision]]) |

Конвертация коллажа в **core-блоки убивает дизайн** (формы/наезды невозможны).
Только **Lazy Blocks** дают и WYSIWYG-правку полей, и сохранение коллаж-вёрстки.

### Коллаж и редактируемость СОВМЕСТИМЫ (ключевой факт)

Сложная вёрстка (наезды, `position:absolute`, blob, floating-цифры) НЕ конфликтует
с редактируемостью **если декор отделён от контента**:
- декор-слои — отдельные `<div>` с `pointer-events:none`, ниже по `z-index`;
- редактируемые `{{slot}}` — в чистом контент-слое поверх (`z-index:1`).

Подтверждено: 10+ блоков библиотеки уже используют `position:absolute` для декора
без конфликта с полями. То есть коллаж-блок МОЖЕТ быть Lazy Block.

### Что нужно, чтобы коллаж поехал в WP (объём)

1. разрезать дизайн на блоки (`hero` / `цифры` / `карточки` / `тарифы` …);
2. в каждом — текст/фото заменить на `{{slot:name}}` (формат B35);
3. заполнить `block-spec.yaml` (slot→control);
4. этап 08 соберёт Lazy Blocks тему → wp-admin редактируем.

Фундамент (Lazy Blocks, slot→поле, совместимость с absolute) **уже есть** —
работа в наполнении (коллаж-блоки + подключение `_shapes/`), не в архитектуре.

### 🔒 ПРАВИЛО ФЛОУ (T29): ВСЕ цвета — только через CSS-переменные, ВСЕГДА

> Зафиксировано 2026-06-08 на прогоне hibridcars-uae (переключатель дизайн-систем
> lp-preview-panel). При попытке переключить дизайн-систему «на лету» оказалось,
> что **часть цветов захардкожена мимо токенов** (`#161311` фон карточек,
> `rgba(0,120,214,…)` синие галочки/теги/glow, `#fff` тексты, `background:#fff`
> у цифр-якорей). Поэтому смена mood перекрасила только токенизированные элементы,
> а захардкоженные остались в старой палитре → дизайн «протёк» наполовину,
> выглядел уродливо (тёмные сине-чёрные карточки на бежевом фоне brutalist).

**Правило (нормативное, для composed.html И для DESIGN.md/темы):** в CSS
лендинга **НИ ОДНОГО литерального цвета** — все цвета ТОЛЬКО через
`var(--c-*)`-токены. Это касается:

1. **Заливок/фонов** — включая «технические» (`background:#fff` у наложенных
   цифр-якорей → `var(--c-bg)`, чтобы заливка всегда совпадала с фоном секции).
2. **Тёмных секций/карточек** — фон `var(--c-dark)`/`--c-dark-2`, текст
   `var(--c-dark-ink)`, линии `var(--c-dark-line)` (НЕ `#161311`, НЕ `#fff`).
3. **Полупрозрачных акцентов** (glow, теги, галочки, рамки) — через
   `color-mix(in srgb, var(--c-accent) N%, transparent)`, НЕ `rgba(0,120,214,…)`.
4. **Декора** (blob, glow, градиенты) — оттенки из токенов, не литералы.

**Зачем:** дизайн-система меняет ТОЛЬКО цвета (шрифты и формы остаются —
решение клиента T29). Это работает, только если 100% цветов идут через токены:
тогда `body.lpd-<mood>` переопределяет палитру — и перекрашивается ВСЁ, без
ручной правки каждого селектора. Любой литеральный цвет = «протечка» старого
дизайна при переключении.

**Проверка (добавить в build/verify):** grep по CSS темы на литеральные цвета
вне `var()`/`color-mix()` — `#[0-9a-f]{3,6}` и `rgba?\(` не в составе токена →
fail. Исключения: `transparent`, `currentColor`, белый/чёрный ВНУТРИ
`color-mix`. **Связано:** T28 (артефакты из composed), lp-preview-panel
(`08_КОД/plugins/`), B2 (cookie-banner token-driven).

**Конкретные ловушки, пойманные на прогоне hibridcars (все давали «протечку»):**

1. **SVG `fill="#fff"` в разметке блока** (волна-разделитель `.wave` в brands) —
   на светлом mood белая волна = «белая полоса». Фикс: `fill="currentColor"` +
   `.wave{color:var(--c-bg)}` (волна = цвет фона предыдущей секции).
2. **Hero overlay-градиент** `rgba(8,7,6,…)` захардкожен → hero оставался
   чёрным во всех moods. Фикс: `color-mix(in srgb,var(--c-dark) N%,transparent)`.
3. **Тёмные тона `--c-dark`/`--c-black`/`--c-dark-2` = чистый #000** в светлых
   moods → шапка/подвал/карточки чёрные, хотя «в стандартных дизайн-системах
   чёрного нет». Фикс: задавать `--c-dark*` как **тёмный ТОН mood** (тёмный
   кобальт для swiss, тёмный бордо для coral, navy для retro), НЕ #000.
4. **`background:#fff` у наложенных цифр-якорей** (`.svc-card__n`) → на бежевом
   фоне белые прямоугольники. Фикс: `background:var(--c-bg)` (заливка = фон).
5. **Cache:** после правки CSS браузер кэширует по имени файла → правки «не
   видны». В `wp_enqueue_*` ставить версию `filemtime($file)`, не `'1.0'`.

**Найдено через pixel-sampling рендера (надёжнее визуального осмотра):**
сэмплировать ключевые зоны (`PIL.getpixel`) и сверять с ожидаемой палитрой mood —
nav, hero-overlay, фон секций, переходы-швы. Чёрные пиксели вверху ≠ всегда nav
(может быть тёмный фон самой панели превью lp-preview-panel).

**1. Палитра mood — ВСЕГДА с пикселей референса (T12), не на глаз.** Замер

`--c-dark*` тоже тёмные (вся страница тёмная). Любой захардкоженный `#fff`
(текст) или `background:#fff` (плашка/число-якорь/актив-пилюля) на тёмном mood
«протекает» бельмом — поэтому T29 (100% цветов через токены) на тёмном moode
**обязателен**, а не желателен.

### 🔒 ПРАВИЛО ФЛОУ (T31): токенизация учитывает ПАРУ «подложка ↔ то, что сверху» (авто-контраст), а не глобальный акцент

> Зафиксировано 2026-06-09 на прогоне hibridcars-uae. **Эволюция T29.** T29 требует
> «всех цветов через токены», но этого МАЛО: элемент, берущий глобальный
> `--c-accent`/`--c-accent-2`, сливается с фоном, если подложка СЛУЧАЙНО близка к
> акценту. **Воспроизведено:** карточке подмешали тинт акцента в фон (см. T34), и на
> синем mood теги/иконки/текст (бравшие синий акцент) слились с поголубевшей
> подложкой — «всё через токены», но нечитаемо.

**Правило (нормативное):** цвет элемента выбирается ОТНОСИТЕЛЬНО ЕГО ПОДЛОЖКИ
(светлота фона), а не как глобальный токен акцента. «Токенизировано» ≠ «контрастно».
Каждый элемент-текст/иконка/акцент-на-поверхности обязан читаться на СВОЁМ фоне при
любом mood и любом тинте подложки.

**Механизм (решение клиента 2026-06-09): переменная светлоты поверхности (НЕ
`color-contrast()`).** Причина выбора: CSS `color-contrast()` пока экспериментальный
(Safari частично, Chrome за флагом) → на проде ненадёжен, нарушил бы правило
«проверяем по пикселям во всех браузерах». JS-замер яркости — лишняя зависимость на
каждый блок (для server-rendered WP). Поэтому: **каждая поверхность объявляет свой
тон**, а on-color (текст/иконка/акцент) выбирается из пары light-surface/dark-surface.
Это «авто» в смысле «задал фон → контраст следует сам», работает во всех браузерах,
чистый CSS. Тёмная поверхность → светлые on-цвета (`--c-dark-ink`, `--c-accent-2`),
светлая → тёмные (`--c-ink`, `--c-accent`).

**Проверка (в verify):** для каждой пары фон↔текст в композе/теме — контраст
(APCA/WCAG) выше порога при ВСЕХ mood. Сэмплировать рендер (`PIL.getpixel`) фон и
элемент, сверять дельту яркости. Низкий контраст = дефект, не «на вкус».
**Связано:** T29 (токены — этот пункт его усиливает), T34 (тинт подложки вскрыл
проблему), B9/B21 (mood/премиум), T12 (по пикселям).

### Находки по деплою (прогон 2026-06-09)

- **D1: `lp-preview-panel` НЕ деплоится основным `deploy-wordpress.sh`** — скрипт синхронит только `wp-theme/`. Плагин-переключатель дизайн-систем (`08_КОД/plugins/`) надо заливать отдельно (scp+`wp plugin activate`). **Backlog:** deploy-скрипт должен подхватывать `08_КОД/plugins/*`.
- **D2: переключатель mood admin-only** (`current_user_can('edit_theme_options')`). Для показа КЛИЕНТУ без логина — выставить option `lp_preview_panel.visible_to_anon=1`; **снять перед прод-деплоем** (иначе панель видна всем посетителям).
- **D3: B23#15 подтверждён** — `deploy-wordpress.sh` не создаёт `.htaccess` и не делает `wp rewrite flush` → REST 404 → превью блоков в редакторе «не JSON». Ручной пост-шаг: `.htaccess` с `RewriteBase /<sub>/` + `wp rewrite flush` → `/wp-json/` стал 200. **Backlog (как B23#15):** в deploy-скрипт.
- **D4: фото бренд-карточки рендерятся прямым URL темы** (`get_template_directory_uri()/assets/img/<file>`), НЕ через медиатеку → замена файла в `assets/img/` (имя то же) обновляет фото без media-reimport/page-content правок.
- **D5: новый WP-проект на тест-Beget** = отдельная установка в подпапку (`public_html/hibridcars`) + СВОЯ БД (создаётся в панели Beget, не по SSH) + prefix. Эталоны других проектов (`/lixiang` и т.д.) не трогаются.
- **D6: брендовые подстраницы = standalone HTML-файлы темы + pretty-URL rewrite.** Каждая марка получает отдельный лендинг (`wp-theme/<slug>.html`), отдаётся по `/<slug>/` через `add_rewrite_rule('^<slug>/?$','index.php?lp_subpage=<slug>','top')` + `template_redirect`, который `echo file_get_contents()` и `exit` (не Lazy-Blocks-страница — самодостаточный документ со своим head/nav/footer/mood-панелью). Все подстраницы делят ОДИН «каркас» (head-токены, nav-SVG, footer, 3 хвостовых скрипта) — копируется дословно из эталона (`li-auto.html`), различается только page-specific `<style>` + body. **Mood наследуется между страницами** через общий `localStorage` ключ `lp-axis-design` (mood-панель пишет туда, каждая страница читает на init). При добавлении новых slug'ов — расширить и `lp_register_subpages` (массив), и whitelist в `lp_render_subpage`, и **бампнуть маркер `lp_subpages_flushed`** (иначе rewrite-правила не перерегистрируются) + один раз `wp rewrite flush`.
- **D7: КРИТИЧНО — ручное редактирование `page-content.html` не делать через `urllib.parse.quote()` всей строки блока.** Хранимый формат Lazy-Blocks-комментария = JSON с `\"`-экранированием внутри (например `logo_html`), при этом строка в page-content **минимально-кодирована** (`<`,`"`,`{` оставлены raw, `%XX` почти нет). `quote()` percent-кодирует обратные слэши → `\"` превращается в `%5C"` → JSON-атрибуты блока **не парсятся**, блок молча падает на дефолты (у нас: кнопка карточки → дефолт `#custom` вместо subpage-URL). **Правильно:** вставлять атрибут точечным `str.replace` по УЖЕ-закодированной строке (`marker → marker+' "cta_url": "<v>",'`), НЕ декодируя/перекодируя весь блок. Проверка после правки: `re.findall(r'%[0-9A-Fa-f]{2}', line)` должно совпадать с эталонной нетронутой строкой (у нас — пустой список во всех брендах).
- **D8: `deploy-wordpress.sh` сидит page-content из ТРАНСФОРМИРОВАННОЙ копии** (`fix-page-content-images.py`) — повторный прогон может не подхватить свежие неизображенческие атрибуты. Для правок атрибутов (cta_url и т.п.) надёжнее ручной re-seed: `scp page-content.html` → `wp post update <ID> --post_content="$(cat ...)"`. Фото бренд-карточек это не ломает (они theme-URL, не page-content `<img>` — см. D4).

### Правило: CSS-геометрия приоритетнее inline WP-атрибутов

При переносе CSS коллажа (шаг 1 рецепта) — **инструкции, задающие геометрию и
вид элемента (размер, пропорция, форма, цвет, object-fit), должны быть
приоритетными** над тем, что WordPress навешивает inline. WordPress/Lazy Blocks
динамически добавляют к контенту inline-атрибуты (`width`/`height` на `<img>` от
`wp_get_attachment_image`, дефолтные размеры от `wp-block-library`, global-styles
CSS-переменные), которые **перебивают** наш CSS. Поэтому правила формы/размера в
коллаж-блоках задавать с защитой от перебивания:

- размеры/пропорции картинок: `width:100% !important; height:auto !important` +
  `aspect-ratio` + селектор `img[width]` (перебить inline width/height);
- цвета/шрифты/отступы критичных элементов — через `var(--lp-*)` + при
  необходимости повышенная специфичность;
- отключать WP-дефолты, которые конфликтуют (баг #8: `wp_dequeue_style`
  `wp-block-library`/`global-styles`/`classic-theme-styles`).

Принцип: **дизайн-система проекта (наш CSS) — источник истины вида элемента, а не
динамические inline-атрибуты WordPress.** Это закладывать в генератор тем (B23) и
в перенос CSS из `composed`→`DESIGN.md`.

### Решение по флоу (принято на прогоне 2026-06-04): источник истины = прототип, шаг парсинга в YAML — пропускаем

Поскольку T6/T7 доказали, что промежуточный `prototype.yaml` **лоссивный** (теряет
карточки-каталоги и кнопки), а правило задачи — «реализовать прототип ДОСЛОВНО, ни одна
кнопка/комментарий не меняются», на этом прогоне принято **новое правило флоу**:

> **Источником истины является сам прототип** (PDF + дословно прочитанный человеком/агентом
> `prototype.md`), а **НЕ его машинный парсинг.** Шаг `md-to-yaml.py` (prototype.yaml) во
> флоу **пропускается** — он только вносит потери. Контент для wireframe/compose берётся
> напрямую из дословного `prototype.md`.

Что это меняет в спеке (кандидат в backlog как изменение пайплайна, не только багфикс):
- **3.1 «Импорт прототипа»**: финальный артефакт этапа 07 — дословный `prototype.md`
  (+исходный PDF/render), без обязательного `prototype.yaml`. YAML — опционально и только
  если он станет lossless (после фикса T6/T7).
- **fidelity-проверка** проводится напрямую: `extract-pdf-text.py` (источник) ↔ `prototype.md`
  (наш дословный разбор), цель — 0 галлюцинаций и 0 потерянных кнопок/строк. YAML из цепочки
  проверки убирается.
- **07_content / compose**: читают `prototype.md`, а не `prototype.yaml`.
- Кнопки и client-комментарии в `prototype.md` помечены явно и переносятся 1:1.

## ЧАСТЬ VII — СЕРВИС ГЕНЕРАЦИИ ВИЗУАЛОВ

> **Назначение раздела:** все правки флоу и алгоритмов по генерации/адаптации
> изображений вносим СЮДА. Это рабочая область подсистемы «изображения лендинга»:
> анализ места под визуал → спецификация → генерация → cut-out → вставка.
> Статус: **гипотеза проверена на пилоте (Li Auto), оформляется как флоу.**

### VII.0. Замысел (одной фразой)

Не «подобрать фото», а для КАЖДОГО визуального слота страницы **проанализировать**
его (контент + цель + регион) и выдать **спецификацию на генерацию**
изображения — дизайн-агностичную (подходит под любую дизайн-систему). Конечная
цель — масштабировать на ВСЕ визуальные элементы страницы.

### VII.1. Алгоритм (по шагам)

```
ДЛЯ КАЖДОГО визуального слота:
  1. АНАЛИЗ КОНТЕНТА   — что вокруг слота (заголовок, тексты, теги, кнопка, блок)
  2. АНАЛИЗ ЦЕЛИ       — что изображение должно доносить (ВЫВОДИТСЯ из контента;
                         напр. карточка-бренд + кнопка «view models» = весь
                         модельный ряд, а не одна машина)
  3. КУЛЬТ. АНАЛИЗ     — числа/цвета/символы/обычаи/табу региона: избегать
     РЕГИОНА             спорного + использовать «хорошее» (см. VII.3, база+ресёрч)
  4. СПЕКА ИЗОБРАЖЕНИЯ — расположение / размер / ratio / формат / промпт
  5. РЕФЕРЕНСЫ         — N референсов = СОСТАВУ композиции (см. VII.4, T22)
  6. ГЕНЕРАЦИЯ         — codex image_gen на CUT-OUT-FRIENDLY фоне (см. VII.2)
  7. CUT-OUT           — rembg isnet-general-use → trim → PNG/alpha
  8. ВСТАВКА           — PNG на CSS-фон дизайн-системы (агностично)
```

### VII.2. Формат генерации — «дизайн-агностичность»

Решение (пилот): нейросети плохо/не делают чистый PNG без фона напрямую →
**генерируем объект на фоне, который ЛЕГКО вырезать**, затем rembg.
Требования к промпту под безопасный cut-out:
- объект на **чистом нейтральном студийном градиенте** (не cinematic-сцена);
- объект **НЕ касается краёв** кадра (margin со всех сторон);
- мягкая контактная тень под объектом, **не доходящая до краёв**;
- → rembg вырезает чисто → PNG/alpha → ложится на ЛЮБОЙ CSS-фон дизайн-системы.

Вариант «фон + объект двумя изображениями» — ОПЦИЯ, не основа (риск, что не
сольются «как влитые»). По умолчанию: один объект → вырез → CSS рисует фон/блоб/glow.

### VII.3. Культурный анализ региона (ОБЯЗАТЕЛЬНЫЙ шаг)

> **Правило флоу:** перед предложением любых визуальных решений агент проводит
> **культурный анализ региона** — числа, цвета, символы, обычаи, табу. Цель:
> **избегать спорного** и осознанно **использовать «хорошее»** (благоприятные
> символы/числа/цвета). Это шаг 3 алгоритма VII.1, не опциональная заметка.

**Как ведём (решение клиента):**
1. **Статичная база — ТЕКСТОМ (Markdown), НЕ YAML.** Курируемые файлы
   `docs/region-knowledge/<region>.md` (напр. `uae-islam.md`): числа/цвета/
   символы/обычаи/табу по региону+религии, **свободным текстом с нюансами и
   оговорками**. Агент **читает базу, не выдумывает**.
   *Почему текст, а не YAML (решение клиента 2026-06-05):* культурные данные —
   это нюансы и контекст («4 = смерть в Восточной Азии, у мусульман нет, но…»),
   которые плоский YAML теряет; для каждого проекта свои важные данные — текст
   гибче (дописал абзац), YAML заставляет придумывать поля. Та же логика, что
   «истина = текст, не лоссивный YAML» для прототипа (T6/T7/T8).
2. **Напоминание про ресёрч** перед запуском проекта: «регион = X, проверь
   актуальность культурных правил (web search), при находках — допиши в базу».
3. **Переиспользование наработок:** если регион УЖЕ был в базе — показать
   накопленное (не ресёрчить заново с нуля), дополнить при необходимости.
4. **При новом/редком регионе** — ресёрч (WebSearch) → внести в базу.

**База: ОАЭ / ислам (стартовая, дополняется).**

*Числа (по разбору клиента 2026-06-05):* особенными в исламе считаются числа,
связанные с Кораном/хадисами/обрядами, НЕ «магия чисел»:
- **благоприятные/значимые:** `1` (таухид, единство Аллаха), `3` (троекратные
  действия в омовении/поклонении), `5` (5 столпов, 5 молитв), `7` (семь небес,
  7 обходов Каабы — одно из самых известных), `12` (месяцы), `33` (зикр после
  молитвы), `40` (возраст Пророка при откровении, испытание/очищение),
  `99` (99 имён Аллаха). `19` — обсуждается (интерпретации, не вероучение).
- **табу:** у мусульман прямого табу на числа (как `4` в Восточной Азии) **нет**
  (проверено). НО: число `4` — символ смерти в Китае/Японии/Корее (тетрафобия,
  пропускают этаж/номер 4) — учитывать, если регион сменится на восточноазиатский.
- *применение:* можно опираться на `3/5/7/99` в количестве элементов (3 машины,
  5 фич, 7 преимуществ) как уместные; не навязывать религиозные числа там, где
  это неестественно.

*Цвета (ОАЭ/ислам):* **зелёный** — цвет ислама/рая (благоприятный, использовать
осознанно, не профанировать); **золото/песочный/белый** — премиум, чистота,
уместны для Dubai-люкс; избегать сочетаний, читаемых как флаги/религиозные
символы не к месту. (Уточнять в базе при ресёрче.)

*Символы/обычаи/табу:*
- нет свиней/алкоголя/азартных игр/немусульманских религ. символов;
- люди — скромная одежда (закрытые плечи/колени), без рискованных жестов
  (палец вверх/«ок» в некоторых культурах оскорбительны — проверять);
- **левая рука** считается «нечистой» — избегать жестов/подачи предметов левой;
- собаки — в исламе неоднозначно (не в дом/не к еде) — осторожно с домашними
  животными в кадре.

*Рыночное/техническое (ОАЭ):*
- **Руль слева (LHD)** — левостороннее движение (правый ряд) → генерить LHD;
- **без текста/номеров:** «no text, no license plate, no chinese characters»;
  либо нейтральный номер.

> При смене региона — свой текстовый файл `docs/region-knowledge/<region>.md`.
> Восточная Азия: добавить тетрафобию (`4`), цветовые табу (белый = траур в
> Китае), и т.д. — по ресёрчу.

### VII.5b. Подложка под cut-out (тёмные элементы на тёмном фоне)

**Проблема (T24):** cut-out машины на тёмной карточке → **чёрные шины сливаются с
чёрным фоном**, машины читаются «без колёс». Общий случай: любой тёмный объект
(колёса/тени/тёмные кромки) на тёмной панели теряет контур.

**Решение — CSS-подложка (НЕ перегенерация изображения):** под объектом —
светлое/бронзовое **органичное пятно-блоб** (`::after` в медиа-блоке), которое
подсвечивает зону колёс. Колёса на светлом → читаются; коллаж-глубина без
перегруза. Применено к карточке Li Auto (вариант B — мягкий блоб-помост):
```css
.brand-card__media::after{
  content:"";position:absolute;z-index:1;left:10%;right:-2%;bottom:14%;height:48%;
  background:radial-gradient(ellipse 70% 90% at 58% 75%,
    rgba(243,233,216,.22),rgba(184,137,63,.12) 50%,transparent 72%);
  border-radius:46% 54% 52% 48%/60% 56% 44% 40%;filter:blur(10px);pointer-events:none}
```
*Правило:* тёмный cut-out на тёмном фоне ВСЕГДА получает светлую подложку под
зоной тёмных элементов (колёса/тени). Изображение при этом не трогаем — фикс
чисто на стороне дизайн-системы (CSS), что и подтверждает агностичность (T21).

> **Уточнение области:** сейчас правится ОДНА карточка Li Auto с линейкой из 5
> машин (L6/L7/L8/L9/MEGA внутри неё). «5 брендов» (Zeekr/Xiaomi/ROX/Lynk&Co) —
> это ОТДЕЛЬНЫЕ карточки на будущее, не «5 карточек сейчас».

## ЧАСТЬ VIII — ГИПОТЕЗА: ФУНДАМЕНТ ФЛОУ = ПРОТОТИП + АНАЛИЗ РЫНКА×НИШИ

> **Статус: ГИПОТЕЗА НА ПРОВЕРКЕ. Флоу НЕ меняем, пока не подтвердится.**
> Фиксируем как наблюдение к тесту (принцип «сначала проверяем гипотезу, потом
> оформляем спеку» — как с сервисом визуалов VII). Раздел — рабочая область:
> правки вносим сюда, в действующий флоу — только после подтверждения.

### VIII.1. Суть гипотезы

У флоу **ТРИ входа первого класса**, и всё остальное (дизайн-система, контент,
визуалы, генерация изображений, цвета, числа, тон, структура) **выводится из них**,
а не решается отдельно «на вкус»:

1. **ПРОТОТИП** — «ЧТО»: блоки, тексты, кнопки, структура (что хочет клиент).
2. **АНАЛИЗ РЫНКА × НИШИ В РЕГИОНЕ** — «ДЛЯ КОГО / КАК / ЧТО МОЖНО»: культурно-
   поведенческий профиль (цвета/числа/символы/табу/тон/архетипы) + специфика ниши
   именно в этом регионе.
3. **РЕФЕРЕНС КЛИЕНТА ПО ДИЗАЙН-СИСТЕМЕ** — «КАКОЙ ВИД ХОЧЕТ КЛИЕНТ» (напр.
   Mercedes MENA): желаемый визуальный язык. Тоже ВХОД, не истина в последней
   инстанции — проверяется на соответствие региону/нише.

Все три — **внешние ручные входы** (клиент даёт), система их принимает.

**+ КОНТЕКСТ (обязателен для корректного gate, наблюдение 5):**
- **БИЗНЕС-МОДЕЛЬ клиента** (офиц. дилер / посредник-подборщик / производитель) —
  определяет, что МОЖНО заявлять. Посредник НЕ вправе писать «official dealer /
  GCC specs / manufacturer warranty» — это ложь (= табу «misleading»). Без этого
  контекста gate выдаёт ложные «конфликты».
- **ТИП СТРАНИЦЫ** (агрегатор / страница модели / лендинг-оффер) — определяет,
  какие cues уместны. finance/monthly/спеки — по-модельные (страница модели),
  не на агрегаторе. Агрегатор = выбор/навигация/заявка → довести лид до менеджера.

**Ключевое уточнение (клиент):** анализ — это **ниша × регион**, НЕ ниша отдельно
и регион отдельно. Их **пересечение** даёт реальные правила. Пример клиента:
> Свинина в Испании — деликатес (целый ресторанный бизнес), в восточных странах —
> табу (нельзя вообще). Одна и та же ниша → противоположные правила в разных
> регионах. Поэтому «анализ ниши без региона» бессмыслен.

### VIII.1b. ВЫХОД фундамента = ДОКУМЕНТ-ПРОВЕРКА (hard gate перед генерацией)

Из трёх входов собирается **документ-проверка соответствия** — он СНАЧАЛА
валидирует входы на соответствие региону/нише, и **только после согласования
человеком** флоу переходит к генерации. Это **hard gate** (как stage-gates
системы: агент НЕ идёт дальше без явного approve).

**Что проверяет (по порядку):**
1. **Тексты** — соответствие региону/нише: нет запретных формулировок
   (для Дубая: «sinfully good», шутки о религии, misleading claims), тон уместен
   (official/trusted/family-ready/peace of mind), фразы под архетипы.
2. **Прототип / структура** — есть ли нужные trust-cues ниши (для авто-Дубай:
   finance/monthly/service/official dealer/warranty/GCC specs), нет ли лишнего/
   неуместного, bilingual-готовность (Arabic/English, RTL).
3. **Дизайн-система / референс клиента** — цвета/символы/числа не нарушают табу
   региона и уместны (для Дубая: палитра safe-default, 7/5 ок, священные формулы
   нельзя, modest, без свиней/алкоголя, LHD).

**Поведение при несоответствии (решение клиента — «стоп + отчёт»):**
- Документ **помечает конфликты** и **НЕ переходит к генерации**.
- Показывает: «референс хочет X, рынок говорит Y — решите»; «текст Z = табу».
- **Не идёт дальше без согласования** (явный approve человеком).
- Только после approve → переход к генерации (визуалы, изображения — часть VII).

> Аналог: stage-gate. «Проверка соответствия региону/нише» — обязательный вентиль
> между ВХОДАМИ (прототип+рынок+референс) и ГЕНЕРАЦИЕЙ. Без approve — стоп.

### VIII.2. Что меняется относительно текущего состояния

- **Сейчас:** анализ рынка существует как deep-research документы (Дубай:
  `Маркетинговый культурно-поведенческий профиль рынка Дубая 01/02.md`), но во
  флоу он **прикручен сбоку** — региональные правила всплыли только на этапе
  генерации визуалов (VII.3). Дизайн-система собиралась из референса (Mercedes),
  контент — из прототипа, а рынок не был источником решений.
- **Гипотеза:** рынок×ниша — **сквозной фундамент**, влияет на ВСЕ этапы
  (подтверждено пользователем: «на ВСЕ этапы»):
  - **дизайн-система** — палитра/типографика/тон выводятся с учётом региона
    (напр. для Дубая: белый/зелёный/чёрный/песок/золото — safe-default; неон —
    чужероден; bilingual Arabic/English; Dubai Font);
  - **контент** — тон/фразы/архетипы из рынка (напр. «official/trusted/peace of
    mind/family-ready/GCC specs», избегать «sinfully good/rule the city»);
  - **визуалы** — числа/символы/табу (7 и 5 — позитивны; священные формулы —
    нельзя; modest dress; без свиней/алкоголя; LHD);
  - **структура** — рыночные trust-cues (для авто-ниши Дубая: finance/monthly
    payment/service/official dealer/warranty/GCC specs рядом с product action);
  - **SEO/тон/CTA** — под цифровую культуру региона.

### VIII.3. Анализ рынка×ниши — ВНЕШНИЙ ВХОД, не этап системы

> **Договорённость (подтверждено клиентом):** анализ рынка/ниши проводится
> **ВРУЧНУЮ вне нашей системы** (клиент/маркетолог сам, через внешний deep-research
> — как документы Дубая). В системе — только **(1) напоминание** провести анализ
> и **(2) место для результатов** (вход), НЕ этап-обработчик. Та же логика, что
> прототип: система принимает как вход, не генерирует.

Следствия для гипотезы:
- **НЕ** делать `01a_АНАЛИЗ_НИШИ` этапом-генератором. Это вход первого класса,
  как прототип (см. артефакты `/landing-start`).
- Система: напоминает «положи анализ рынка×ниши региона (если нет — проведи
  вручную)» + принимает готовый текст (как `prototype.md` принимает прототип).
- Хранение — **текстом** (как region-knowledge, VII.3; не YAML): результаты
  анализа кладутся текстовым документом в проект (место — уточнить, напр.
  `01a_АНАЛИЗ_НИШИ/market-niche-region.md` как ВХОД, не вывод скрипта).
- Порядок: оба входа (прототип + анализ рынка×ниши) готовы на старте, ДО решений
  по дизайну/контенту/визуалу; из них всё выводится.

> Существующий `01a` (market-profile.md, competitors.yaml) и `seo-tech-audit` —
> отдельная история; гипотеза НЕ превращает их в обязательный авто-этап, а
> закрепляет анализ рынка×ниши как ручной внешний вход + напоминание.

### VIII.4. Что проверяем в тесте (критерий подтверждения)

Гипотеза подтверждается, если на прогоне видно, что **решения, выведенные из
рынка×ниши, дают заметно лучший/уместный результат**, чем решения «на вкус»
(напр. палитра/тон/числа/структура, обоснованные анализом Дубая, vs произвольные).
Тест начинаем сначала с этим принципом: прототип (есть) + анализ рынка Дубая
(есть, 2 документа) → из них выводим всё остальное.

### VIII.4b. 🔒 ПРАВИЛО (нормативное): цвета и шрифты — ТОЛЬКО из референса

> **Цвета и шрифты НЕ должны противоречить нише × региону.**
> - Если цвет/шрифт референса **НЕ запрещён и НЕ спорен** по рынку×нише → агент
>   берёт его **ТОЛЬКО из референса**, КАК ЕСТЬ.
> - Агент может **порекомендовать** замену (для усиления эффекта), но **НИКОГДА
>   не заменяет сам** — замена дизайн-системы возможна только с approve клиента.
> - Если цвет/шрифт референса **запрещён/спорен** по рынку×нише → агент даёт
>   рекомендацию по правке и **согласовывает**, не меняет молча.
>
> **Запрещено:** менять палитру/типографику «на вкус» и подводить под это
> постфактум-обоснование. Доказано на прогоне: агент заменил синий референса
> Mercedes `#0078d6` → золото `#b8893f` сам, без права на это (синий рынку не
> противоречил). Это нарушение правила (наблюдение 6).
>
> Применяется в gate (ШАГ 3 документа-проверки): для каждого цвета/шрифта референса
> — проверка «запрещён/спорен по рынку×нише?» → нет → брать референс; да →
> рекомендация+согласование. Усиление — только через рекомендацию клиенту.

### VIII.4c. 🔒 ПРАВИЛО (нормативное): ПОРЯДОК — анализ ПЕРЕД сборкой дизайн-системы

> Результат gate-шага «дизайн-система» = **АНАЛИЗ + РЕКОМЕНДАЦИИ**, НЕ готовая
> дизайн-система и НЕ правки кода. Дизайн-система **СОБИРАЕТСЯ ПОСЛЕ** согласования
> рекомендаций. Сборка раньше анализа = нарушение гипотезы (дизайн = следствие
> фундамента).
>
> **Доказано на прогоне (моя ошибка, наблюдение 7):** дизайн-система проекта
> (tokens/DESIGN/composed) была собрана РАНЬШЕ анализа и «на вкус» (золото вместо
> синего референса). Из-за этого gate-шаг скатился в «вернуть/поменять цвет в
> готовой системе» вместо «проанализировать и порекомендовать». Слово «вернуть»
> вообще некорректно: синего в системе никогда не было (он только в референсе) —
> система создана сразу золотой. Это симптом перевёрнутого порядка.
>
> **Правильный порядок:** входы (прототип + рынок×ниша + референс + бизнес-модель)
> → gate-АНАЛИЗ + РЕКОМЕНДАЦИИ → согласование клиентом → **сборка** дизайн-системы
> → генерация. Никогда не собирать/не править дизайн-систему ДО согласования

### VIII.5. Наблюдения к гипотезе (заполняется по ходу теста)

| № | Наблюдение | Доказательство | Вывод |
|---|------------|----------------|-------|
| 1 | Анализ = **ниша × регион**, не по отдельности. Пример: свинина Испания(деликатес) vs Восток(табу) — одна ниша, противоположные правила по региону. | Пример клиента; deep-research Дубая показывает авто-нишу в региональном разрезе (GCC specs, finance-bundle, family/status, LHD). | Анализ ниши обязан быть в связке с регионом. | 2 | Анализ рынка×ниши — **ВНЕШНИЙ ручной вход, НЕ этап-генератор системы.** Договаривались ранее: ниша-анализ делается вручную вне системы, система только напоминает + принимает результаты. | Подтверждено клиентом: «01a_АНАЛИЗ_НИШИ не нужен как этап; в системе только напоминание + результаты». | НЕ делать авто-этап. Анализ = вход первого класса (как прототип). Хранить текстом. См. VIII.3. |
| 3 | **ТРИ входа, не два:** + референс клиента по дизайн-системе (Mercedes). Референс — тоже вход, не истина: проверяется на соответствие региону/нише. | Клиент: «у нас ещё референс клиента по дизайн-системе, его тоже учитываем». | Зафиксировано VIII.1: 3 входа (прототип + рынок×ниша + референс). |
| 4 | **Выход фундамента = документ-проверка (hard gate).** Сначала валидирует тексты/прототип/дизайн-систему на соответствие региону/нише, потом генерация. При конфликте — **стоп + отчёт на решение**, **не переходит к генерации БЕЗ согласования** человеком. | Клиент: «документ, который проверяет тексты/прототипы/дизайн-систему на соответствие региону/нише, затем генерация»; «не переходит без согласования». | Зафиксировано VIII.1b как hard gate. | 8 | **🔴 «С нуля» ≠ «починить старое».** Клиент: тест начинаем СНАЧАЛА, дизайн-систему собираем с нуля по референсу. Это правка черновика-нарушения, НЕ сборка с нуля. Откатано: старый composed отложен в `_DRAFT-NARUSHENIE/`, собираем чистый с нуля (вёрстка тоже). | Клиент: «мы договаривались делать с нуля!!! откуда изменения?»; «с нуля всю вёрстку тоже». | Правило: «начать сначала / с нуля» = НЕ переиспользовать накопленный «на вкус» артефакт; отложить как черновик, собрать чистое из фундамента (референс+прототип+анализ). | 7 | **🔴 ПОРЯДОК перевёрнут: дизайн-система собрана ДО анализа.** Результат gate-шага должен быть **анализ+рекомендации**, а у меня дизайн-система уже готова (золотая, «на вкус») → шаг скатился в «вернуть/поменять цвет», что неверно (синего в системе и не было — он только в референсе). | 6 | **🔴🔒 ЖЁСТКОЕ ПРАВИЛО: цвета и шрифты — ТОЛЬКО из референса; агент НИКОГДА не заменяет сам.** Формулировка клиента: цвета/шрифты не должны противоречить нише×региону; если НЕ запрещены/НЕ спорны → берутся ТОЛЬКО из референса; агент может РЕКОМЕНДОВАТЬ замену для усиления, но **НИКОГДА не заменяет сам** (замена — решение клиента). **Поймана моя ошибка:** я САМ заменил синий референса Mercedes `#0078d6` на золото `#b8893f` — это прямое нарушение (синий рынку Дубая не противоречил → менять было нельзя, и тем более не самому). | Клиент дословно: «если не запрещены или не спорные, берёшь ТОЛЬКО из референса.
