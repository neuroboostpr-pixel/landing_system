# Niche Analysis Stage — Design Spec

**Status:** Draft
**Date:** 2026-05-06
**Stage:** 01a_АНАЛИЗ_НИШИ (between 01_КОНТЕКСТ and 02_МАТЕРИАЛЫ_КЛИЕНТА)
**Owner agent:** `niche-analyst`

---

## 1. Цель и проблема

### Проблема

Сейчас следующие этапы (мудборд, бренд-кит, контент) принимают визуальные и текстовые решения **в вакууме**. Brand-architect выбирает tone of voice, не зная, что говорят прямые конкуренты. Moodboard-composer ищет референсы, не зная, какой визуальный язык уже занят лидерами ниши. Content-writer пишет «на что давим», основываясь только на брифе клиента — а клиент почти всегда переоценивает свою уникальность.

### Цель

Между «вот что нам сказал клиент» (`01_КОНТЕКСТ`) и началом креативной работы (`02_МАТЕРИАЛЫ_КЛИЕНТА`+) встроить этап автоматического анализа ниши, который выдаёт три артефакта:

- `niche-analysis.md` — нарратив для человека: тип бренда, краткое описание ниши, рекомендация «на что давим»
- `competitors.yaml` — машиночитаемая база 15–25 игроков (прямые, дилеры, производитель, аналоги, лидеры категории, локальные, косвенные)
- `positioning.md` — единый источник истины про позиционирование, на который ссылаются brand-architect и content-writer

### Принцип

**Zero-touch.** Пользователь даёт бриф → пользователь читает готовый отчёт. Между этим — никаких уточняющих вопросов. Если данных не хватает, агент делает обоснованные допущения с пометкой `[ДОПУЩЕНИЕ]`, не блокируется.

### Язык артефактов

Все **значения полей, описания, тексты** в `niche-analysis.md`, `competitors.yaml`, `positioning.md` — **на русском**. Имена ключей YAML/Markdown — на английском (machine-readable, на них ссылается gate-check.sh и другие агенты). Имена брендов и URL — как в оригинале (BMW iX, не «БМВ айКс»).

## 2. Где встраивается в workflow

### Изменение нумерации

Существующие этапы 00–12 не меняются. Новый этап вставляется как **01a** между `01_КОНТЕКСТ` и `02_МАТЕРИАЛЫ_КЛИЕНТА`:

```
00_БРИФ → 01_КОНТЕКСТ → 01a_АНАЛИЗ_НИШИ → 02_МАТЕРИАЛЫ_КЛИЕНТА → 03_РЕФЕРЕНСЫ → ...
```

Папка проекта: `template/01a_АНАЛИЗ_НИШИ/`.

Stage key в `.landing-state.yaml`: `01a_niche_analysis`.

### Зачем 01a, а не сдвиг 02→03

Сдвиг сломает все существующие проекты (lixiang-dubai и др.) и потребует миграции `.landing-state.yaml`. Вариант `01a` совместим: новые проекты получают этап автоматически, старые могут пропустить (gate-check помечает stage как optional если папки нет).

## 3. Артефакты

### 3.1 `niche-analysis.md`

Нарративный отчёт для человека. Структура:

```markdown
# Анализ ниши: <Название клиента/продукта>

> Дата: YYYY-MM-DD
> Источник входных данных: 00_БРИФ/brief.md, 01_КОНТЕКСТ/context.md
> Тип бренда: 1 | 2 | 3 (Глобальный / Региональный / Локальный без бренда)

## 1. Что мы продаём
<2–4 абзаца: продукт, категория, основной job-to-be-done покупателя>

## 2. Кто покупатель
<1–2 абзаца: ЦА (агрегированная по конкурентам + бриф), их главная боль, что выбирают между>

## 3. Тип бренда и обоснование
<Классификация (Тип 1/2/3) + 3–5 сигналов, на которых решено>
<Что это значит: какой объём анализа, на чём фокус>

## 4. Конкурентная карта (краткое summary)
<Прямые конкуренты: 3–5 строк>
<Локальные игроки: 3–5 строк>
<Производитель/дилеры/аналоги: 2–3 строки>
<Полная база — competitors.yaml>

## 5. На что давим (рекомендация)
<1–2 угла отстройки, каждый — абзац>
<Почему именно эти — со ссылкой на gaps в конкурентной карте>

## 6. Что брать с собой в следующие этапы
- Для brand-architect: <тон, обязательные элементы>
- Для moodboard-composer: <занятые визуальные языки, gaps>
- Для content-writer: <ключевые сообщения, чего избегать>

## 7. Допущения
<Список [ДОПУЩЕНИЕ] с обоснованием — если есть>
```

Длина: 400–800 слов. Без воды.

### 3.2 `competitors.yaml`

Машиночитаемая база. Минимум 15, максимум 25 записей. Обязательные роли (если применимо к нише):

| role | Минимум записей | Если нет в нише |
|---|---|---|
| `direct` | 3 | пропускается с пометкой в notes |
| `local_dealer` | 1 | пропускается |
| `manufacturer` | 1 | пропускается (если клиент сам производитель) |
| `analog` | 2 | пропускается |
| `category_leader` | 1 | пропускается |
| `local_competitor` | 2 | пропускается |
| `indirect` | 1 | пропускается |

Схема записи:

```yaml
- name: string                # обязательно
  role: enum                  # обязательно: direct|local_dealer|manufacturer|analog|category_leader|local_competitor|indirect
  url: string                 # обязательно если есть
  region: string              # geographic scope (UAE, RU, global, ...)
  positioning: string         # 1 предложение, как они себя позиционируют
  target_audience: string     # кому продают, 1–2 предложения
  price_range: string         # ценовой сегмент в локальной валюте, "n/a" если не применимо
  key_messages:               # 3–5 ключевых обещаний с их сайта/коммуникаций
    - string
    - string
  visual_notes: string        # как выглядит их визуал (палитра, фото, ритм). 1–2 предложения.
  notes_for_us: string        # что мы из этого берём / против чего отстраиваемся
  source: string              # откуда данные (URL, search query, brief)
  confidence: enum            # high|medium|low
                              # high: данные с официального сайта или Wikipedia, все обязательные поля без [ДОПУЩЕНИЕ]
                              # medium: вторичные источники (обзоры, агрегаторы) ИЛИ 1 поле помечено [ДОПУЩЕНИЕ]
                              # low: 2+ полей помечены [ДОПУЩЕНИЕ] ИЛИ источник не подтверждён
```

Пример:

```yaml
- name: BMW iX
  role: direct
  url: https://bmw.ae/iX
  region: ОАЭ
  positioning: "Электрический флагманский SUV — устойчивая роскошь"
  target_audience: "Состоятельные профессионалы 35–55, эко-сознательные, премиум-сегмент"
  price_range: "480–650 тыс. AED"
  key_messages:
    - устойчивость и роскошь без выбросов
    - производительность: 0–100 за 4,6 с
    - салон ручной работы, переработанные материалы
  visual_notes: "Чёрный фон, контурный свет, медленные пролёты камеры. Холодные тона."
  notes_for_us: "Давят на устойчивость. Отстраиваемся через family-first и запас хода."
  source: "https://bmw.ae/iX (собрано 2026-05-06)"
  confidence: high
```

### 3.3 `positioning.md`

Единый источник истины. Структура жёсткая, чтобы читать программно (brand-architect, content-writer):

```markdown
# Позиционирование: <Название>

## Core promise
<Одно предложение. Главное обещание покупателю.>

## Tone of voice
- <3–5 атрибутов: например, "уверенный, тёплый, экспертный, без хайпа">

## Угол 1: <название>
**Аргумент:** <почему это работает в нише>
**Доказательство:** <ссылки на конкурентную карту — какие gaps закрывает>
**Сообщения:**
- <конкретное сообщение для лендинга>
- <конкретное сообщение>

## Угол 2: <название>
<...то же что угол 1...>

## Чего избегать
- <что говорят все конкуренты — не повторяем>
- <что обещают, но провалится в этой нише>

## Ссылки
- Конкурентная карта: ./competitors.yaml
- Полный анализ: ./niche-analysis.md
```

Углов 1–2, не больше. Если три угла — значит позиционирование размыто, агент должен выбрать.

## 4. Алгоритм агента `niche-analyst`

### 4.1 Входы

- `00_БРИФ/brief.md` — обязательно
- `01_КОНТЕКСТ/context.md` — если есть (фактура от клиента про продукт)
- `02_МАТЕРИАЛЫ_КЛИЕНТА/` — если есть (отзывы, фото, могут содержать сигналы про ЦА)

### 4.2 Шаги

1. **Парсинг входов.** Извлечь: название бренда/продукта, категория, регион, язык брифа, целевой рынок.

2. **Определение языка и региона поиска.**
   - Язык запросов = язык брифа.
   - Регион = целевой рынок (Dubai → google.com + UAE-domain results; Россия → google.ru + Я.Карты).

3. **Классификация типа бренда.** Параллельные сигналы:
   - WebSearch: `"<brand>" wikipedia` → есть статья, на скольки языках?
   - WebSearch: `"<brand>" site:wikipedia.org` → подтверждение
   - WebSearch: `"<brand>"` (общий) → объём результатов (>100k = известный, <1k = локалка)
   - Brief mentions awareness percentage? Brand book?

   Решение:
   - Wikipedia ≥3 языков + brand book публичный → **Тип 1**
   - Wikipedia 1–2 языков ИЛИ >5k упоминаний → **Тип 2**
   - Иначе → **Тип 3**

4. **Сбор конкурентов** (зависит от типа):

   **Тип 1 (глобальный бренд):**
   - `manufacturer`: 1 (сам HQ)
   - `local_dealer`: 1–3 (другие дилеры в других регионах для тонального ориентира)
   - `direct`: 5 (главные конкуренты в категории, локальные к рынку)
   - `local_competitor`: 3 (что ещё на этом рынке)
   - `analog`: 2 (смежная категория)
   - `category_leader`: 1
   - `indirect`: 1

   **Тип 2 (региональный/нишевой):**
   - `manufacturer`: 1 если применимо
   - `direct`: 5
   - `local_competitor`: 5 (ключевая категория для этого типа)
   - `analog`: 2
   - `category_leader`: 1
   - `indirect`: 1–2

   **Тип 3 (локальный без бренда):**
   - `local_competitor`: 8–10 (ядро анализа — что в топ-10 поиска)
   - `category_leader`: 1 (общий бенчмарк доверия)
   - `indirect`: 2 (альтернативы решения проблемы)
   - `direct`: 2–3 (если различимы от local_competitor)

   Во всех типах суммарно **минимум 15 записей**. Если категория узкая (нет 5 direct), компенсируется большим количеством `local_competitor` или `analog`.

   Источники: WebSearch топ-выдачи + Firecrawl scrape сайтов конкурентов + Я.Карты/Google Maps для локалки.

5. **Скрейп каждого конкурента.** Через Firecrawl: получить homepage + about-страницу. Извлечь: positioning (h1/hero), key_messages (выделенные блоки), price_range (если на сайте), visual_notes (визуальный анализ через скриншот, опционально), target_audience (если упомянуто).

6. **Синтез позиционирования.**
   - Свести все `key_messages` конкурентов → найти повторяющиеся темы (что говорят ВСЕ — туда нельзя)
   - Найти gaps (что не покрыто никем) — кандидаты на угол отстройки
   - Свести с УТП клиента из брифа/контекста — выбрать 1–2 угла, которые: (а) подтверждены фактурой клиента, (б) не заняты конкурентами, (в) релевантны для ЦА

7. **Запись артефактов** в `01a_АНАЛИЗ_НИШИ/`.

### 4.3 Tools, которые использует агент

- `WebSearch` — поиск конкурентов, проверка узнаваемости
- `mcp__firecrawl__scrape` — извлечение контента сайтов конкурентов
- `Read` — чтение брифа и контекста
- `Write` — запись трёх артефактов

Не использует: Edit, Bash (кроме как для записи), любые ssh/scp.

### 4.4 Обработка нехватки данных

При любом из следующих:
- Конкурент не отвечает / 404
- Wikipedia не находит ничего
- Бриф упоминает регион, но не указывает страну
- Цена не на сайте

Агент **не блокируется**. Он:
- Заполняет поле как `[ДОПУЩЕНИЕ] ...` с пояснением
- Понижает `confidence: low` для записи
- В `niche-analysis.md` Section 7 фиксирует допущение

## 5. Контракты с другими этапами

### 5.1 Что читает `niche-analyst`

Только `00_БРИФ/brief.md` и (если есть) `01_КОНТЕКСТ/context.md`. Не читает мудборд, бренд-кит, дизайн.

### 5.2 Что читают другие агенты из `01a_АНАЛИЗ_НИШИ/`

| Агент | Этап | Что читает | Зачем |
|---|---|---|---|
| `references-curator` | 03 | `competitors.yaml` (visual_notes) | Не клонировать визуал лидеров, искать gaps |
| `moodboard-composer` | 03 | `niche-analysis.md` (Section 6) | Какой визуальный язык уместен |
| `brand-architect` | 04 | `positioning.md` (полностью) | Tone of voice, core promise |
| `content-writer` | 07 | `positioning.md` + `competitors.yaml` (key_messages) | Что писать, чего избегать |
| `seo-optimizer` | 12 | `competitors.yaml` (key_messages) | Семантика, ключевые слова |

Эти агенты получают новый обязательный шаг «прочитать positioning.md» в их инструкциях.

## 7. Acceptance criteria

- ✅ `/landing-niche` запускается в любом проекте, где `.landing-state.yaml` показывает 01_КОНТЕКСТ как approved
- ✅ Агент получает только бриф + контекст, не задаёт пользователю вопросов
- ✅ За один прогон создаются все 3 артефакта
- ✅ `competitors.yaml` валиден по схеме, минимум 15 записей, минимум 3 разных role
- ✅ `positioning.md` содержит ровно 1 или 2 угла, не больше
- ✅ `niche-analysis.md` помещается в 800 слов
- ✅ При нехватке данных по конкуренту запись имеет `confidence: low` и поле `[ДОПУЩЕНИЕ]`
- ✅ Если бриф на английском про локальный бизнес в Лагосе — агент гуглит на английском в google.com.ng, не классифицирует как глобальный бренд
- ✅ `gate-check.sh --stage 01a_niche_analysis` проходит после генерации артефактов
- ✅ Существующие проекты (lixiang-dubai) не падают из-за отсутствия папки `01a_АНАЛИЗ_НИШИ/`

## 8. Открытые вопросы (на ревью)

1. **Объединение в `client-assets-collector`?** Сейчас этот агент уже использует Firecrawl для отзывов с Я.Карт. Можно ли переиспользовать его инфраструктуру или нужен полностью отдельный агент? Решение: **отдельный агент** — у `client-assets-collector` другой scope (фото клиента, отзывы), смешивать ответственности плохо.

2. **Visual scrape конкурентов.** Делать скриншоты сайтов конкурентов в этом этапе или оставить moodboard-composer'у? Решение: **только текстовые `visual_notes` от агента**, скриншоты — moodboard-composer.

3. **Кеширование.** Если бриф изменился, нужно ли инвалидировать competitors.yaml? Решение: **полный пересчёт по `/landing-niche`**, без инкрементальных обновлений в MVP.

---

## 9. Out of scope (не в этом spec)

- Анализ цен (price intelligence) — отдельный этап если понадобится
- A/B тестирование позиционирования — это уже после деплоя, в `lifecycle-keeper`
- Автоматический выбор палитры по конкурентам — это `style-extractor`, не niche-analyst
- Отзывы с Я.Карт — остаётся в `client-assets-collector` (этап 02)
- Multilingual positioning (если у клиента несколько рынков) — отдельный этап `i18n` из BACKLOG B9
