## 1. Главное: как теперь делается лендинг

Раньше лендинг **собирался из готовых кубиков**: была библиотека из 200+ блоков,
система подбирала блок под каждую секцию, маркетолог выбирал вариант, блоки
склеивались встык. На реальных прогонах этот способ провалился по двум причинам:

1. **Терялся контент.** Промежуточный машинный разбор прототипа (`prototype.yaml`)
   молча выкидывал карточки и кнопки — между тем, что прислал клиент, и тем, что
   шло в вёрстку, стоял шаг, который искажал данные.
2. **Получалось плоско.** Склейка готовых блоков встык даёт «студенческую вёрстку».
   Премиальную глубину (наезжающие слои, вырезанные фото, крупные цифры, фигуры)
   из кубиков собрать нельзя. Поэтому агент всё равно стал **рисовать макет
   вручную** — в обход всей блочной машины.

**Новый способ — агент создаёт макет сам, по двум материалам клиента:**

```
  ПРОТОТИП клиента ───────┐
  (что и где на странице) │
                          ├──► агент РИСУЕТ макет (composed.html) ──► сборка в WordPress
  РЕФЕРЕНС клиента ───────┘    коллажем, с глубиной                  (тема, где клиент
  (как это должно выглядеть)                                          сам правит тексты)
```

Никакого подбора из библиотеки. Агент **создаёт** дизайн, а не **выбирает** блоки.

**Полная цепочка этапов:**

```
материалы клиента
  → прототип дословно (prototype.md)            [правда о структуре]      🔧 ПЕРЕДЕЛАТЬ
  → дизайн-система из референса (скриншот)       [правда о виде]           🔧 ПЕРЕДЕЛАТЬ
  → макет composed.html (рисует агент, коллаж)   [правда о готовом виде]   ⚠️ работает руками
  → сборка темы (макет → WordPress Lazy Blocks)  [редактируемый сайт]      ⚠️ работает руками
  → деплой на Beget                              [живой сайт]              🔧 ПЕРЕДЕЛАТЬ
```

Дальше — три зоны, где сейчас больше всего боли: **источник истины**, **декор/премиум**,
**сборка в WordPress**.

## 2. Источник истины: прототип, референс, готовый макет

Самое важное правило нового флоу: **у каждого вида информации — ровно один источник,
и их нельзя путать.**

### 2.1. Прототип — дословно, без потерь *(ПЕРЕДЕЛАТЬ, 🔧)*

Прототип клиента (PDF / DOCX / картинка / текст) превращается в **дословный
`prototype.md`** — это и есть правда о структуре и текстах. Каждый текст, каждая
кнопка, каждый комментарий клиента переносится 1:1.

**Что сейчас не так и надо поправить:**
- Машинный разбор в `prototype.yaml` **теряет данные** (карточки-каталоги
  схлопываются в одну, у кнопок пропадают поля). Поэтому: **`prototype.yaml`
  убираем из обязательного флоу.** Канон этапа — `prototype.md`. YAML — только если
  кто-то сделает его действительно без потерь.
- Скрипты разбора **падают на русском тексте под Windows** (нет указания кодировки
  utf-8) — починить во всех скриптах прототипа.
- Проверка «дошло ли ≥90% текста, не выдумано ли лишнее» сейчас работает **только
  для DOCX**. Для PDF/картинок она просто пропускается — то есть защиты нет.
  Распространить проверку на все форматы (для картинок/сканов — через распознавание
  текста, OCR).
- Комментарии клиента («тут карусель», «вот так я вижу блок») — это **намерение**,
  не текст для сайта. Они хранятся отдельно и переносятся как рекомендации, не в
  вёрстку.

*(`2026-06-03-block-system-consolidated-spec.md` — T6/T7/T8 — лоссивность; B27 — багфикс; T4/T5 — Windows/PDF-гейт)*

### 2.2. Откуда дизайн, откуда структура, откуда красота *(ПЕРЕДЕЛАТЬ, ⚠️)*

Когда агент создаёт макет, он берёт информацию из **трёх разных мест. Смешивать их —
главная ошибка, которую этот раздел запрещает.**

| Что берём | Откуда | Что именно |
|---|---|---|
| **Внешний вид** («чем рисуем») | из **референса** клиента (скриншот) | цвета, шрифты, стиль кнопок/тегов/полей, скругления, тени, отступы, характер, движение |
| **Структуру** («что где стоит») | из **прототипа** клиента, 1:1 | какие блоки, их порядок, что внутри блока, выравнивание, какие тексты и кнопки |
| **Красоту/глубину** («коллаж») | из **правил коллажа** (см. раздел 3) | блобы, наезжающие слои, вырезанные фото, крупные цифры — добавляются ПОВЕРХ структуры |

**Категорически нельзя:**
- брать **раскладку** у референса (порядок блоков, композицию hero, выравнивание),
  **если клиент не указал этого явно**. По умолчанию раскладка — только из прототипа.
  *(реальный провал: агент сам, без указания клиента, сделал hero как у Mercedes,
  хотя в прототипе клиента там была карусель машин.)*
- **выдумывать элементы**, которых нет в прототипе (лишние плашки, бейджи, блоки,
  кнопки). Это такая же ошибка, как выдумать текст. *(реальный провал: агент
  пририсовал плашку «5 brands», которой в прототипе не было.)*

**Исключение — клиент явно указал брать раскладку с референса.** Клиент может дать
референс **на конкретный блок** (скриншот) с пометкой, что именно из него берём:
- «бери отсюда **только дизайн-систему**» → берём вид, раскладку — из прототипа;
- «бери отсюда **расположение блоков**» (или «и то, и другое») → для этого блока
  раскладка берётся с референса, это законно.

То есть запрет — на **самовольное** копирование раскладки референса. Если клиент
прямо сказал, что хочет расположение как на скриншоте — это указание, выполняем.
По умолчанию (нет явного указания) — структура только из прототипа.

**Проверка перед сборкой:** агент поблочно сверяет свой макет с прототипом —
порядок, выравнивание, состав элементов (с поправкой на блоки, где клиент явно
разрешил раскладку с референса). Расхождение = дефект, чинить до деплоя.

*(подробности — в `2026-06-03-block-system-consolidated-spec.md`, журнал T13/T14)*

### 2.3. Референс — всегда скриншотом от клиента, не ссылкой *(ПЕРЕДЕЛАТЬ, 🔧)*

**Источник того, как сайт должен выглядеть, = скриншот и/или текстовое описание
ОТ КЛИЕНТА.** Ссылка на живой сайт — только подсказка, никогда единственный источник.

**Почему** (доказано на прогонах):
- Живой сайт часто **недоступен** агенту: защита от ботов (Mercedes за CloudFront —
  агент получил «403»), авторизация, гео-блок.
- Когда агент «читает» сайт ссылкой, он получает **только текстовый пересказ, без
  пикселей**, и это **врёт**: про Mercedes пересказ сказал «белый/без засечек/
  прямоугольные кнопки», а по реальному скриншоту — чёрный кинематографичный фон,
  шрифт с засечками, синие кнопки-пилюли. Дизайн, собранный по пересказу, оказался
  неверным и был переделан.

**Правила:**
1. На этапе сбора референсов у клиента **запрашиваются скриншоты** и/или текстовое
   описание желаемого стиля — это вход первого класса, наравне с прототипом.
2. Если дана только ссылка — агент пытается открыть, но при недоступности **обязан
   попросить у клиента скриншот**, а не «забить на референс» и не выдумать стиль.
   Молча пропустить референс — дефект.
3. **Палитра и шрифты снимаются с пикселей скриншота**, а не с текстового описания.
   Цвета замеряются по картинке (по пикселям), не «на глаз».

*(`2026-06-03-block-system-consolidated-spec.md` — T11/T12 — провал с Mercedes; B26 — правило)*

### 2.4. Готовый макет (composed.html) — единственная правда о виде *(ПЕРЕДЕЛАТЬ, ⚠️)*

`composed.html` — это **финальный визуал** (структура из прототипа, вид из референса,
премиум-глубина). Дальше — ключевое правило сборки:

> **Всё, что нужно для сборки сайта, выводится ИЗ `composed.html`, а не пишется
> заново руками «по памяти».**

Иначе сайт разойдётся с утверждённым макетом. Сейчас между «агент нарисовал макет»
и «сборка в WordPress» есть разрыв: сборка собирает тему из отдельных файлов
(описание дизайна + описание блоков), а **никто эти файлы из макета не порождает** —
их пишут вручную. Отсюда десятки ручных правок (раздел 4).

**Что надо:** шаг-конвертер, который из `composed.html` достаёт всё нужное для сборки
автоматически. Подробности — в разделе 4.1.

*(`2026-06-03-block-system-consolidated-spec.md` — T28 — правило «артефакты из composed»)*

### 2.5. Дизайн-системы (mood) — переключатель цветов *(ПЕРЕИСПОЛЬЗОВАТЬ, ♻️)*

Есть 6 готовых цветовых наборов (`_styles/`: brutalist, editorial-warm и т.д.). В
новом флоу они работают как **переключатель палитры**: дизайн-система проекта берётся
из референса клиента, а готовые наборы — это **альтернативные палитры**, которые
клиент может примерить.

**Как это работает (проверено на прогоне hibridcars):**
- Переключение меняет **только цвета** — шрифты и формы остаются (это осознанное
  решение: клиент примеряет цвет, не ломая макет).
- Работает это **только если 100% цветов идут через токены** (переменные). Любой
  цвет, вписанный напрямую, при переключении «протекает» старой палитрой. Это
  жёсткое требование — см. раздел 4.3.

**Панель доступна на ДВУХ этапах (один источник мудов):**
1. **В `composed.html` (превью, ДО деплоя)** — ОБЯЗАТЕЛЬНЫЙ элемент composed
   (premium-чеклист §12.5). Позволяет видеть разницу мудов до публикации;
   едет на тестовый сайт включённой для согласования с клиентом, перед продом
   выключается флагом `data-preview`.
2. **На задеплоенном сайте** — плагин `lp-preview-panel` (WP).
- **Единый источник мудов:** оба читают ОДНИ И ТЕ ЖЕ палитры (`palettes.css` /
  `palettes.yaml` проекта + системные `_styles/`). Превью и прод не должны разойтись.

**Состав мудов (множественность):** референсов у проекта может быть НЕСКОЛЬКО →
дизайн-систем тоже несколько (см. реестр `03_РЕФЕРЕНСЫ/references-index.md`: канон +
кандидаты). В панель идут: референсы проекта + 6 системных style-moods. Канон-муд
(флаг в references-index) = дефолт.

**Что выбросить:** в старой системе mood ошибочно прицепили ещё и к выбору на этапе
wireframe (вкладки настроения у каждого блока). Wireframe целиком уходит (раздел 6),
поэтому и эти вкладки — **ВЫБРОСИТЬ**. Остаётся только цветовой переключатель на
уровне темы/сайта.

*(`2026-06-03-block-system-consolidated-spec.md` — B9 — развести; T29/T30/T31 — токенизация)*

## 3. Декор и премиум: чтобы не было плоско

Главный риск нового флоу: когда агент рисует «с нуля», без библиотеки готовых блоков,
легко скатиться в плоскую вёрстку. Этот раздел — про то, что делает результат
премиальным.

> **Важно: премиальность ≠ тёмный фон.** Единственный старый эталон был тёмным, и
> это создало ложное правило «премиум обязан быть тёмным». На самом деле 4 из 5
> референсов клиента — **светлые**. Премиальность даёт **композиционная глубина**
> (слои, формы, вырезанные фото, крупные цифры), а не цвет фона. *(`2026-06-03-block-system-consolidated-spec.md` — B22)*

### 3.1. Декор агент генерирует сам *(СОЗДАТЬ + подсказка ПЕРЕИСПОЛЬЗОВАТЬ, 🔧)*

Как с блоками (отказались от готовой библиотеки), так и с декором: **агент рисует
каждую фигуру/блоб/волну сам**, под конкретный дизайн — через CSS (`border-radius`
для блобов) или inline SVG. Готового банка форм, из которого тянут как есть, **нет**.

- Папка `_shapes/` (18 фигур) **остаётся как подсказка-палитра** — «вот какие
  вообще бывают формы», чтобы агент не изобретал с нуля и держал единый язык. Но
  итоговую форму он **генерирует под проект**, а не вставляет файл как есть.
- **Что выбросить:** идею «хранилища разобранных референсов-эталонов» (общая папка
  с приёмами красивых сайтов) — **не делаем**. Агент работает только с референсом
  конкретного клиента + правилами коллажа из раздела 2.2.

**Правило плотности (универсальное):** не больше ~1 акцентного декор-объекта на
смысловую зону, иначе шумно.

> **Пример** (НЕ жёсткое правило, просто иллюстрация «контекст → роль»; конкретику
> агент решает под дизайн-систему и потребность места): hero с фото человека —
> форма-подложка под фото + крупные цифры; граница двух секций разного фона —
> форма-разделитель вместо прямой линии; блок с числами — полоса цифр-якорей;
> карточка — мелкая декор-форма в углу + иконка в плашке. Это не чек-лист «что
> ставить», а показ логики «декор отвечает потребности места».

*(подробности — в `2026-06-03-block-system-consolidated-spec.md`: B10 — было
«подключить _shapes», теперь генерировать; B24/B25 — хранилища, от которых отказались)*

### 3.2. Премиум-правила *(ПЕРЕДЕЛАТЬ, 🔧)*

Что отличает премиальный макет от «на коленке» (замерено на двух реальных результатах):

- **Никаких эмодзи в заголовках.** Эмодзи вместо иконок (🎯💰⚡ в `<h3>`) — главный
  маркер «собрано наспех». Только иконки (SVG) или картинки.
- **«Дышащая» типографика** — размеры шрифтов плавающие (`clamp()`), не фиксированные
  пиксели. Заголовки крупные.
- **Движение** — появление блоков при прокрутке, стекло на липкой шапке, лёгкие
  подъёмы карточек при наведении. Без движения страница «мёртвая».
- **Глубина** — фон-фото с наложениями-градиентами, свечения, вырезанные фото на
  цветных подложках, а не «сток в прямоугольнике».
- **Живой контент** — реальные фото в секциях, а не серые карточки с текстом.
- **Production-голова документа** — мета для соцсетей (OG/Twitter), favicon, цвет
  темы, подключение шрифтов.
- **Никаких порядковых цифр там, где это не последовательность шагов** — цифры
  01–04 у четырёх услуг читаются как «этапы», вводят в заблуждение. Якоря-цифры —
  только для реальных этапов/процесса.

Эти правила надо собрать в проверочный чек-лист, который не даёт закрыть макет, пока
они не выполнены.

*(`2026-06-03-block-system-consolidated-spec.md` — B21 — премиум-качество; T32 — цифры-якоря)*

### 3.3. Логотипы и иконки *(ОСТАВИТЬ, ✅ — флоу отработан)*

- **Логотипы брендов — это векторизация исходника, не генерация.** Логотип нельзя
  «нарисовать похожим» — это узнаваемый знак. Берём файл у клиента (PNG/JPG/SVG) и
  трассируем в SVG (`vtracer`). Генерацию картинок (codex) для логотипов **не
  использовать** — она даёт похожую выдумку. Codex — только для абстрактных
  иконок/инфографики без бренд-знаков.
- **Подключать логотип через inline SVG** с `currentColor` (цвет управляется
  дизайн-системой). Не через `mask-image` на локальный файл — он не виден при
  открытии файла напрямую.
- **Ровный оптический размер набора логотипов/иконок.** Когда несколько SVG стоят
  рядом, нельзя задавать им одинаковую высоту в пикселях — у них разная «масса
  чернил», и визуально они получаются разного размера. Размер нормируется по
  **площади закрашенных пикселей** (замер рендером), а не по высоте/ширине. Алгоритм
  с формулами — в старой спеке, шаг 9 правила SVG.
- **Favicon из логотипа.** Если логотип — широкая надпись, favicon делается из
  **монограммы** (первые буквы фирменным шрифтом и цветом), а не из сжатого логотипа
  (он нечитаем в 16px). Генерится через headless Chrome + обрезка, подключается
  ссылками в теме.

*(`2026-06-03-block-system-consolidated-spec.md` — T17/T18/T19 — логотипы; T42 — favicon)*

### 3.4. Рабочие правила добавления дизайн-элементов *(СОЗДАТЬ, 🔧 — из отдельного прогона)*

Развёрнутая инструкция, как именно агент добавляет любой визуальный элемент.
Дополняет разделы 2.2 (три источника) и 3.1 (генерация декора) до уровня
пошагового флоу. Это то, чем агент руководствуется при рисовании макета.

#### Базовый принцип

**Элемент добавляется под конкретную потребность места, а не «для красоты».**
Каждый дизайн-элемент отвечает на вопрос «какую проблему этого места он решает?»:

- блок плоский (текст без визуальной опоры) → иконка/цифра;
- в блоке зияет пустая зона → декор или визуал-объект;
- переход между секциями голый → разделитель;
- фото лежит «в боксе встык» → вырезать и дать глубину.

Если на вопрос «зачем здесь этот элемент» ответа нет — **элемент не нужен**.

**Плотность.** Не более ~1 акцентного декор-объекта на смысловую зону. Глаз должен
цепляться за один якорь в зоне, а не метаться. Перебор декора = «шумно», читается
как непрофессионально — хуже, чем пусто.

**Премиальность** даёт композиционная глубина (слои заходят друг на друга, фото
вырезано и выходит за рамку, крупные цифры-якоря, формы-подложки, разделители-формы).
Премиум **НЕ даёт**: тёмный фон сам по себе, обилие анимаций, много эффектов. Тёмная
тема — один из вариантов, не признак «дорого».

> Базовый принцип, плотность, дерево решений «откуда брать» и список запретов ниже —
> **универсальные правила**, применяются всегда. Каталог элементов и алгоритм по
> шагам — **справочная иллюстрация** (как обычно делается), не жёсткий чек-лист:
> конкретику агент решает под дизайн-систему и потребность места.

#### Каталог элементов *(справочно, не универсальное правило)*

> Это примеры — какие элементы бывают, как обычно делаются и куда ставятся. Не
> «список обязательного». Универсальное здесь — только колонка «Запрет».

| Элемент | Как делается | Куда ставится | Запрет |
|---|---|---|---|
| **Иконка** | inline-SVG под стиль системы (толщина обводки/угловатость — из характера) либо готовый набор (Lucide); `currentColor`=токен; в плашке или с единым оптическим размером | плоские блоки с одним текстом — списки преимуществ, сегменты ЦА, отделы, пункты программы, регалии (главный «оживитель») | эмодзи вместо иконок |
| **Цифра-якорь** | display-шрифт, очень крупно, акцентный цвет; floating-бейдж поверх фото или полоса-якорь | только реальные числа из контента (проценты, годы, количество, цены, сроки); нет чисел — взять из оффера | порядковые 01–04 у списка услуг (читаются как «этапы»); «водяная» цифра-призрак за текстом «для объёма» |

| **Подчёркивание-росчерк** | inline-SVG `<path>` со `stroke`, чуть неровный (Безье), `currentColor` | под **1** ключевым словом в заголовке секции | не под каждым словом |
| **Форма-кромка / разделитель** | трассировка из референса (vtracer) либо CSS/SVG-путь; `currentColor`; переиспользовать через `<symbol>`/`<use>` | между секциями разного фона (см. §«Разделители» ниже) | — |
| **Форма-подложка** (блоб, овал, «сцена») | CSS `border-radius` (неровные значения = блоб) или SVG | под вырезанным фото человека (hero, портрет); под иконкой в карточке (мелкая, в углу) | — |
| **Фото человека / бренд-объект** | реальный файл клиента → вырезка фона (rembg) → PNG/прозрачность → на форму-подложку; если фон уже прозрачный — как есть (часто чище авто-вырезки) | hero (вырезанное, с наездом за край); блок-портрет (на подложке со свечением) | **лицо не генерировать** — узнаваемый знак |
| **Логотип бренда** | векторизация исходника (vtracer; готовый SVG — как есть); нормализовать (viewBox, убрать width/height, `fill=currentColor`); inline-`<svg>` | где нужен узнаваемый знак; несколько рядом — нормировать по площади чернил, не по высоте px | **не генерировать**; не `mask-image` на локальный файл |
| **Абстрактный визуал** (маскот, инфографика, объект без бренда) | генерация на сплошном хромакее (magenta `#FF00FF`, объект не касается краёв) → rembg → вставка под палитру; при нужде — оверлей акцента | крупные пустые зоны под характерный объект (маскот-робот, инфографика-чарт) | только без бренд-знаков и без реальных лиц |

#### Алгоритм добавления элемента *(справочно — обычный порядок работы)*

1. **Анализ блока** — посмотреть на блок глазами (рендер-скриншот). Найти: где
   пусто, где плоско (текст без опоры), где голый переход, где фото «в боксе».
2. **Определить потребность** словами: «здесь не хватает иконок у пунктов» / «правая
   зона пустая» / «переход не оформлен».
3. **Подобрать элемент** по каталогу выше под эту потребность.
4. **Выбрать источник** по дереву решений ниже (рисую / трассирую / генерирую /
   реальный файл).
5. **Согласовать с пользователем** — для заметного декора показать «блок → место →
   элемент» до создания. Мелкие иконки в плашках обычно без согласования; крупный
   декор/визуал — требует.
6. **Создать.** `currentColor`=токен. Выровнять по границам контента (фото/текста),
   а не «на глаз».
7. **Проверить рендером** — скриншот, посмотреть: не сливается ли с фоном, не на
   лице/тексте ли, не перекрывает ли читаемое, не торчит ли невыровненно.
8. **Сверить.** Токенизация чистая (0 прямых цветов); раскладка прототипа цела; нет
   эмодзи в заголовках; шрифты `clamp()`; декор не добавил структуры, которой нет в
   прототипе.

#### Дерево решений «откуда брать форму/картинку»

```
Нужен визуальный элемент
│
├─ Это ТЕКСТ или структурный элемент?
│     → из прототипа 1:1. Не трогаем, не выдумываем.
│
├─ Это ЛИЦО человека или БРЕНД-ЗНАК (логотип)?
│     → РЕАЛЬНЫЙ файл клиента.
│        фото → rembg-вырезка;  логотип → vtracer-векторизация.
│        ❌ НЕ генерировать (выйдет похожая выдумка).
│
├─ Это КОНКРЕТНАЯ форма, которая есть в референсе (край краски, волна)?
│     → ТРАССИРОВАТЬ из картинки (vtracer) → нормализовать → currentColor.
│        ❌ Не «рисовать похоже на глаз» — обводим источник.
│
├─ Это АБСТРАКТНЫЙ объект без бренда/лица (маскот, инфографика)?
│     → ГЕНЕРИРОВАТЬ на хромакее → rembg → вставка под палитру.
│
├─ Это ИКОНКА?
│     → inline-SVG под стиль системы, либо готовый набор. currentColor.
│
└─ Это ДЕКОР-ФИГУРА (блоб, росчерк, звезда, подчёркивание)?
      → CSS border-radius / inline-SVG. currentColor.
```

**Ключ дерева:** точную/узнаваемую вещь берут из источника (реальный файл или
трассировка), не выдумывают. Генерация — только для абстрактного без брендов и лиц.

#### Разделители между блоками

**Главное правило — ЕДИНООБРАЗИЕ.** Разделители на всех стыках проекта должны
говорить на одном языке. Допустимы два подхода, но в рамках одного проекта —
**только один из них на всех блоках**, не вперемешку:

- **(А) Переход между соседними блоками** — кромка в цвете одной из двух соседних
  секций, она «перетекает» в другую. Контраст получается тонкий и спокойный.
- **(Б) Яркий разделитель-элемент** — заметная форма/цвет как самостоятельный
  акцент. **Яркие разделители разрешены** — но тогда они **на всех стыках
  единообразны** (одна форма, один приём), а не «здесь яркий, там никакой».

Что выбрать (А или Б) — решает дизайн-система/референс проекта. Нельзя смешивать:
на одном стыке тонкий переход, на другом — внезапная яркая полоса, на третьем —
голый стык. Это читается как несогласованность.

- **Форма разделителя — одна на весь проект**, переиспользуется (`<symbol>`/`<use>`),
  чтобы стыки читались как единый язык.
- **Все переходы между секциями должны быть оформлены** одним выбранным способом —
  голый стык фонов встык читается как «недоделано».

> *Откуда это правило:* изначально оно выводилось из конкретного референса (где
> разделители были переходами цвета). В общем виде — важен не конкретный приём
> (переход или яркий элемент), а его **единообразие** по всему проекту.
> *(`2026-06-03-block-system-consolidated-spec.md`)*

#### Запреты (универсальные)

| Запрет | Почему |
|---|---|
| Карточки-коробки посреди секции, когда остальные блоки полноширинные | выбиваются из ритма; единый формат блоков |
| Эмодзи в заголовках | главный маркер «наспех»; только иконки |
| Водяные цифры-призраки «для объёма» | читаются как случайное пятно; ставить реальный визуал |
| Невыровненный декор (висящие края, элементы «мимо» контента) | выглядит как ошибка; выровнять по границам или убрать |
| Генерация лица или логотипа | узнаваемый знак нельзя выдумывать — только реальный файл |
| Прямые цвета вне токенов | ломают переключатель палитры, «протекают» |
| Фиксированные px у шрифтов | не «дышит»; только `clamp()` |
| Декор, меняющий раскладку прототипа или добавляющий структуру | галлюцинация структуры, как выдуманный текст |
| Раскладку/композицию брать у референса | раскладка только из прототипа; у референса — лишь вид |

> **Токенизация (повтор для контекста этого раздела):** ни одного прямого цвета вне
> определения токенов в `:root`. Декор красится `currentColor` (наследует токен).
> Исключение — только мета-тег `theme-color` (там переменные не работают). Подробно —
> раздел 4.3.

## 4. Сборка в WordPress: чтобы клиент сам правил тексты

Требование: клиент должен **сам править тексты и фото** в админке WordPress. Значит
макет превращается в **набор редактируемых блоков** (Lazy Blocks), а не в цельный
неизменяемый HTML.

**Хорошая новость:** коллаж и редактируемость **совместимы**. Сложная вёрстка
(наезды, абсолютное позиционирование, блобы) не мешает правке полей, если **декор
отделён от контента**: декор — отдельные слои-подложки (не кликаются, лежат ниже),
а редактируемые тексты — в чистом слое поверх. Это уже подтверждено. *(ОСТАВИТЬ, ✅)*

**Плохая новость:** реальный прогон (макет → сборка → деплой → живой WordPress)
сработал 1:1, но потребовал **~16 ручных правок**. Ниже — что автоматизировать.

### 4.1. Превращение макета в тему — сейчас вручную *(СОЗДАТЬ, ❌)*

Сборка **не конвертирует** готовый макет напрямую — она **заново собирает** тему из
отдельных файлов (описание дизайна + описание блоков + список шрифтов/зависимостей).
Проблема: эти файлы сейчас **никто не порождает из макета** — их пишут руками, и они
расходятся с макетом.

**Что надо создать:** шаг-конвертер `composed.html → файлы для сборки`:
- из стилей макета → файл с дизайн-токенами и CSS;
- из секций макета → описание блоков (каждая секция → блок с полями для текстов;
  повторяющиеся элементы — карточки/шаги/тарифы — как список);
- из «головы» макета → список шрифтов и зависимостей;
- фото из макета → в папку темы.

Пока конвертера нет — собирать строго по макету (не по прототипу, не по памяти),
сверяя автоматической проверкой соответствия.

*(`2026-06-03-block-system-consolidated-spec.md` — T28; B23)*

### 4.2. 16 болячек сборки *(ПЕРЕДЕЛАТЬ, ⚠️ — воспроизведены на реальном прогоне)*

Каждая воспроизведена с доказательством и временным ручным фиксом. Это точный план
доработки сборщика. Приоритет — те, что ломают вёрстку «на ровном месте».

| Болячка | В чём | Что чинить в сборщике |
|---|---|---|
| Контент дублируется | каждое поле выводится дважды | не дописывать поля, если вёрстка блока их уже содержит |
| Карточки не рендерятся | внутренние блоки-карточки теряются | вставлять внутренние блоки внутрь вёрстки, не терять |
| Картинки битые | поле картинки отдаёт имя файла, не объект | обрабатывать имя файла как путь в теме |
| Плейсхолдеры фото не заменились | не совпали имена файла и вложения | починить сопоставление имён |
| Масштаб поехал (всё сжато) | обёртки блоков без правил ширины ломают сетку | CSS-правки должны покрывать и верхние обёртки |
| Нет навигации | шапка была вне блоков, сборка её не перенесла | переносить элементы уровня страницы (шапку) в шаблон темы |
| Интерактив не работает | классы движения макета ≠ классам темы | согласовать классы движения |
| Дефолты WordPress ломают кнопки | стандартные стили WP перебивают наши | тема должна отключать дефолты WP |
| Hero выше экрана | при переносе CSS добавлен лишний `min-height` | переносить CSS точно, без «улучшений» |
| Сложные блоки упрощены | таймлайны/таблицы/росчерки не перенеслись | сборщик не умеет в интерактив — нужен шаблон |
| Ошибка в YAML | многострочные вставки ломаются отступами | проверять/нормализовать многострочные блоки |
| SSH-ключ без кавычек | ключ с пробелами в настройках | кавычки на ключ в шаблоне настроек |
| Падает редактор WordPress | функция в коде блока объявляется повторно | оборачивать или выносить функции |
| `<script>` в блоке ломает редактор | скрипт попадает в превью редактора | скрипты — только в файлы темы, не в блок |
| Превью блоков «не JSON» | деплой не создал `.htaccess` → REST не работает | деплой должен создавать `.htaccess` и обновлять правила |
| Фото растягивает формы | размеры от WordPress перебивают CSS-геометрию | наша CSS-геометрия (размер/форма) приоритетнее размеров от WP |

**Общее правило из этого:** **наш CSS — источник истины вида элемента, а не
размеры/стили, которые навешивает WordPress.** Геометрию (размер, пропорции, форму)
задавать с защитой от перебивания.

*(`2026-06-03-block-system-consolidated-spec.md` — B23, часть III-quinquies — полная таблица с доказательствами)*

### 4.3. Все цвета через токены *(ПЕРЕДЕЛАТЬ, 🔧)*

Чтобы переключатель палитры (раздел 2.5) работал, **в CSS лендинга не должно быть ни
одного цвета, вписанного напрямую** — все через переменные-токены. Любой прямой цвет
при смене палитры «протекает» старым.

- Это касается всего: фонов, тёмных секций, полупрозрачных акцентов (свечения, теги,
  галочки), декора. Даже «технические» заливки (белый фон под цифрой) — через токен.
- **Контраст «подложка ↔ то, что сверху».** Мало просто «через токен»: если элемент
  берёт глобальный акцент, а подложка случайно близка к нему — сливается. Цвет
  текста/иконки выбирается **относительно своей подложки** (тёмная подложка →
  светлый текст, и наоборот).
- **Тёмные палитры** требуют отдельного токена «текст на акцентной кнопке»: на
  светлом акценте белый текст работает, на светлой бронзе — нет (нужен тёмный).
- **Токенизировать надо и макет, и тему синхронно** — иначе при пересборке из макета
  «протечки» вернутся.
- Исключения (можно прямой цвет): фирменные иконки мессенджеров (WhatsApp,
  Telegram), зелёная точка «онлайн».
- **Проверка:** поиск по CSS прямых цветов вне токенов → ошибка сборки.

*(`2026-06-03-block-system-consolidated-spec.md` — T29/T30/T31)*

### 4.5. Редактируемость — фундамент уже есть *(ОСТАВИТЬ, ✅)*

Превращение `{{slot:name}}` в редактируемое поле админки уже работает: слот →

## 5. Картинки: генерация и подгонка под дизайн *(ПЕРЕДЕЛАТЬ, ⚠️ — пилот пройден)*

Не «подобрать сток-фото», а для **каждого визуального места** на странице:
проанализировать (что вокруг, какая цель) → сгенерировать → вырезать фон → вставить
под дизайн-систему.

**Шаги:**
1. **Анализ места** — что вокруг (заголовок, тексты, кнопка).
2. **Цель картинки** — выводится из контекста (карточка бренда + кнопка «смотреть
   модели» = показать **весь модельный ряд**, не одну машину).
3. **Спецификация** — размер, пропорции, формат, текст запроса на генерацию.
4. **Референсы для генерации** — **число референсов = составу композиции**: нужно
   5 разных машин — даём 5 фото-референсов (с одним получаются клоны).
5. **Генерация** — на фоне, который **легко вырезать** (чистый студийный градиент,
   объект не касается краёв, мягкая тень не до края).
6. **Вырезание фона** — `rembg` → PNG с прозрачностью.
7. **Вставка** — PNG на CSS-фон дизайн-системы (подходит под любую палитру).

**Адаптация фото под палитру** — не делать отдельную картинку под каждый цвет, а
накладывать **полупрозрачный оверлей акцентного цвета** (он сам перекрашивается под
палитру). Одно фото на все дизайн-системы.

> **Культурный анализ региона** (числа/цвета/символы/табы региона) — **отложен,
> добавим позже.** Пока этого шага в флоу нет.

*(подробности — в `2026-06-03-block-system-consolidated-spec.md`, часть VII,
T20/T21/T22)*

## 7. Список задач

Сгруппирован по трём зонам боли. Внутри — по убыванию важности.

### Зона A — Источник истины и раскладка
- A1. Сделать `prototype.md` каноном этапа прототипа; убрать обязательный
  `prototype.yaml`; починить кодировку и проверку покрытия на всех форматах.
- A2. Зафиксировать в инструкциях агента правило трёх источников (вид/структура/

- A3. Сбор референса = скриншот/описание от клиента; палитра замеряется по пикселям;

- A4. Зафиксировать `composed.html` как единственную правду о виде, из которой
  выводится сборка.

### Зона B — Декор и премиум
- B1. Научить агента генерировать декор сам (формы под проект); `_shapes/` оставить
  подсказкой; убрать из системы идею хранилища эталонов.

  «дорого ≠ тёмное», цифры-якоря только для шагов) + проверку, что не даёт закрыть
  макет без них.
- B3. Зафиксировать как готовое: логотипы — векторизация исходника, ровный
  оптический размер, favicon из монограммы.
