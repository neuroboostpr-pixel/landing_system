# Phase 2 — Token Hotspots & Алгоритмические Петли

**Дата:** 2026-05-23
**Скоуп:** активные скиллы, агенты, команды + HTTP/AI/DB вызовы в скриптах и mu-plugin
**Инструмент:** code-reviewer skill (read-only)

## Executive Summary (для руководства)

Главная находка: **27 из 32 агентов проекта содержат слова «retry», «again», «попробуй ещё», «auto-fix»**, но **ни одного упоминания ограничителя** (`max_attempts`, `max_retries`, «не более N раз»). Если оркестратор уходит в петлю «попробовать-упало-попробовать ещё раз» — он будет крутиться пока пользователь не остановит. Один такой случай может съесть бюджет дня.

Вторая важная находка: **wiki/ построена как навигационный граф (472 концепта с `[[wikilinks]]`), но ни один агент не инструктирован по нему ходить**. Замысел очевиден: оркестратор должен начинать с `wiki/index.md`, переходить по ссылкам к нужным концептам и читать **короткие** wiki-версии вместо тяжёлых исходников. Граф готов, **«нога» не подключена**. Сам `landing-orchestrator` напрямую ходит по исходникам. Wiki пишется (через git-hook компиляции, через `--write-wiki`), но не читается на pipeline. Это **главный архитектурный gap проекта**: инфраструктура построена, продукт не запущен.

Третья: распределение размеров промптов нормальное (медиана 47 строк, p90=102, p99=317), есть **7 outlier'ов** превышающих медиану в 3 раза. Они — кандидаты на вынесение части в `references/X.md` (lazy-load для экономии токенов при invocation).

По heavy operations (платные внешние вызовы): HTTP-вызовы есть только в SEO-аудите (с timeout — норма) и в шрифт-загрузчике. AI-вызовы (codex/image_gen) есть, кэш реализован в `visual-generation` (есть `visual-cache.py`). Главный риск — отсутствие `max_attempts` в auto-fix loop оркестратора (см. выше).

**Всё — на согласование. Никаких действий не выполнено.**

## 🔴 Критичные

### #1 🔴 КРИТИЧНО — Auto-fix loop в `/landing-go` не ограничен числом попыток

**Что это значит простыми словами:**
Главная команда `/landing-go` поддерживает автоматическое исправление ошибок: если на этапе упал verify-скрипт — оркестратор предлагает запустить fix-команду из конфига и продолжить. Но в коде команды нет ограничения «не более N попыток». Если фикс ломает что-то ещё, или verify-скрипт всегда возвращает ошибку — оркестратор будет крутиться в цикле fix→verify→fix→verify бесконечно. Один такой запуск может съесть бюджет дня.

**Чем грозит бизнесу:**
- Расход денег на токены без понятного предела (Claude API считает по токенам).
- Расход времени маркетолога — он ждёт результат, который не приходит.
- Маркетолог думает «зависло», прерывает работу, теряет контекст.
- Если фикс ломает данные клиента — каждый цикл усугубляет проблему.

**Оценка срочности (мнение ревьюера, на согласование):** стоит решить до сдачи клиенту. Не блокирует разработку, но риск инцидента в проде высокий.

**Статус решения:** ☐ на согласовании

---

**Технические детали:**

- Файл: `.claude/commands/landing-go.md`
- Строка 17: `--auto-fix yes` — применять авто-фиксы без подтверждения.
- Строка 50: «Если гейт упал — предлагает auto-fix (auto-resume после исправления).»
- Строки 71-74: секция «Auto-fix mechanism», описывает что при `auto_fix:` префиксе в фикс-инструкции — команда запускается. Никакого `max_attempts` рядом нет.
- Проверено: `grep -i 'max_attempts\|max_retries\|attempt < \|attempt <=\|не более'` по `agents/` — 0 матчей.
- Проверено: то же по `.claude/commands/landing-go.md` — 0 матчей.
- Возможные пути решения (на согласование):
  - добавить в `.claude/commands/landing-go.md` явный ограничитель `--max-fix-attempts 3` с default=3;
  - на 3-й fail подряд — выйти с сообщением «гейт не закрывается, требуется ручной разбор», вернуть управление пользователю;
  - писать в `.landing-state.yaml` счётчик попыток для текущего этапа, чтобы re-run не сбрасывал счётчик.

## 🟠 Важные

### #2 🟠 ВАЖНО — 27 агентов содержат retry-логику без явного ограничителя

**Что это значит простыми словами:**
В описаниях 27 из 32 агентов встречаются слова «retry», «again», «попробуй ещё», «auto-fix» — то есть агент инструктирован пробовать снова при неудаче. Но ни в одном из этих 27 агентов нет явного лимита «не более N попыток». В теории каждый агент может попасть в локальный цикл — но без числа попыток модель ориентируется по своему усмотрению, и это непредсказуемо.

**Чем грозит бизнесу:**
- Каждый агент с retry — потенциальный источник «зависания» (хотя на практике LLM обычно сам останавливается через 2-3 попытки).
- Невозможно сделать обоснованную оценку «сколько токенов потратит pipeline в худшем случае».
- Тесты на retry-поведение в `tests/` отсутствуют (это отдельно проверит фаза 5).

**Оценка срочности (мнение ревьюера, на согласование):** не блокирует, но стоит ввести **общий стандарт** в `docs/standards/stage-execution-protocol.md` — «при retry агент обязан указать счётчик попыток в TodoWrite и остановиться на 3-й попытке». Не править каждый агент — только стандарт, на который они ссылаются.

**Статус решения:** ☐ на согласовании

- 3 команды с retry: `landing-audit`, `landing-go`, `landing-qa`.
- Полный список Grep'а — см. evidence appendix.
- Возможные пути решения:
  - добавить раздел «Retry policy» в `docs/standards/stage-execution-protocol.md` с обязательным max 3 попытки;
  - в каждом агенте сослаться на стандарт (одной строкой);
  - не вводить per-agent счётчики — это раздувает промпт.

### #3 🟠 ВАЖНО — wiki/ построена как навигационный граф, но ни один агент не инструктирован по нему ходить

**Что это значит простыми словами:**
В проекте есть огромная wiki/ — 480 файлов, **472 концепта** связанных навигационными ссылками `[[wikilinks]]` (как Obsidian/Roam). Замысел очевиден из `wiki/index.md`: оркестратор должен начинать с индекса, переходить по `[[wikilink]]` к нужному этапу/агенту/скиллу, читать **короткое** описание из wiki вместо тяжёлого исходника, и так экономить токены.

**Реальность:** граф построен, но «нога» к нему не подключена. Ни в одном агенте — включая `landing-orchestrator` — **нет инструкции «начни с `wiki/index.md`»** или «прежде чем читать `agents/X.md`, прочитай `wiki/X.md` (она короче)». Сам `landing-orchestrator` оркестрирует напрямую через `.landing-state.yaml` + `stage-gates.yaml` + Read оригинальных источников. Wiki **пишется** (через `--write-wiki` в orchestrator, через git-hook компиляции), но **не читается** на pipeline.

**Чем грозит бизнесу:**
- Граф готов, **навигатор отсутствует**. Спроектированная экономия токенов не реализуется.
- Усилия на wiki-compiler + hash-cache + git-hook — окупаются только тем что wiki «есть на полке».
- При каждом коммите тратится время на пересборку wiki, которой никто не пользуется в runtime.
- Если разработчик будет читать wiki вручную для понимания системы — это даст ценность; но это не основная декларированная цель.

**Оценка срочности (мнение ревьюера, на согласование):** не блокирует, но это **главный архитектурный gap**: инфраструктура построена, продукт не запущен. Стоит решить в близкое время — либо подключить wiki-навигацию к агентам (для этого нужно правило в `docs/standards/stage-execution-protocol.md` и упоминание в каждом stage-агенте), либо признать что wiki — это reference-материал для человека, а не для агента, и переосмыслить scope (меньше файлов / меньше компиляции).

**Статус решения:** ☐ на согласовании

---

- Концептов в `wiki/index.md`: **472**, организованы по категориям (agent / block / command / rule / script / skill / stage / unknown).
- Формат навигации: `[[concept-slug]]` — wikilinks между концептами (проверено в `wiki/index.md`).

  - **сократить wiki:** оставить только те концепты, которые реально нужны человеку (документация), убрать авто-генерацию для всех 472 концептов.

### #4 🟡 СТОИТ ВНИМАНИЯ — 7 outlier'ов промптов, превышающих медиану в 3+ раза

**Что это значит простыми словами:**
В проекте 92 файла-промпта (скиллы / агенты / команды). Их размеры распределены так: половина короче 47 строк, четверть длиннее 73, только 10% длиннее 102. Семь файлов превышают медиану в 3+ раза — это outlier'ы. Каждый раз когда LLM грузит такой файл в контекст, тратится больше токенов, чем на «обычный» файл проекта. Часть из этих файлов можно разнести на основной (короткий) + подгружаемые `references/X.md`, чтобы экономить токены когда детали не нужны.

**Чем грозит бизнесу:**
- Каждый запуск оркестратора, который грузит эти агенты — дороже базового.
- При длинных сессиях кеш не успевает спасать (TTL 5 минут).
- Длинные промпты ухудшают instruction-following — модель чаще «забывает» начало.

**Оценка срочности (мнение ревьюера, на согласование):** не блокирует, но при росте проекта проблема будет накапливаться.

**Статус решения:** ☐ на согласовании

## Глоссарий

- *перцентиль (pN)* — отметка, ниже которой остаются N% значений. Например p90=102 означает: 90% файлов короче 102 строк, и только 10% длиннее.
- *outlier* — экстремальное значение, далеко выпадающее из общего распределения. Здесь — файл длиннее 3× медианы.
- *retry* — повтор попытки после неудачи. *Retry без max_attempts* — потенциальный бесконечный цикл.
- *auto-fix* — автоматическое применение фикса при провале verify-проверки.
- *prompt cache* — кэш Claude API на 5 минут; повторное чтение того же контента в окне 5 минут оплачивается со скидкой.
- *wiki-utilization* — доля wiki-страниц, которые реально читаются в pipeline (vs. компилируются и лежат «на полке»).
- *N+1 query* — паттерн когда в loop'е делается отдельный SQL-запрос для каждой записи (вместо одного агрегирующего).
