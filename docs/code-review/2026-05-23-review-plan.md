# Code Review Playbook — landing-system

**Дата:** 2026-05-23
**Скоуп:** полный репозиторий, по фазам
**Инструмент:** skill `code-reviewer` (read-only: Read, Grep, Glob) + где требуется `/security-review`

---

## Зачем это ревью (для руководства)

Проект `landing-system` вырос быстро: десятки скиллов, агентов и команд,
mu-plugin для WP-админки с множеством файлов, REST endpoint для приёма заявок
от клиентов, несколько интеграций с CRM, multisite на Бегете. По мере роста
накопились типичные проблемы:

- **Мёртвый код** — файлы, которые когда-то писали, но больше нигде не вызывают. Каждый такой файл оркестратор всё равно «видит» и тратит на него токены. Сколько таких — предстоит выяснить ревью; никаких априорных оценок не делаем.
- **Сломанные кнопки в админке** — маркетолог жмёт, ничего не происходит, или открывается «страница не найдена».
- **Дыры в безопасности** — WP-админка с интеграциями CRM и базой заявок клиентов — главная мишень. Если не закрыть — украдут лиды, получим штраф Роскомнадзора (152-ФЗ), потеряем доверие клиента.
- **Дыры в флоу** — оркестратор может пропускать шаги, заходить в циклы, тратить токены на повторную работу.

**На выходе ревью** — 7 отчётов на русском (по фазам) + сводный SUMMARY для руководства + папка `technical-appendix/` с патчами для разработчика.

**Что получим на выходе (отчёты, не действия):**

1. Список файлов с пометкой «нигде не используется» — на согласование, что с ними делать.
2. Перечень всех найденных дыр безопасности с описанием риска.
3. Карта реального флоу оркестратора с указанием мест где он может «сломаться».
4. Список мест с раздутыми промптами и потенциальными циклами без ограничения.
5. Список сломанных кнопок/ссылок в WP-админке.

**Важно:** Ревью **только репортит**. Никаких готовых действий, удалений, переименований, слияний. Любая правка происходит **только после согласования** с пользователем по конкретному пункту отчёта.

## Bilingual Reporting Standard (обязательно для всех фаз)

### Принципы

1. **Все отчёты пишутся на русском.** Технические термины (XSS, SQL injection, nonce, capability, `wp_ajax`) сохраняем как есть, но **с пояснением в скобках при первом упоминании в документе**.

2. **Каждое issue имеет 2 уровня описания:**

   **Уровень 1 — для руководителя (3-5 строк):**
   - Что сломано (бытовым языком).
   - Чем грозит бизнесу: данные клиентов, работа маркетолога, штраф, лишние расходы.
   - Срочность: блокирует / надо до запуска / можно потом.

   **Уровень 2 — для разработчика:**
   - `file.php:42` — конкретное место.
   - Что не так в коде (одна-две строки / patch suggestion).
   - Как воспроизвести.
   - Как починить (конкретно).

3. **Severity по русской шкале (оценка ревьюера, не приказ к действию):**
   - 🔴 **КРИТИЧНО** — блокирует запуск, риск утечки данных или штрафа.
   - 🟠 **ВАЖНО** — мешает работе маркетолога, есть способ обойти, но больно.
   - 🟡 **СТОИТ ВНИМАНИЯ** — работает, но плохо: глюки, неудобства, потенциальные баги.
   - 🟢 **К СВЕДЕНИЮ** — best practice / стилистическое замечание.

   Severity — это **оценка серьёзности проблемы**, а не указание что делать. Решение «фиксить / отложить / игнорировать» принимает пользователь по каждому пункту отдельно.

4. **Глоссарий в конце каждого отчёта** — короткий блок «термины» с переводом упомянутых понятий.

5. **Executive Summary в начале каждого отчёта** — 5-10 строк на русском **без единого технического термина**. Образец: «В админке нашли N сломанных кнопок, M потенциальных дыр в безопасности, K файлов без видимых вызовов. Самое серьёзное — пункт №3 (через эту дыру теоретически можно украсть базу заявок). Полный список — ниже, решения по каждому пункту — за пользователем.»

6. **Никаких априорных чисел в инструкциях ревьюеру и в шаблонах отчётов.**
   - Не указываем «должно быть N скиллов», «пайплайн из 13 этапов», «46 deep-links», «6 CRM-адаптеров» — это **anchoring bias**, модель подгонит результат под цифру или поленится найти все.
   - Все количественные данные получаются **по факту** через Glob/Grep/чтение кода.
   - В шаблонах отчётов используем `<по факту>`, `<число>`, `N`, `M` как плейсхолдеры — но не образцовые значения.
   - Исключение: цитирование известных стандартов (OWASP A03, 152-ФЗ ст. 9) — это идентификаторы, не якоря.

7. **Никаких именных якорей.**
   - Не указываем «проверить скилл X», «агент Y подозрительный», «команда Z может быть лишней» — это **selection bias**, ревьюер посмотрит только эти файлы внимательно, остальные пройдёт по диагонали.
   - Указываем **паттерны**: «все файлы с префиксом `_`», «все агенты с глаголами retry/loop в описании», «все кластеры команд с общим префиксом», «все пары имён, потенциально путающие пользователя».
   - Имя конкретного файла или ID в playbook'е упоминается только если это **архитектурный entry-point**, без которого ревьюер не сможет начать чтение (например главная команда оркестратора `landing-orchestrator` или `/landing-go` — без них непонятно откуда стартует pipeline). PR-ID, версии фич, конкретные stage-ID — **не упоминаются**: ревьюер обязан найти их сам через Grep по документации, чтобы не пропустить тех, которые я не заметил.
   - Различие: «entry-point упоминается, чтобы ревьюер знал откуда начать чтение флоу» ≠ «файл упоминается как подозрительный, чтобы ревьюер искал в нём проблемы».

8. **Никаких произвольных лимитов на размер списков.**
   - Запрещены формулировки «топ-N», «первые N», «top issues», «head_limit», «самые важные K».
   - Все списки выгружаются **полностью**: все orphan-файлы, все findings, все референсы. Если список длинный — это сам по себе сигнал, его нельзя скрывать обрезкой.
   - Сортировка — пожалуйста (по severity, по числу ссылок, по алфавиту). Обрезка — нет.
   - Исключение: внутри одного finding'а блок «Воспроизведение» / «Возможный путь решения» может быть кратким — но это не лимит на количество, это краткость одного описания.

9. **Никаких готовых действий в отчёте.** Запрещены формулировки:
   - ❌ «Удалить файл X» → ✅ «Файл X не имеет входящих ссылок — кандидат к удалению при согласовании»
   - ❌ «Заменить алгоритм на Y» → ✅ «Текущий алгоритм имеет проблему Z; возможный путь решения — Y»
   - ❌ «Объединить скиллы A и B» → ✅ «Скиллы A и B имеют пересекающийся scope в части X — возможное объединение на согласование»
   - ❌ «Roadmap фиксов» → ✅ «Перечень найденного, отсортированный по severity»

   Ревью — это **диагностика**, не лечение. Каждый пункт — на согласование. Решение, патч, рефакторинг — отдельная задача после approve.

### Что НЕ переводим

- Названия файлов / путей / commit-хэшей.
- Имена функций, классов, переменных.
- Идентификаторы стандартов (152-ФЗ, GDPR, OWASP A03).
- Названия скиллов/команд (`/landing-go`, `block-composer`).
- Цитаты кода в code-fences.

### Стилистика

- Без воды, без «следует отметить, что».
- Глаголы действия: «сломано», «не работает», «утечёт», «украдут», «исправить».
- Размер: руководительский блок — не больше 4-5 строк. Технический — сколько нужно.
- Эмодзи только заданные severity-маркеры (🔴🟠🟡🟢).

### Шаблон одного finding (copy-paste готовый)

# Фаза 0 — Reference Map

## Цель (для руководства)

Прежде чем что-то рекомендовать к удалению, надо понять — **кто кого вызывает**.
Строим карту: для каждого файла проекта — список откуда на него ссылаются.
Это фундамент для всех остальных фаз. Без этой карты любое «удалить» — гадание.

## Методология

1. Собрать список «candidate» файлов через Glob (точные количества определяются по факту, не предполагаются заранее):
   - `skills/*/SKILL.md`
   - `agents/*.md`
   - `.claude/commands/*.md` и `commands/*.md` (зафиксировать обе папки отдельно для последующего diff)
   - `scripts/**/*.{sh,py}` (без `__pycache__`)
   - `config/*.yaml`
   - `docs/standards/*.md`
   - `template/**/README.md`
   - `block-library/*/*/meta.yaml`, `block-library/_patterns/*/meta.yaml`, `block-library/_styles/*/README.md`
   - mu-plugin: `skills/wp-landing-config/mu-plugin/**/*.php`

   **Принцип:** ревьюер не должен заранее знать «сколько должно быть». Glob возвращает столько, сколько есть. Расхождение между ожиданием и фактом — само по себе finding.

2. Для каждого кандидата — `basename` без расширения + полный путь.
3. Через Grep пройти по всему репо и для каждого упоминания записать:
   - кто ссылается (файл-источник)
   - тип ссылки (`Skill: name`, `Agent(subagent_type=name)`, `bash scripts/X.sh`, `include 'X.php'`, упоминание в markdown, etc)

4. Классификация usage_class:
   - `active` — есть ≥1 ссылка из исполняемого слоя (агент/команда/скрипт/PHP include)
   - `doc-only` — упоминается только в `wiki/`, `docs/`, `README`, `CLAUDE.md`
   - `orphan` — 0 ссылок откуда бы то ни было

5. Output:
   - `phase-0-reference-map.json` — машиночитаемый: `{file: {referenced_by: [...], references: [...], usage_class: ...}}`
   - `phase-0-reference-map.md` — human summary: полный список sources с числом исходящих ссылок (отсортированный по убыванию) + полный orphan-лист. Никаких «топ-N» — все файлы.

## Что искать особенно (паттерны, не конкретные файлы)

Применять ко **всему списку** candidate-файлов, без выделения каких-либо имён заранее:

1. **Дубликат папок:** `.claude/commands/` vs `commands/` — для каждой команды сравнить наличие и содержимое в обеих папках.
2. **Кластеры с общим префиксом** (например `photo-*`, `landing-*`, `wp-*`, `_migrate-*`) — для каждого кластера зафиксировать состав и пересечения функционала, без априорного предположения что часть «лишняя» или «нужная».
3. **Префикс подчёркивания** в именах файлов (`_X.py`, `_X.sh`) — соглашение часто означает «приватный» или «одноразовый» (миграция). Зафиксировать факт + проверить вызовы.
4. **Выпадающий стиль именования** — для каждого файла, чьё имя сильно отличается от доминирующих в проекте паттернов (например, проектные имена идут как `<prefix>-<verb>`, а встречается другое), зафиксировать наблюдение. **Это не повод считать файл мёртвым** — только повод проверить вызовы и историю коммитов. «Доминирующие паттерны» определяются ревьюером по факту, не по моим примерам.
5. **Migration-скрипты** (`migrate-*`, `*-migrate.*`, `backport-*`) — для каждого: запускался ли уже, оставлен ли для будущих установок, или одноразовый завершённый.
6. **Скрипты с суффиксом `.doc.md`** рядом с исполняемыми — wiki-источники для авто-документации. Проверить что упомянутый исполняемый файл существует и наоборот.

**Принцип:** ревьюер не должен знать заранее «какие файлы подозрительные». Все паттерны применяются ко всем файлам равномерно. Имена в этом playbook'е не приводятся, чтобы не задавать фокус.

## Дополнительный output

`phase-0-suspicious-duplicates.md` — список пар файлов с похожими именами/функциями, для ручного решения в фазе 1.

# Фаза 1 — Inventory of Unused Files

## Цель (для руководства)

Главный запрос: найти все файлы которые **не имеют видимых вызовов в исполняемом слое**.
Каждый такой файл оркестратор всё равно «видит», тратит токены. Долю предстоит установить
по фактам, без априорных оценок.

Фаза **только составляет список с пометками**. Никаких удалений, никаких слияний.
По каждому пункту — финальное решение за пользователем.

## Методология

1. Прочитать `phase-0-reference-map.json`.
2. Для каждого скилла/агента/команды/скрипта — заполнить классификацию:
   - 🔴 **БЕЗ ВИДИМЫХ ВЫЗОВОВ** (`usage_class: orphan`, 0 ссылок откуда-либо). На согласование: сохранить / архивировать / удалить.
   - 🟡 **ТОЛЬКО В ДОКУМЕНТАЦИИ** (`usage_class: doc-only`) — упоминается в `wiki/`, `docs/`, `README`, `CLAUDE.md`, но не вызывается из агентов/команд/скриптов. На согласование: возможно это «забытый» компонент, или специально оставлен для будущего.
   - 🟢 **АКТИВНЫЙ** — есть хотя бы один вызов из исполняемого слоя.

3. Дубликат папок `.claude/commands/` vs `commands/` — зафиксировать факт расхождения, перечислить какие команды есть в одной и нет в другой. **Не решать за пользователя какая каноничная** — только показать данные.

4. Похожий по названию/scope функционал (требует human-decision):
   - Для **каждого кластера файлов с общим префиксом** (выявленных в фазе 0) — описать что именно каждый делает (одна строка цели) и где пересечения. **Не предлагать слияние как готовое решение** — только зафиксировать факт пересечения для согласования.
   - Не выделять заранее «подозрительные» кластеры — применять ко всем равномерно.

## Структура отчёта

```markdown
# Phase 1 — Inventory of Unused Files

## Executive Summary
Скиллов без видимых вызовов <число>, агентов <число>, команд <число> (полные суммы — в секции «Метрики»).
Папка `commands/` и `.claude/commands/` содержат расхождения — фиксируем факт.
Все пункты — на согласование пользователя. Никаких действий не выполнено.

## Список без видимых вызовов (🔴)
### #1 🔴 Скилл `<имя>` — нет входящих ссылок

**Что это значит простыми словами:**
Скилл существует, но ни один агент / команда / скрипт его не зовёт.
Возможно: остался от прошлого эксперимента, или планировался к использованию, но не подключён.

**Чем грозит бизнесу:**
- Лишний файл в репо.
- Оркестратор тратит токены при сканировании структуры.
- Путает разработчика — непонятно живой компонент или нет.

**Оценка срочности (на согласование):** не блокирует ничего, но можно навести порядок в любой момент.

**Статус решения:** ☐ на согласовании

---

**Технические детали:**

- Путь: `skills/<имя>/`
- Проверено: 0 упоминаний в `agents/`, `commands/`, `.claude/commands/`, `scripts/`.
- Последний коммит, затрагивавший файл: <дата> (`<commit-hash>`)
```

# Фаза 2 — Token-Hotspots & Алгоритмические Петли

## Цель (для руководства)

Главный запрос: расход токенов и петли в алгоритме оркестратора.
Если агент уходит в цикл «попробовать-упало-попробовать ещё раз» без ограничения,
один прогон может съесть бюджет дня. Если промпт раздут — каждый вызов стоит дороже
в N раз. Это деньги.

## Методология

### 2.1 Раздутые промпты

Сканируем активные (`usage_class: active`) скиллы и агенты:

1. `wc -l` каждого `SKILL.md` и `agents/*.md` → получаем список размеров.

2. **Строим распределение по факту** — считаем перцентили:
   - **медиана (p50)** — серединная длина: половина файлов короче, половина длиннее. «Типичный» размер для этого проекта.
   - **p75** — длина, ниже которой остаются 75% файлов; четверть проекта — длиннее этой отметки.
   - **p90** — только 10% файлов длиннее этой черты. Это «верхний хвост».
   - **p99** — только 1% файлов длиннее. Экстремальные значения.

   Заранее заданных порогов (типа «400 строк = подозрительно») **нет**. Что считать «раздутым», определяется **относительно остальных файлов этого же проекта**: в проекте с короткими скиллами 300 строк — outlier, в проекте с длинными — норма.

3. **Кандидаты на «раздутые промпты»** — два независимых критерия:
   - все файлы выше **p90** (верхний хвост распределения);
   - все файлы, превышающие медиану **в 3+ раза** (абсолютные outlier'ы, даже если хвост распределения сам тяжёлый).

4. Для каждого такого файла проверяем: можно ли часть содержимого вынести в `references/X.md` (скиллы поддерживают подгружаемые рефы — это token-friendly паттерн).

5. Output фазы должен содержать **таблицу всех файлов** с размерами + отметки кому в какой критерий попал. Не «верхние X» — все.

### 2.2 Циклы без exit-condition

Grep по активным агентам и командам на паттерны:
- «retry», «again», «if fails go back to», «iterate until», «keep trying»
- Без рядом стоящего `max_attempts`, `max_retries`, `attempt < N`, «не более X раз»

Зоны повышенного внимания (по архитектуре, не по «подозрительности имени»):
- **Главные диспетчеры** (агенты/команды с самым большим числом исходящих вызовов по reference-map'е) — у них больше всего возможностей для loop'ов.
- **Auto-fix паттерны** во всех stage-gates и оркестраторе — везде где после verify-failure есть «попробуй ещё раз».
- **Spec'и из `docs/superpowers/specs/`** — для **каждого** spec'а, который декларирует что-то «out of scope» или «вне scope текущего PR», проверить что декларация соблюдена в текущем коде. Это паттерн «doc says X is not implemented — verify it's still not implemented» для всех spec'ов, не для какого-то конкретного.
- **Все агенты с глаголами «keep», «watch», «monitor», «retry» в имени или описании** — подозрительность определяется по содержимому файла, не по имени.

### 2.3 Каскадные вызовы

Построить граф «агент A → агент B → агент C» (на основе фазы 0).
Найти циклы в графе. Любой цикл без явного breaker'а — потенциальный infinite loop.

### 2.4 Дубли контекста

Для тяжёлых файлов (`tokens.json`, `prototype.md`, `composed.html`, `brand-kit.md`,
`.landing-state.yaml`) — кто их читает? Если 3+ агента читают один файл подряд
без передачи через параметр — это N-кратная оплата чтения.

### 2.5 Wiki-utilization check (гипотеза пользователя)

Пользователь использует wiki/ для **экономии токенов** — чтобы оркестратор читал
сжатые wiki-страницы вместо полных исходников. Проверяем реальность гипотезы:

1. Grep по `wiki/` упоминаниям в `agents/*.md`, `.claude/commands/*.md`, `scripts/`.
2. Если 0 упоминаний — wiki **не выполняет свою цель**, никто её не читает.
3. Если есть — фиксируем кто использует, и оцениваем экономию.
4. Дополнительно: проверить актуальность wiki (хэш-кэш / `check-wiki-sync.sh` —
   реально ли работает; есть ли в репо случаи когда wiki разошлась с источниками).

### 2.6 Heavy operations (платные / медленные внешние вызовы)

Для **всех** скриптов и скиллов ищем паттерны дорогих операций (без выделения каких-либо имён заранее):

1. **HTTP-запросы:** grep по `curl`, `wget`, `wp_remote_*`, `requests.get/post`, `fetch(`, `http.get`, `urlopen`. Для каждого найденного места:
   - вызывается в loop'е?
   - есть ли кэш по входу (hash, mtime, etag)?
   - есть ли rate-limit / sleep между запросами?
   - есть ли timeout?
   - есть ли retry-policy с `max_attempts`?

2. **AI / LLM вызовы:** grep по `codex`, `openai`, `anthropic`, `claude`, `gpt`, `image_gen`, `chat.completions`, `messages.create`. Для каждого:
   - есть ли кэш результата (по hash промпта + параметров)?
   - есть ли подсчёт токенов / стоимости в логах?
   - есть ли fallback на дешёвую модель при retry?

3. **Файловые операции в loop'е:** чтение одного и того же файла несколько раз подряд в рамках одного процесса/агента. Любой файл — без выделения каких-либо как «особо тяжёлых». Если файл большой по размеру (`stat -c %s` или эквивалент) и читается повторно — это потеря производительности.

4. **wp-cli / shell вызовы:** `subprocess.run`, `shell_exec`, `wp ` — каждый вызов это новый процесс PHP/wp-cli, дорого. Можно ли батчить?

5. **DB-запросы:** в mu-plugin — `$wpdb->query` в loop'е (N+1 паттерн)?

Для **каждой** найденной точки в отчёте — отдельная запись с file:line, без отбора «важных».

Сравнение с гипотезами из документации: если CLAUDE.md или spec'и заявляют что «есть кэш», «работает hash-кэш», «есть rate-limit» — фиксируем как **гипотезу для проверки**, а не как «известный факт». Реальность проверяется по коду.

## Структура отчёта

Стандартная (Executive Summary + все findings, сгруппированные по 4 severity), плюс **отдельная секция**
«Wiki-utilization report» с конкретными числами:

```markdown
## Wiki-utilization report
- Wiki-страниц всего: N
- Из них упоминается в исполняемом слое: M (M/N = X%)
- Если M=0 → wiki не работает на свою цель, разобраться зачем она.
- Все wiki-страницы с числом обращений из исполняемого слоя (отсортированы по убыванию, без обрезки).
- Wiki-страницы которые никто не читает: [список]
```

# Фаза 3 — Flow Integrity (AI-pipeline)

## Цель (для руководства)

Главный запрос: порядок шагов и возможные пропуски.
Главная команда оркестратора (по описанию проекта — `/landing-go`) ведёт через
последовательность этапов от прототипа до деплоя. Если где-то можно «проскочить»
этап или этап не закроется при ошибке — клиент получит полусобранный лендинг.

Точное число этапов, их идентификаторы, подэтапы, параллельные ветки —
**всё определяется по факту чтения кода**, без априорных предположений.
В playbook'е намеренно не указываются ни количество этапов, ни конкретные ID —
чтобы ревьюер не пропустил то, чего нет в этом списке.

## Методология

1. Реконструировать happy-path. Источники (entry-points системы по описанию проекта):
   - `agents/landing-orchestrator.md` — главный диспетчер;
   - `commands/landing-go.md` и/или `.claude/commands/landing-go.md` — главная команда;
   - `config/stage-gates.yaml` — конфиг гейтов;
   - `template/*/README.md` — собрать **полный список** через Glob, не предполагая количество;
   - `.claude/commands/landing-*.md` — **все** команды этапов, без выделения каких-либо.

   Дополнительные источники определяются по reference-map (фаза 0): любой файл, на который ссылается оркестратор или команда `landing-go`, попадает в скоуп.

2. Построить Mermaid-диаграмму happy-path:
   - Узлы = **все этапы и подэтапы, найденные в коде** (не из памяти, не из CLAUDE.md, а из факта чтения).
   - Стрелки = переходы между этапами (по reference-map и по `prerequisites:` в `stage-gates.yaml`).
   - Ромбы = gates с verify-скриптами.
   - **Все** параллельные ветки, найденные в коде — без выделения «особо важных».

3. Для **каждого** stage-gate в `config/stage-gates.yaml` (без отбора):
   - Указан ли `verify_script`?
   - Существует ли файл скрипта на диске?
   - Есть ли права на исполнение (`chmod +x` или интерпретатор в shebang)?
   - Указан ли `hard_gate: true/false`? Если `false` — что произойдёт при провале: skip / halt / warn?
   - `prerequisites: [...]` — все ли референс-стейджи существуют?
   - Что произойдёт при провале verify'я? auto-fix / halt / skip / другое?

4. **Заявления из документации против фактического состояния кода:**
   CLAUDE.md и spec'и в `docs/superpowers/specs/` часто содержат фразы «вызывается вручную», «не интегрировано», «out of scope», «TODO», «вне scope», «задача следующего PR», «будет позже», «manual». Ревьюер обязан:
   - извлечь **все** такие заявления через Grep по приведённым паттернам (на русском и английском);
   - для **каждого** заявления зафиксировать актуальное состояние в коде (закрыто / не закрыто / частично);
   - не выделять каких-либо конкретных PR-ID, фич или дыр заранее — каждое заявление обрабатывается равноправно, в порядке Grep-вывода.

5. Циклы и параллельность в флоу:
   - Все параллельные ветки, найденные в Mermaid-графе (шаг 2): для каждой проверить наличие join-point'а перед следующим последовательным этапом.
   - Все auto-fix loops (определяются Grep'ом по паттернам «retry», «if fails», «attempt», «again», «auto-fix», «исправь»): для каждого проверить наличие `max_attempts` или эквивалентного breaker'а.

6. Migration paths:
   - Найти **все** скрипты с паттерном `migrate-*`, `*-migrate.*`, `backport-*`, `_migrate-*` в `scripts/` и `skills/*/scripts/`.
   - Для каждого: упоминается ли в CLAUDE.md / README / onboarding? Описан ли когда запускать? Авто или вручную? Идемпотентен?

7. Stage-gate из любых дополнительных источников: `landing-final-check`, `landing-audit`, `landing-qa`, `seo-tech-audit` — для каждой команды/скилла с глаголом проверки в имени найти что именно проверяется и встроено ли в pipeline. Не ограничиваться этими именами — искать по паттерну «check», «verify», «audit», «qa», «final», «gate».

## Что выдаёт фаза

- `phase-3-flow-integrity.md` — отчёт.
- `phase-3-flow-expected.mmd` — Mermaid диаграмма «как пайплайн заявлен в CLAUDE.md / spec'ах» (с цитатами источников).
- `phase-3-flow-actual.mmd` — Mermaid диаграмма «как реально устроено в коде» (с пометками broken/unwired/missing).
- В отчёте — таблица расхождений «заявлено vs реально», построчно для каждого этапа.

## Формат finding'а для этой фазы

Используем общий шаблон из Bilingual Reporting Standard. Никаких предзаготовленных

# Фаза 4 — UI Completeness (HTML/CLI)

Главный запрос: «каждой кнопке/ссылке должны быть соответствующие элементы».

# Фаза 5 — Code Quality & Correctness

## Цель (для руководства)

Это «классический» code review: баги, плохая обработка ошибок, плохие имена, слабые тесты.

## Методология

4. **Тесты:**
   - В `tests/` есть `.bats`, `pytest`, `vitest`? Покрытие критических зон есть?
   - CLAUDE.md заявляет «TDD строго» — реально ли каждое изменение начиналось с теста?

5. **Naming consistency:**
   - Для **всех** команд/скиллов/агентов: однозначно ли имя описывает функцию? Где имена пересекаются по смыслу, пользователь может не понять какую звать. Зафиксировать пары/тройки с потенциальной путаницей — все, найденные при просмотре, не только примеры.

# Фаза 6A — WP-admin UI Wiring

## Цель (для руководства)

Главная боль пользователя: «часть интерактивных элементов вообще не работает,
часть ведёт на несуществующие ссылки». Это про WP-админку mu-plugin'а.
Маркетолог жмёт кнопку — ничего. Кликает ссылку — «страница не найдена».
Это первое впечатление клиента; если админка глючит — система выглядит сырой.

## Скоуп

**Все** WP-admin страницы проекта — независимо от того, в каком mu-plugin'е, плагине или теме они зарегистрированы. Точка входа в скоуп — Grep по всему репозиторию:

- `add_menu_page` / `add_submenu_page` / `add_network_admin_menu` / `add_options_page` / `add_management_page` / `add_dashboard_page` / `add_theme_page` / `add_plugins_page` / `add_users_page` / `add_tools_page` — каждое срабатывание = одна admin-страница в скоупе.

Дополнительно в скоуп попадают:
- **все** PHP-файлы, в которых найдено хотя бы одно из срабатываний выше;
- **все** PHP-файлы, на которые из них есть `include` / `require` / `require_once` / автозагрузка;
- **все** JS/CSS-ассеты, подключённые через `wp_enqueue_script` / `wp_enqueue_style` к hooks этих admin-страниц.

Точное число admin-страниц, табов, layout-ов, плагинов, регистрирующих admin — определяется по факту. В playbook'е не указано ни конкретное имя плагина, ни конкретный путь — чтобы фаза 6A покрыла любые новые mu-plugin'ы и плагины, которые появятся в проекте.

## Методология

Для каждой admin-страницы построить **таблицу контролов**:

| Контрол | Тип | Где определён | Action / Handler | Status |
|---|---|---|---|---|

Проверки для каждого контрола:

1. **Формы** (`<form action=`):
   - Если `action="admin-post.php?action=X"` → существует ли `add_action('admin_post_X', ...)` или `admin_post_nopriv_X`?
   - Если `action=""` (POST на ту же страницу) → читается ли `$_POST` в page-handler'е?

2. **AJAX** (JS `wp.ajax` / `fetch` / `$.post`):
   - Существует ли `wp_ajax_X` / `wp_ajax_nopriv_X` зарегистрированный handler?
   - Совпадает ли `action`-имя на клиенте и сервере?

3. **Кнопки без action:**
   - `<button>` без `type="submit"` и без JS listener'а → orphan, не работает.

4. **Ссылки** (`<a href="?page=X">`, `<a href="admin.php?page=X">`, `<a href="post.php?post=ID">`, `<a href="customize.php?...">` и любые другие admin URL):
   - Зарегистрирована ли страница `X` через `add_menu_page` / `add_submenu_page` / `add_network_admin_menu` / `add_options_page` / `add_management_page`?
   - Для **любых** deep-link'ов с параметрами (`?id=`, `?post=`, `?segment=`, и т.п.) — параметр валиден на момент рендера ссылки? Или может оказаться пустым/неверным?
   - Если есть каталоги ссылок (массивы fix-actions, навигационные карты, breadcrumb-конфиги) — для **каждой** записи каталога проверить что target существует. Без выделения какого-либо одного каталога.

5. **Hidden inputs** (`<input type="hidden" name="X">`):
   - Читается ли `$_POST['X']` в handler'е? Если нет — мёртвый input.

6. **`data-*` атрибуты:**
   - Используются ли в JS этого же шаблона?

7. **Cookie-banner UI** (все layout-файлы из `includes/cookie-banner/layouts/` — количество по факту):
   - Каждая кнопка категории / «Принять» / «Отклонить» / «Настройки» имеет listener в `banner.js`?
   - Layout-preview в admin (thumbnail) — кликабельно? Выбор сохраняется?

8. **Segment selector**:
   - `?segment=N` корректно подтягивается на все admin-pages?
   - Сохраняется при навигации между табами?

## Output

`phase-6a-ui-wiring.md` + полная таблица контролов с маркировкой ✅/⚠️/❌.
Каждый ❌ — отдельный finding по шаблону.

# Фаза 6B — WP-admin Security (deep)

## Цель (для руководства)

**Главная зона риска во всём проекте.** Через эту админку проходят:
- база заявок клиентов (имена, телефоны, email);
- учётные данные CRM (API-ключи AmoCRM/Bitrix24, токены HubSpot, Telegram bot-токены);
- произвольный HTML/JS (snippets) — атакующий может вставить любой код в head лендингов;
- настройки 152-ФЗ согласия — если сломать, штраф Роскомнадзора.

Если злоумышленник получит доступ хотя бы как «editor» — он сольёт лиды или подменит CRM
на свой webhook. Если найдёт XSS или CSRF в админке — то же самое без логина.

## Скоуп

**Все** mu-plugin'ы, плагины и темы проекта, имеющие хотя бы один из признаков ниже — независимо от пути и имени. Точка входа в скоуп — Grep по всему репозиторию для определения границ; конкретное имя `wp-landing-config` (или любое другое) **не** прописывается в playbook'е заранее.

В скоуп попадают **все** PHP- и JS-файлы из таких компонентов:
- `**/*.php` (рекурсивно, без выделения папок)
- `**/*.js` (для XSS-векторов через клиент)

Особое внимание к файлам с публичной поверхностью атаки (определяется ревьюером по содержимому, не по имени):
- любые REST endpoint'ы (Grep по `register_rest_route`);
- любые публичные admin-post handlers (`admin_post_nopriv_*`);
- любой код, выполняющий шифрование/дешифровку (Grep по `openssl_`, `sodium_`, `hash_hmac`, `random_bytes`);
- любые SQL-запросы к per-blog таблицам (Grep по `$wpdb->`);
- любые внешние HTTP-вызовы к CRM/webhook'ам (Grep по `wp_remote_*`, `curl_*`);
- любая обработка user-uploaded файлов (Grep по `wp_handle_upload`, `move_uploaded_file`).

Точное число файлов в каждой категории — определяется по факту Grep'а.

## WP-Security Checklist (для этой фазы)

### 1. Capability checks (авторизация)
- [ ] Каждая admin-страница начинается с `current_user_can()`?
- [ ] `manage_options` (site admin) vs `manage_network_options` (super admin) — корректно разделено?
- [ ] Каждый `admin_post_*` / `wp_ajax_*` handler имеет capability check?
- [ ] REST endpoints: `permission_callback` НЕ `__return_true`?
- [ ] Для **каждой** network-only admin-страницы (editor'ы CPT, dictionary editors, vocab editors и т.п.) проверить что доступ требует `manage_network_options`, а не `manage_options`?

### 2. Nonce verification (CSRF — защита от подложных запросов)
- [ ] Каждая форма содержит `wp_nonce_field()`?
- [ ] Каждый handler делает `check_admin_referer()` или `wp_verify_nonce()`?
- [ ] Bulk actions: `check_admin_referer('bulk-leads')`?
- [ ] AJAX: `check_ajax_referer()`?

### 3. Input sanitization (очистка пользовательского ввода)
- [ ] `$_POST` / `$_GET` обёрнуты в `sanitize_text_field` / `sanitize_email` / `absint` / `wp_kses_post`?
- [ ] **Snippets** (произвольный HTML в head/body):
  - Whitelist тегов через `wp_kses`?
  - Capability-gate: только super-admin может писать `<script>`?
  - Если super-admin'у разрешено всё — задокументировано ли что это сознательный риск?
- [ ] `llms.txt content` — фильтруется?

### 4. Output escaping (защита от XSS)
- [ ] `echo $var` без обёртки → найти все случаи.
- [ ] Все динамические данные в HTML обёрнуты: `esc_html`, `esc_attr`, `esc_url`, `esc_textarea`?
- [ ] **Для каждого** места, где пользовательский ввод из admin рендерится в `<meta>`, `<title>`, `<link>` или другие head-теги фронта — обёрнут в `esc_attr`?
- [ ] **Для каждого** места рендера SVG из user-input (admin поле / БД) — обёрнут в `wp_kses` с whitelist'ом разрешённых SVG-тегов?

### 5. SQL injection (защита БД)
- [ ] Все запросы к `wp_<bid>_landing_leads`, `wp_<bid>_landing_lead_status_log` через `$wpdb->prepare`?
- [ ] Динамическое `$table_name` собирается через `$wpdb->prefix`, не из user-input?
- [ ] `LIKE` queries используют `$wpdb->esc_like`?

### 6. REST endpoint `/wp-json/landing/v1/lead` (публичный!)
- [ ] Rate-limit работает per-IP (не per-session, иначе тривиально обходится)?
- [ ] Honeypot `website` проверяется ДО записи в БД?
- [ ] 152-ФЗ: `pd_consent != '1'` → 400?
- [ ] User-Agent / IP — анонимизация для соответствия 152-ФЗ?
- [ ] CSRF не нужен (это публичный endpoint), но валидация Origin/Referer для anti-spam?
- [ ] SSRF в адаптерах CRM: URL валидируется на схему (http/https only)?
- [ ] Timeout для CRM-вызовов установлен (иначе DoS-вектор)?

### 7. Encryption (`encryption.php`)
- [ ] Алгоритм: AES-256-GCM (а не CBC без HMAC)?
- [ ] IV случайный для каждого шифрования (не статичный)?
- [ ] Ключ в `wp-config.php` constant — не в `wp_options` (иначе ключ рядом с шифротекстом = бесполезно)?
- [ ] Все `encrypt: true` поля в `field_definitions()` реально проходят через encrypt перед записью?
- [ ] Существуют ли legacy plain-text записи? Migration path есть?

### 8. File handling
- [ ] OG image upload: `wp_handle_upload` с whitelist mime-types?
- [ ] Cookie-banner previews: assets через `wp_enqueue_*`, не `file_get_contents` с user-controlled path?

### 9. Multisite isolation
- [ ] `switch_to_blog()` всегда парный с `restore_current_blog()` (в try/finally или ранний return)?
- [ ] Per-blog таблицы: `wpmu_delete_blog` hook для cleanup при удалении сайта?
- [ ] Cascade resolver (`cascade.php`): может ли site admin от subsite редактировать network запись?
- [ ] Read-only views на subsite реально read-only (нет скрытых POST-форм)?

### 10. Sensitive data в логах
- [ ] `error_log()` / debug.log — нет CRM credentials, phone numbers, full IPs?
- [ ] Adapter exceptions — stack trace без API keys в plain text?

### 11. CRM adapters (`adapters/*.php`)
- [ ] `wp_remote_post` / `wp_remote_get`: `'sslverify' => true` (не false)?
- [ ] Timeout установлен?
- [ ] Webhook URLs валидируются на schemes (только http/https, не `file://`, `gopher://`, `php://`)?
- [ ] Retry-on-failure: есть max_attempts (иначе loop при стабильно отказывающем CRM)?

### 12. Cookie consent / GDPR / 152-ФЗ
- [ ] Google Consent Mode v2 действительно блокирует analytics ДО consent?
- [ ] `lp_cookie_consent` localStorage — expiry установлен?
- [ ] PD-consent в `landing-leads`: timestamp пишется?
- [ ] Можно ли клиенту экспортировать / удалить свои данные (152-ФЗ ст. 14, 21)?

## Структура отчёта

Стандартная + **обязательный блок «PoC и эксплойт-вектор»** для каждого 🔴/🟠 finding:
конкретные шаги/код как воспроизвести атаку. Это нужно для:
1. Понимания серьёзности (руководству).
2. Тестирования фикса (разработчику).

PoC может включать `curl`-запросы, HTML-формы для CSRF-демо, JS payload для XSS.

## Дополнительный инструмент

Параллельно с code-reviewer запустить встроенный `/security-review` на том же скоупе
(все mu-plugin'ы, плагины, темы проекта — определяются Grep'ом из секции «Скоуп»).
Сравнить findings, мерджить в единый отчёт. Помечать: «найдено code-reviewer'ом»,
«найдено security-review'ом», «обоими».

# Фаза 6C — WP-admin Flow Coherence

## Цель (для руководства)

Связность путей маркетолога: не «работает ли одна кнопка», а «может ли маркетолог
пройти полный сценарий от начала до конца, не заблудившись».

## Сценарии для проверки (определяются по факту, не из этого списка)

**Принцип:** ревьюер строит карту admin-страниц (через `add_menu_page` /
`add_submenu_page` / `add_network_admin_menu` / `add_options_page` / `add_management_page`
grep по **всему** репозиторию, не ограничиваясь конкретным mu-plugin'ом), затем для
**каждой** редактируемой сущности проходит весь её жизненный цикл от создания
до отображения на фронте. В playbook'е намеренно не перечисляются конкретные
сценарии (cookie-banner, lead detail, audit, и т.д.) — ревьюер должен сам
обнаружить **все** flow и проверить каждый, а не ограничиться теми что я успел
вспомнить.

**Универсальные паттерны flow, которые нужно отследить (без привязки к именам):**

1. **Edit-cycle flow** — для каждой настройки/сущности, редактируемой в admin:
   - admin-страница → preview/visual feedback после изменения → save → запись в БД (option / CPT / per-blog table) → применение на subsite/фронте → видим эффект на реальной странице.

2. **List → Detail → Action flow** — для каждой коллекции в admin (заявки, статусы, CTA-пресеты, integration-адаптеры, snippets, и т.д.):
   - список → клик на элемент → detail-страница → действие на элементе → возврат в список с обновлёнными счётчиками/состоянием → история изменений если применимо.

3. **Cross-page state flow** — для **любого** глобального селектора (сегмент, проект, environment, и т.д.):
   - выбрал значение на странице A → перешёл на B → состояние сохранилось? Или сбросилось?

4. **Network → Subsite cascade flow** — для **каждой** сущности с cascade-логикой:
   - редактирование на network уровне → видно ли на subsite? Read-only views корректно отображают данные? Override на subsite перебивает network default?
   - Не утекают ли encrypted/sensitive данные в read-only view?

5. **Async/Job flow** — для **каждой** долгой операции (audit, batch action, import, generate):
   - запуск → progress/feedback → завершение → результат доступен → можно ли вернуться к нему позже?
   - что произойдёт при перезагрузке страницы в середине job'а?

6. **Migration / Versioning flow** — для **каждого** migration marker в коде (Grep по `landing_config_migration_*`, `update_option.*migration`, `maybe_run`):
   - идемпотентность: что произойдёт при повторном запуске?
   - rollback path: что произойдёт при downgrade плагина?
   - порядок миграций при чистой установке vs incremental update.

7. **Deep-link flow** — для **каждого** deep-link'а из admin (в audit dashboard, lead detail, и т.д.):
   - target страница существует?
   - параметры (`?id=`, `?segment=`) валидны?
   - возврат после действия попадает обратно в нужную точку?

Для **каждой** обнаруженной сущности в admin строится отдельный flow по одному из
паттернов выше (или нескольким). Никаких «топ-N сценариев» — все, что найдены.

## Output

`phase-6c-admin-flow.md` + **sequence-диаграммы** наиболее критичных flow в Mermaid:
```
sequenceDiagram
    Marketer->>NetworkAdmin: Открыть Cookie-banner
    NetworkAdmin->>DB: SELECT cookie_banner_settings
    ...
```
С маркировкой broken-нод и пропущенных переходов.

Фазы запускаются последовательно (каждая в своей сессии Claude Code), чтобы не убивать контекст:

```
Сессия 1: Фаза 0 (Reference Map)
  ↓ артефакт: phase-0-reference-map.json

Сессия 2: Фаза 1 (Dead Code) — читает phase-0
  ↓
Сессия 3: Фаза 2 (Token Hotspots) — читает phase-0
  ↓
Сессия 4: Фаза 3 (Flow Integrity) — читает phase-0
  ↓
Сессия 5: Фаза 4 (UI Completeness) — читает phase-0
  ↓
Сессия 6: Фаза 5 (Code Quality) — читает phase-0, phase-1
  ↓
Сессия 7: Фаза 6A (UI Wiring) — читает phase-0
  ↓
Сессия 8: Фаза 6B (Security) — независимая, скоуп mu-plugin
  ↓
Сессия 9: Фаза 6C (Admin Flow) — читает phase-6a
  ↓
Сессия 10: SUMMARY.md — читает все отчёты
```

Каждую сессию запускать командой формата:
```
Запусти code-reviewer skill согласно docs/code-review/2026-05-23-review-plan.md, фаза N.
Прочитай phase-0-reference-map.json как input.
Output → docs/code-review/phase-N-<topic>.md (+ technical-appendix/phase-N-evidence.md).
Все описания issues — на русском по шаблону playbook'а, severity на русском.
ВАЖНО: только репортинг. Никаких действий, удалений, переименований, фиксов.
Каждый пункт — на согласование пользователя, статус «☐ на согласовании».
```

# Известные ограничения

1. **Code-reviewer skill — read-only** (Read/Grep/Glob). Не правит код, только пишет отчёты.
2. **Не запускает тесты** — анализ статический.
3. **PoC уязвимостей** — описательные, без реальной эксплуатации (мы анализируем свой код, не пентестим прод).
4. **Reference-map не покрывает динамические include** (`include $variable` в PHP), они помечаются как «требует ручной верификации».
5. **Phase 6C sequence-диаграммы** требуют чтения нескольких файлов цепочкой — самая дорогая фаза по контексту.

# Глоссарий (мастер)

- **AJAX** — асинхронный запрос из браузера на сервер без перезагрузки страницы.
- **capability** — право пользователя в WP (например, `manage_options` есть только у админа сайта).
- **CSRF (cross-site request forgery)** — атака, при которой жертва, будучи залогиненной, по подложной ссылке выполняет действие в админке.
- **CRM** — система учёта клиентов и заявок (AmoCRM, Bitrix24, HubSpot).
- **DoS (denial of service)** — атака на отказ в обслуживании; например, медленный CRM зависает все обработчики.
- **GDPR** — европейский регламент защиты персональных данных.
- **honeypot** — скрытое поле формы; если бот заполнил — отбраковываем.
- **mu-plugin** (must-use plugin) — WP-плагин, который активирован принудительно и не отключается из админки.
- **multisite** — несколько WP-сайтов в одной инсталляции (для нас: главный сайт клиента + поддомены сегментов ЦА).
- **nonce** — одноразовый токен; WP добавляет в формы и проверяет при отправке для защиты от CSRF.
- **orphan-файл** — файл без входящих ссылок; никто его не вызывает.
- **outlier** — значение, сильно выпадающее из общего распределения. Например, файл в 5 раз длиннее «типичного» в проекте.
- **перцентиль (p50/p75/p90/p99)** — статистическая отметка: pN значит «N% значений ниже этой черты». p50 = медиана (середина). p90 = «черта верхнего хвоста»: 90% файлов короче, только 10% длиннее. Используется чтобы определить «раздутость» **относительно остальных файлов проекта**, а не по выдуманному порогу.
- **PoC (proof of concept)** — минимальная демонстрация что уязвимость реально работает.
- **REST endpoint** — URL, по которому браузер/сервер обращается за данными (наш `/wp-json/landing/v1/lead`).
- **rate-limit** — ограничение количества запросов с одного IP в единицу времени.
- **SQL injection** — внедрение злоумышленником SQL-кода в запрос; даёт доступ к БД.
- **SSRF (server-side request forgery)** — атакующий заставляет сервер обратиться по своему URL (например, на внутреннюю сеть).
- **subsite** — отдельный сайт в multisite (для нас: один сегмент ЦА).
- **XSS (cross-site scripting)** — внедрение JS в страницу; выполнится в браузере жертвы, украдёт сессию.
- **152-ФЗ** — российский закон «О персональных данных»; нарушение — штраф Роскомнадзора.
