# Phase 5 — Code Quality & Correctness

**Дата:** 2026-05-23
**Скоуп:** активные Python-скрипты в `scripts/` и `skills/*/scripts/`, активные bash-скрипты, активные `agents/*.md` (на предмет противоречий и нечётких инструкций). mu-plugin **не входит** — он целиком в фазе 6B.
**Инструмент:** code-reviewer skill (read-only)

## Executive Summary (для руководства)

Главная находка: **wiki-скрипты системы жёстко привязаны к Unix-пути `~/Lendings/<slug>/` через `Path.home() / "Lendings"`**. У текущего пользователя на Windows проекты лежат в `d:/AI_TEAMS/Lendings/` — то есть **wiki-инфраструктура не работает на машине разработчика** без ручного создания симлинка/junction. Этот же дефект усугубляет finding из фазы 2 (#3): wiki не только без навигатора, но и не запускается на текущей среде разработки.

Вторая важная находка: **18 из 34 bash-скриптов проекта запущены без `set -euo pipefail`** (53%). Это значит, что если в середине скрипта команда упала — скрипт **продолжает работать**, делая последующие шаги на основе сломанного состояния. Verify-скрипты (которые должны падать при failure) и migration-скрипты (которые могут повредить данные при частичном выполнении) — основные пострадавшие. Аналогично, **только 16 из 34 скриптов проверяют существование файлов перед чтением** через `[[ -f ]]`.

Третья: **в проекте 238 тестов** (отлично организованы по фазам PR-A/B/C/D и стейджам) — это хорошее покрытие. Но конкретный аудит «каждое изменение начиналось с теста» (CLAUDE.md заявляет TDD) — невозможно без git-blame по каждому файлу, и поверхностный осмотр показывает что много изменений сделано не через TDD-цикл (например, миграции).

Четвёртая: **6 команд имеют пересекающиеся имена в пайплайне 07** (`landing-content`, `landing-prototype`, `landing-wireframe`, `landing-compose`, `landing-photos`, `landing-visuals`). Маркетолог может перепутать какую звать на каком этапе — особенно `compose` vs `content`. Это findings о naming consistency.

**Всё — на согласование. Никаких действий не выполнено.**

## 🔴 Критичные

### #1 🔴 КРИТИЧНО — Wiki-скрипты жёстко привязаны к Unix-пути `~/Lendings/`; на Windows не работают без ручного хака

**Что это значит простыми словами:**
Несколько Python-скриптов в `scripts/wiki/` ожидают что все клиентские проекты лежат в `~/Lendings/<slug>/` (на Unix это `/home/<user>/Lendings/`). На Windows у текущего пользователя проекты живут в `d:/AI_TEAMS/Lendings/`. Скрипты используют `Path.home() / "Lendings"` — это резолвится в `C:\Users\<user>\Lendings\`, **папки которой не существует**. Wiki-compile, flush, session_start hooks — все они в этой среде не запустятся, пока не сделать junction (Windows-симлинк) с `C:\Users\<user>\Lendings\` на реальный путь.

**Чем грозит бизнесу:**
- На новой машине разработчика wiki **не работает из коробки** — нужен ручной шаг по созданию симлинка/junction.
- Session-hook'и (которые автоматически читают wiki при старте Claude Code сессии) **молча падают** — пользователь не получает контекст из wiki и не знает почему.
- Compile-команда из CLAUDE.md (`python3 -m scripts.wiki.compile --source-mode=system`) на свежей Windows-установке упадёт с ошибкой пути.
- Усугубляет finding фазы 2 #3 (wiki без навигатора): теперь wiki ещё и без работающего pipeline на главной dev-машине.

**Оценка срочности (мнение ревьюера, на согласование):** **блокирует онбординг нового разработчика на Windows**. Не блокирует production-flow для маркетолога (он работает через `/landing-go`, не через wiki напрямую), но создаёт ложное впечатление «wiki сломана» при первом запуске.

**Статус решения:** ☐ на согласовании

**Технические детали:**

- Файл: `scripts/wiki/compile.py:73,90` — `project_root = Path.home() / "Lendings" / args.project`
- Файл: `scripts/wiki/flush.py:60` — `lendings = Path.home() / "Lendings"`
- Файл: `scripts/wiki/hooks/session_start.py:9,38,39,80` — все ссылки на `~/Lendings/`

- Проверено: `if not project_root.exists()` есть (в compile.py:74), значит скрипт **корректно умирает** при отсутствии пути — это не silent failure, но и не useful failure (сообщение «not found», без подсказки настроить путь).
- Возможные пути решения (на согласование):
  - **ввести env-переменную `LANDINGS_ROOT`**: `lendings = Path(os.environ.get('LANDINGS_ROOT', Path.home() / 'Lendings'))`. Backwards-compatible. Маркетолог на Windows ставит `LANDINGS_ROOT=d:/AI_TEAMS/Lendings` в `.env` или системно.
  - **читать путь из `config/system.yaml`** или эквивалента (system-конфиг есть, см. `docs/SETUP.md`).
  - **создать junction** при первом запуске preflight-скриптом: проверить `~/Lendings` → если нет, спросить «куда указать» → создать junction.

### #2 🔴 КРИТИЧНО — 18 из 34 bash-скриптов без `set -euo pipefail` — могут продолжать после ошибки, делать вредное

**Что это значит простыми словами:**
Стандартная защита bash-скриптов — добавить в начало строку `set -euo pipefail`. Это значит «если любая команда упала — упади весь скрипт». Без этой строки скрипт продолжает работать после ошибки: например, если `cp` не сработал, следующая `rm` всё равно удалит файл. Для verify-скриптов это означает «возвращает exit 0 даже когда внутри упало». Для migration-скриптов это означает «частичная миграция оставляет данные в полу-сломанном состоянии».

**Чем грозит бизнесу:**
- Verify-скрипты привязанные к stage-gates могут «зелёным» закрывать этап, в котором реально что-то не прошло. Маркетолог думает «всё ок», деплоит сломанное.
- Migration-скрипты могут оставить state.yaml в несогласованном состоянии: часть изменений применена, часть нет.
- При запуске на CI скрипт может маскировать ошибку до прода.

**Оценка срочности (мнение ревьюера, на согласование):** стоит решить до сдачи клиенту. Особенно для verify-скриптов (риск ложного pass) и migration-скриптов (риск повреждения данных).

**Статус решения:** ☐ на согласовании

---

**Технические детали:**

- Всего bash-скриптов в `scripts/`: **34**
- Без `set -e` или `set -euo pipefail`: **18 (53%)**
- Среди них:
  - **verify-скрипты:** `verify-composed-premium.sh`, `verify-content-preserved.sh`, `verify-identity-preserved.sh`, `verify-photo-pipeline.sh`, `verify-visual-qa.sh` — критично, эти скрипты должны корректно возвращать exit-код
  - **gate/check:** `gate-check.sh`, `gate-state.sh`, `check-wiki-sync.sh` — также критично
  - **landing-final-check.sh** — финальный pre-deploy
  - **migrate-add-wiki.sh, mark-legacy-projects.sh, backport-acf-to-legacy.sh** — миграции
  - и др.
- 16 из 34 проверяют существование файлов через `[[ -f ]]` / `[[ -d ]]` / `test -f` — это **меньше половины**.
- Возможные пути решения:
  - **массовая правка**: добавить `set -euo pipefail` в начало каждого скрипта, прогнать smoke-тест что ничего не сломалось.
  - **lint-правило в CI**: запретить мерж скриптов без `set -e`.
  - **точечная правка**: начать с критичных (verify + migrate), остальные оставить как low-priority.

## 🟠 Важные

### #3 🟠 ВАЖНО — Migration-скрипты идемпотентность не проверена статически — risky при повторном запуске

**Что это значит простыми словами:**
В проекте 7 migration-скриптов (см. фазы 1 и 3). По названию каждого — он что-то меняет в существующих проектах (state.yaml, niche-версию, template-README'мы и т.д.). Идемпотентность (повторный запуск не делает повторных изменений) — основное требование к миграциям. Статический анализ показал что **большинство скриптов не проверяют наличие маркера «уже мигрировано»**, то есть повторный запуск может дублировать изменения.

**Чем грозит бизнесу:**
- Маркетолог запускает миграцию по ошибке второй раз → данные state.yaml дважды трансформируются → сломано.
- Recovery после частичной миграции (см. #2 про `set -e`) — двойной запуск делает дублирующие изменения.

**Оценка срочности (мнение ревьюера, на согласование):** не блокирует, но связано с #2 и фазой 1 #6 (5 миграций не документированы).

**Статус решения:** ☐ на согласовании

**Технические детали:**

- 7 migration-скриптов: см. фаза 3 #6.
- Glub-проверка по `if.*-f.*migrated|grep.*MIGRATED_FLAG` — не проводилась глубоко (требует чтения каждого), но первичный осмотр не показал паттерна «marker-based».
- Возможные пути решения:
  - для каждой миграции добавить маркер в state.yaml (`migrations_applied: [migrate-niche-v2, ...]`) и пропускать если уже применена;
  - либо документировать «однократный запуск» (с предупреждением на старте).

## Глоссарий

- *set -euo pipefail* — стандартная защитная директива bash: остановиться при ошибке (`-e`), при обращении к неопределённой переменной (`-u`), при ошибке в pipe (`-o pipefail`).
- *идемпотентность* — свойство операции давать тот же результат при повторном запуске. Критично для миграций.
- *silent failure* — ошибка, которая не приводит к остановке программы и не сообщается пользователю. Самый опасный тип бага.
- *hard-coded path* — путь к файлу/папке, записанный непосредственно в коде, а не через переменную окружения или конфиг.
- *TDD (Test-Driven Development)* — практика «сначала тест, потом код». Заявлена в CLAUDE.md как обязательная для проекта.
- *junction* — Windows-аналог симлинка для папок.
- *env-переменная* — переменная окружения, которую можно задать на конкретной машине без правки кода.
