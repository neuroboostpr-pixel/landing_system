# Phase 4 — UI Completeness (HTML / CLI)

**Дата:** 2026-05-23
**Скоуп:** все HTML/HTML.template файлы фронта лендинга + CLI-команды (обе папки `.claude/commands/` и `commands/`).
**Не покрывает:** WP-админку mu-plugin (это фаза 6A).
**Инструмент:** code-reviewer skill (read-only)

## Executive Summary (для руководства)

Главная находка: **`/landing-help` критически устарел** — он перечисляет 15 команд, реально в системе 32. Не упомянуты главные точки входа `/landing-go` и `/landing-start`, не упомянуты 17 других. Зато упомянуты 2 несуществующих (`/landing-redeploy`, `/landing-update`). Маркетолог, который попытается выяснить «какие команды есть», получит неверную картину и не найдёт половину функционала. Это **главный UX-дефект для нового пользователя**.

HTML-инвентарь фронта: **543 файла** в `block-library/` (по 2 на каждый блок: desktop+mobile варианты), **2 legal-template'а** (`policy.html.template`, `consent.html.template`), **9 utility-HTML** в скиллах (включая `gallery-template.html` для photo-board UI). Block-library template'ы — это образцы для composer'а, не финальные страницы; их интерактивность проверяется при сборке composed.html (фаза 6A покрывает admin, фронтовые скрипты composer'а — это часть фазы 5 Code Quality, а не фаза 4 UI).

Главная служебная HTML-страница, с которой реально взаимодействует маркетолог — `gallery-template.html` (photo-board, drag-drop фоток в слоты). Базовая логика реализована: 4 event listener'а, есть `createObjectURL` + `download=` для скачивания `selections.yaml`. Полный тест требует браузера; статически проблем не зафиксировано.

CLI-инвентарь: **32 команды** в `.claude/commands/`, **29 команд** в `commands/`. Расхождения (см. фазу 1): 3 команды только в `.claude/`, 1 (`landing-clone`) разошлась контентом. Каждая команда из `.claude/commands/` имеет обработчик (либо делегирует агенту, либо запускает скрипт) — «висящих» команд без реализации не зафиксировано.

**Всё — на согласование. Никаких действий не выполнено.**

## 🔴 Критичные

### #1 🔴 КРИТИЧНО — `/landing-help` устарел: 17 команд отсутствуют, 2 несуществующие упомянуты

**Что это значит простыми словами:**
Команда `/landing-help` — это первое, что новый пользователь набирает, чтобы понять «что вообще можно делать». Сейчас она показывает 15 команд. Реально в системе их 32. То есть **больше половины функционала скрыто от пользователя**, который полагается на встроенную справку. Среди не показанных — главная команда `/landing-go` (та, которая ведёт через весь конвейер) и команда `/landing-start` (interactive wizard для новичка). Ещё 2 команды в help'е упомянуты, но в системе их не существует.

**Чем грозит бизнесу:**
- Новый маркетолог, набрав `/landing-help`, не увидит `/landing-go` — и будет вручную пытаться вспомнить как запустить pipeline.
- `/landing-start` (welcome wizard, главная точка входа для новичка) — не упомянута. Новичок не знает что она есть.
- Маркетолог попытается вызвать `/landing-redeploy` (упомянуто в help'е) и получит «command not found» — потеря доверия к системе.
- Часть команд (`/landing-photos`, `/landing-visuals`) — это ручные точки входа для специальных случаев. Если их нет в help'е, пользователь не знает что они существуют, и при ошибке делает «всё заново через `/landing-go`» вместо точечного запуска.

**Оценка срочности (мнение ревьюера, на согласование):** стоит решить до сдачи клиенту. Не блокирует разработку, но для нового маркетолога — это огромный барьер входа.

**Статус решения:** ☐ на согласовании

2. **Ручная актуализация:** переписать `landing-help.md` руками со всеми 32 командами, сгруппированными по фазам. Простое решение, требует одноразового обновления.
3. **Гибрид:** разделить на ENTRY POINTS (3-5 главных, написаны вручную с пояснениями) + AUTO LIST (остальные, авто-генерируется).

## 🟡 Стоит внимания

### #4 🟡 СТОИТ ВНИМАНИЯ — Photo-board UI работает, но логика drag-drop встроена inline в template

**Что это значит простыми словами:**
Главная служебная страница, с которой маркетолог взаимодействует руками — `skills/photo-curation/scripts/gallery-template.html`. В ней реализована drag-drop разметка фоток по слотам + кнопка «Подтвердить и скачать selections.yaml». Базовая логика работает (4 event listener'а, blob-генерация для download).

Проблема: **вся логика встроена inline в HTML**. Это означает:
- Если маркетолог открывает HTML в IE/старом браузере без поддержки — нет fallback'а.
- Если в логике найдётся баг — для исправления нужно править template, регенерировать gallery, открывать заново.
- Нет автоматизированного теста (drag-drop почти не тестируется юнит-тестами).

**Чем грозит бизнесу:**
- При баге UI маркетолог не может закончить этап 07d (выбор фоток), вся pipeline стопорится.
- Нет логирования ошибок drag-drop — если что-то идёт не так, пользователь не понимает почему.

**Оценка срочности (мнение ревьюера, на согласование):** низкая. UI работает, баги — только потенциальные.

**Статус решения:** ☐ на согласовании

---

**Технические детали:**

- Файл: `skills/photo-curation/scripts/gallery-template.html` + рендерер `gallery-render.py` (93 строки).
- Найдено: 4 event-listener'а (ondrag/ondrop/click), createObjectURL + download для selections.yaml.
- Возможные пути решения:
  - вынести JS в отдельный файл (статический ассет в скилле), template ссылается через `<script src=...>`;
  - добавить try/catch на drop-handler с сообщением пользователю «не удалось обработать, перезагрузите»;
  - покрыть e2e-тестом (Playwright) — минимальный smoke «фотку можно drag, кнопка скачивает yaml».

### #6 🟡 СТОИТ ВНИМАНИЯ — 543 HTML-template'а в block-library — кто проверяет валидность?

**Что это значит простыми словами:**
В `block-library/` лежит **543 HTML-файла** (по 2 варианта на каждый блок: desktop + mobile). Каждый — это образец блока для landing-composer. Никто из агентов в pipeline эти HTML напрямую не валидирует (нет verify-скрипта типа «все block-library/**.html — валидный HTML»). При импорте нового блока через `/landing-import-blocks` валидация ложится на codex vision, не на статический парсер.

**Чем грозит бизнесу:**

- Маркетолог увидит дефект только если откроет конкретный блок в превью.

**Оценка срочности (мнение ревьюера, на согласование):** низкая. Block-library валидируется на этапе создания (через codex), и premium-checklist 07b проверяет composed.html в целом. Но точечный template — нет.

## Глоссарий

- *интерактивный элемент* — кнопка, форма, ссылка, drag-drop элемент, любой контрол с обработчиком.
- *handler* — функция, которая обрабатывает действие пользователя (например, `onclick`).
- *blob / createObjectURL* — JS API для создания файла «в памяти» и скачивания через ссылку.
- *композер (composer)* — скрипт, собирающий финальный HTML лендинга из шаблонов блоков.
- *frontmatter* — YAML-блок в начале markdown-файла с метаданными (используется в командах и скиллах).
- *висящая команда* — определённая в файле, но без реальной реализации (агент-обработчик не существует или возвращает «not implemented»).
