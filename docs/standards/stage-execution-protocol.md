# Stage Execution Protocol (обязательный)

**Действует с:** 2026-05-19
**Применяется к:** `landing-orchestrator` + любым агентам, выполняющим этап pipeline
**Цель:** агент не пропускает шаги, не забывает действия внутри этапа, и пользователь всегда видит карту прогресса.

Этот протокол — обобщение принципов из Tencent Agent-Memory paper (Mermaid task map + structured workflow), адаптированное под нашу файло-основанную архитектуру. Не заменяет HARD GATE'ы и `gate-check.sh` — дополняет их дисциплиной *перед* действиями.

---

## Когда применяется

Любой запуск, который инициирует или продолжает этап pipeline:
- `/landing-go` (главная точка входа)
- Прямые вызовы `/landing-prototype`, `/landing-wireframe`, `/landing-compose`, `/landing-photos`, `/landing-visuals`, `/landing-build`, `/landing-deploy` и т.п.
- Любой агент, дёрнутый orchestrator-ом для конкретного этапа

## Протокол (4 шага, в строгом порядке)

### Шаг 1 — Прочитать состояние и нарисовать карту

Перед любым действием:

1. Открыть `<project>/.landing-state.yaml` — узнать `current_stage` и статусы всех этапов.
2. Запустить рендер карты с `--write-wiki`, чтобы карта оказалась и в чате, и в вики проекта:
   ```bash
   bash "$LANDING_SYSTEM_ROOT/scripts/render-pipeline-map.sh" \
        "<project>/.landing-state.yaml" --write-wiki
   ```
3. Вывести результат пользователю как Mermaid-блок (stdout). Файл `<project>/wiki/pipeline-map.md` обновляется автоматически — он становится частью project-graph вики.

**Цель:** ни агент, ни пользователь не должны держать порядок этапов в голове. Карта — единый источник истины.

### Шаг 2 — Выписать все оставшиеся этапы в TodoWrite

В самом начале прогона, до запуска gate-check, агент обязан создать TodoWrite со всеми этапами от `current_stage` до конца pipeline (исключая `n/a`).

Формат каждого todo: `"Этап <id> — <name>"` (например `"Этап 07b_wireframe — Wireframe"`).

**Цель:** видимый список = страховка от «прыжков» и «забыл закрыть».

### Шаг 3 — Для текущего этапа подгрузить чек-лист

После запуска `gate-check.sh --stage <current>` (если он прошёл `hard_checks`):

1. Проверить, есть ли файл `docs/standards/stage-<id>-checklist.md` (где `<id>` — `current_stage`).
2. Если есть — прочитать его. Для каждого пункта чек-листа создать **под-todo** к текущему этапу в TodoWrite.
3. Если нет — этап считается без внутреннего чек-листа, выполняется по описанию агента.

**Примеры существующих чек-листов:**
- `docs/standards/premium-07b-checklist.md` — 13 premium-фич для composed.html
- (другие добавляются по мере необходимости — паттерн един)

**Цель:** каждое требуемое действие внутри этапа = отдельный todo. Агент закрывает todo по факту выполнения, не на словах.

### Шаг 4 — Verify → approve → переход

После выполнения всех под-todo:

1. Если для этапа есть verify-скрипт (например `scripts/verify-composed-premium.sh` для 07b) — запустить. Exit ≠ 0 → доработать, НЕ сообщать об успехе.
2. Запустить `gate-check.sh --stage <id> --project <project> --approve`.
3. Только после approve — снять текущий todo и переходить к следующему этапу (повторить шаги 1–4).

## Wiki-запросы (обязательный формат)

Перед диспатчем любого агента — запрашивать wiki с явной передачей модели:

```bash
python -m scripts.wiki.query --stage=<N> --type=agent
python -m scripts.wiki.query --slug=<concept-slug>
```

Модель берётся автоматически из `config.DEFAULT_MODEL` — менять только в [scripts/wiki/config.py](../../scripts/wiki/config.py).

---

## Что запрещено

- ❌ Начинать делать что-либо до Шага 1 (даже «по-быстрому проверить файл»)
- ❌ Объявлять этап завершённым без verify-скрипта (где он есть)
- ❌ Игнорировать `stage-<id>-checklist.md` если он существует
- ❌ Закрывать TodoWrite-пункт, если действие не выполнено в артефакте

## Как добавить чек-лист для нового этапа

1. Создать `docs/standards/stage-<id>-checklist.md` со списком обязательных действий
2. (Опционально) Создать `scripts/verify-<stage>.sh` который проверяет артефакт по чек-листу
3. Прописать verify-скрипт в `config/stage-gates.yaml` как `hard_check` типа `script`

Паттерн взят из `premium-07b-checklist.md` + `verify-composed-premium.sh` — расширяй по аналогии.

---

## Связь с другими правилами

- HARD GATE 07b (premium-стандарт) **не отменяется** — он встроен в Шаг 4 как verify
- `gate-check.sh` остаётся источником truth для статусов этапов
- Wiki auto-sync (PR-G) продолжает работать как было
- Этот протокол — слой *перед* gate-check.sh, не вместо
