# Reference-Driven Rules — правило трёх источников и канон макета

**Статус:** обязательный стандарт для этапа 07c (создание макета) и сборки.
**Источник:** спека [2026-06-12-reference-driven-flow-spec.md](../superpowers/specs/2026-06-12-reference-driven-flow-spec.md), разделы 2.2, 2.4.
**Применяют:** block-composer, landing-orchestrator, wp-builder.

## 1. Правило трёх источников

Когда агент создаёт макет, информация берётся из **трёх разных мест.
Смешивать их — главная ошибка, которую этот стандарт запрещает.**

| Что берём | Откуда | Что именно |
|---|---|---|
| **Внешний вид** («чем рисуем») | из **референса** клиента (скриншот) | цвета, шрифты, стиль кнопок/тегов/полей, скругления, тени, отступы, характер, движение |
| **Структуру** («что где стоит») | из **прототипа** клиента, 1:1 (`prototype.md`) | какие блоки, их порядок, что внутри блока, выравнивание, какие тексты и кнопки |
| **Красоту/глубину** («коллаж») | из правил коллажа ([design-elements-rules.md](design-elements-rules.md)) | блобы, наезжающие слои, вырезанные фото, крупные цифры — ПОВЕРХ структуры |

### 1.1. ПРОТОТИП = ТОЛЬКО СТРУКТУРА (железное правило)

**Из прототипа берём ИСКЛЮЧИТЕЛЬНО структуру блоков: какие блоки, их порядок,
тексты, кнопки, что внутри каждого блока. ЦВЕТА / ШРИФТЫ / СТИЛЬ / ТЕМУ
прототипа — ИГНОРИРУЕМ ПОЛНОСТЬЮ.**

- Прототип может быть wireframe (серые рамки), может быть цветным/стилизованным,
  может быть светлым или тёмным — **это не имеет значения.** Его визуал — шум.
- Светлый прототип ≠ «делай светлый сайт». Тёмный прототип ≠ «делай тёмный».
  Цвет/стиль/тема НЕ выводятся из прототипа. *Реальный провал: агент увидел
  «светлый прототип 02.png» и решил, что это сигнал о дизайне — нет, это только
  структура.*
- Вид (палитра, шрифты, тема) берётся ТОЛЬКО из дизайн-системы проекта
  (этап 05, `tokens.json` / `DESIGN.md`), которая собирается из референса
  ИЛИ задаётся отдельно. Не из прототипа.
- Несколько прототипов клиента = несколько вариантов СТРУКТУРЫ (раскладки), к
  каждому применяется ОДНА дизайн-система. Разный вид у прототипов не означает
  разный вид у результата.

### 1.2. Раскладку прототипа НЕ копировать 1:1 — дизайн свой (железное правило)

«Структура из прототипа» = **какие блоки, их порядок, что внутри** (тексты,
кнопки, состав). Это НЕ значит «повтори пиксель-в-пиксель расположение, кегль,
ширину колонок, позицию карточек как на картинке прототипа».

- **Композиция, раскладка, типографика, расположение элементов — это ДИЗАЙН,
  зона агента.** Агент рисует СВОЙ premium-макет, а не обводит прототип.
- НЕ подгонять CSS под скриншот прототипа пиксель-в-пиксель. *Реальный провал:
  агент час подгонял hero (кегль/ширину фото/«4 плашки в ряд») под картинку
  прототипа, вместо того чтобы сделать свой дизайн — получилась кривая копия.*
- Если прототип стилизован дизайнером (не wireframe) — всё равно берём из него
  только структуру/тексты; его конкретную вёрстку не копируем.
- Сверять composed с прототипом нужно по СТРУКТУРЕ (блоки/порядок/тексты —
  гейт `structure_check_md` + `content_preserved`), НЕ по визуальному совпадению
  с картинкой.

### 1.3. Премиальность ≠ тёмная тема

Дизайн-система может быть светлой, тёмной, цветной — любой, какая идёт из
референса проекта. Светлый лендинг с акцентным цветом — полноценный premium.
Премиальность даёт **композиционная глубина** (слои, формы-подложки, вырезанные
фото, крупные цифры-якоря, единые переходы), а НЕ тёмный фон. Гейт `collage_depth`
проверяет глубину независимо от темы; на светлой теме глубину дают цветные формы
и тени вместо тёмных свечений.

## 2. Категорически нельзя

- **Брать раскладку у референса** (порядок блоков, композицию hero, выравнивание),
  если клиент не указал этого явно. По умолчанию раскладка — только из прототипа.
  *Реальный провал: агент сделал hero «как у Mercedes», хотя в прототипе клиента
  там была карусель машин.*
- **Выдумывать элементы**, которых нет в прототипе (плашки, бейджи, блоки,
  кнопки). Это такая же ошибка, как выдумать текст. *Реальный провал: плашка
  «5 brands», которой в прототипе не было.*

### 2.1. Текст: что нельзя и что МОЖНО (важно — не путать)

**НЕЛЬЗЯ — добавлять новый смысл (hard gate `no_invented_text`):**
- новые слова/фразы, которых нет в прототипе: описания к пунктам, подзаголовки,
  буллеты, преимущества, новые CTA. *Реальный провал: к «яйцам смыслов» (финплан,
  первые долги…) дописаны описания «Личный финансовый план под вашу жизнь» —
  их в прототипе не было.*
- на этапе 07a — `item:` со вторым полем через `|`, если описания нет в источнике.
  Значение item ОБЯЗАНО быть дословной подстрокой источника.

**МОЖНО — оформлять существующий текст прототипа (если не ломает структуру):**
- иконки рядом с пунктами, фирменные шрифты, размеры, `clamp()`, цвета-токены;
- разбивка фразы на строки, `<span>` с акцентом/градиентом на ключевом слове;
- цифры-якоря из РЕАЛЬНЫХ чисел прототипа (крупно), копирайт, связки («Соцсети:»).

Граница простая: **оформление меняет вид, но не добавляет новых слов-смыслов.**
Гейт `verify_no_invented_text.py` это и проверяет (сверка видимого текста
composed со словарём прототипа + служебный allowlist).

## 3. Исключение — явное указание клиента

Клиент может дать референс **на конкретный блок** с пометкой:
- «бери отсюда **только дизайн-систему**» → берём вид, раскладку — из прототипа;
- «бери отсюда **расположение блоков**» → для ЭТОГО блока раскладка с референса законна.

Запрет — на **самовольное** копирование. Указание клиента фиксируется в
`03_РЕФЕРЕНСЫ/index.yaml` (поле `take: design|layout|both` у референса).

## 4. Поблочная сверка перед сборкой (обязательная)

Перед HARD GATE 07c агент сверяет макет с прототипом **по каждому блоку**:

```text
Для каждого блока prototype.md:
  [ ] блок присутствует в composed.html (ни один не потерян)
  [ ] порядок блоков совпадает
  [ ] состав элементов совпадает (заголовки/тексты/кнопки/карточки — все, без добавок)
  [ ] выравнивание/композиция из прототипа (кроме блоков с явным layout-референсом)
  [ ] тексты дословные (verify-content-preserved.sh)
И в обратную сторону:
  [ ] в composed.html НЕТ блоков/элементов, которых нет в прототипе
```

Расхождение = дефект. Чинится до деплоя, не «потом».
Результат сверки агент пишет в `07b_COMPOSED/structure-check.md` (таблица
блок → статус → расхождения) и **обязательно** заканчивает файл строкой
машинного вердикта:

```
STRUCTURE_MATCH: PASS
```

(или `STRUCTURE_MATCH: FAIL`, если есть нерешённые расхождения). Гейт 07c
(`scripts/verify-structure-check.py`) не закроется без `PASS` — пустой файл или
отсутствие вердикта = дефект. PASS ставить только когда расхождений реально нет.

## 5. composed.html — единственная правда о виде (A4)

После утверждения макета **всё, что нужно для сборки сайта, выводится ИЗ
`composed.html`** — не пишется заново руками «по памяти» и не берётся из
прототипа напрямую:

- дизайн-токены и CSS — из стилей макета;
- описание блоков (block-spec) — из секций макета;
- шрифты и зависимости — из `<head>` макета;
- фото — из файлов, на которые ссылается макет.

Конвертер: `skills/wp-gutenberg-block-builder/scripts/composed-to-build.py`
(зона C). Пока какой-то части конвертера нет — собирать строго по макету,
сверяя `lint-composed-vs-spec.py`.

## 6. Архитектура дизайн-системы «один факт — одно место» (2026-06-20)

Источник рассинхрона ДС↔HTML — дублирование параметров в нескольких файлах. Правило:
**каждый факт живёт РОВНО в одном месте.**

| Что | Единственный источник | Кто этого НЕ дублирует |
|---|---|---|
| Параметры ВИДА (размер/цвет/шрифт/состояния/motion) | `{mood}/objects.yaml` (роль, через токены) | ТЗ, composition, HTML-числа |
| Значения, РАЗНЫЕ по модам | ТОКЕН (`{mood}/metrics.css` — размеры; `palette/typography/motion.css`) | — |
| Цвет (hex) | ТОЛЬКО `{mood}/palette.css` (`--lp-*`) | ⛔ нигде больше (ни ТЗ, ни composition, ни objects) |
| Расположение (зона/порядок/наезд) | `{mood}/compositions/*.yaml` (`ref:роль` + позиция) | objects, ТЗ |
| Контент (тексты/надписи/иконка-по-смыслу) | прототип (`role`/`group`) → MAPPING в ТЗ | objects, composition |

- **И ЦВЕТА, И РАЗМЕРЫ берутся ТОЛЬКО из мод-CSS через токены** (цвета — `palette.css` `--lp-*`; размеры —
  `metrics.css` `--cta-size`/`--figure-h`/…). 0 прямых цветов И 0 голых размеров в HTML вне токенов —
  иначе мод «протекает» (при смене палитры/мода значение не меняется). HTML использует `var()` везде.
- **Различие параметра по модам = НОВЫЙ ТОКЕН**, не переписанное значение в HTML (cta 140px/118px = один
  токен `--cta-size`, разный по модам).
- **ТЗ (build-spec.md) = MAPPING** контент→роль + только изменяющийся контент. Параметр-размер или hex в ТЗ = баг.
- Гейт `verify_html_vs_ds.py`: токен metrics не используется в HTML → размер захардкожен (FAIL).
  `verify_tokens.py`: hex вне palette (FAIL).

## 7. Требования качества к ТЗ и макету (общие для ВСЕХ проектов)

> Формулировать как ТРЕБОВАНИЯ, не как разбор ошибок конкретного проекта. ТЗ строится на этих правилах,
> а не подгоняется под текущий кейс примерами «вот тут ошибся».

1. **Контент — только из прототипа, дословно.** Смысл не переворачивать, слова не добавлять (`no_invented_text`).
2. **Состав блока = строго прототип.** НЕ добавлять элементы, которых в прототипе нет (лишний CTA, телефон,
   мессенджер, бейдж), даже если они были в РЕФЕРЕНСЕ. Референс даёт ВИД, состав — из прототипа.
3. **Адаптация под мод не порождает новый смысл** — слова берутся только из реального оффера прототипа.
4. **РАЗМЕР и РАСПОЛОЖЕНИЕ из ДС менять ЗАПРЕЩЕНО.** Заданы в `objects.yaml`/`metrics.css` (размер-токен) и
   `compositions/*.yaml` (позиция) → HTML обязан повторить через `var()`/ту же раскладку. Подгонять «на глаз»
   под скриншот — дефект (`verify_html_vs_ds.py`). Свободно меняется только то, что ДС оставляет открытым (контент).
5. **Иконка — по СМЫСЛУ текста** (лид-магнит→документ, контакт→телефон/почта), не «для красоты».
6. **Связанное не разбивать** (`group`): кнопка+подпись, имя+роль+реплика — единым объектом, не по разным зонам.
7. **Эффекты обязательны** (в статичном референсе не видны): reveal-каскад, параллакс, idle-float; `@prefers-reduced-motion`→off.
8. **Контент первого экрана (above the fold) виден СРАЗУ — без reveal по скроллу.** Элементы, попадающие в
   первый видимый экран при загрузке (hero целиком: заголовок, CTA, фигура, полоса доверия в hero и т.п.),
   НЕ анимируются появлением по скроллу — иначе важный блок «появляется только при скролле», а после скролла
   уже не нужен. Reveal/parallax-по-скроллу — ТОЛЬКО для блоков НИЖЕ первого экрана. Above-the-fold: либо
   без reveal, либо `on_load`-анимация при загрузке (мгновенный fade-in), не привязанная к scroll-position.
   Практика: класс `.reveal` вешать только на секции ниже hero; внутри hero — `on_load` или статика.
