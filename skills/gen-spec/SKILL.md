# gen-spec

## Pre-flight

```bash
python -m scripts.wiki.log --type skill_call --skill gen-spec --stage 07b
```

ТЗ = **MAPPING**: какой контент прототипа какой ролью ДС реализован + только ИЗМЕНЯЮЩИЙСЯ контент.
ТЗ НЕ дублирует параметры (они в ДС) и НЕ копирует тексты (они в прототипе) — оно их СВЯЗЫВАЕТ.

## Вход (yaml проекта)

- Активный прототип `07_ПРОТОТИП/prototype-*.yaml` (`meta.active: true`) — контент + `role`/`group` + `block_instructions`.
- Муды `05_ДИЗАЙН-СИСТЕМА/moods/*/` — `objects.yaml` (роли), `compositions/*.yaml` (расположение).

## Выход

- `07b_COMPOSED/build-spec.md` — ТЗ (mapping).

## Инструменты (в этом скиле: `scripts/`)

| Скрипт | Когда | Что делает |
|---|---|---|
| `scripts/verify-spec.py --spec <build-spec.md> --prototype-dir <07_ПРОТОТИП/> [--moods-dir <…/moods/>]` | **обязательно** после записи ТЗ | гейт: ровно один active-прототип, есть раздел «КОНТЕНТ ПРОТОТИПА» + раздел на каждый мод, 0 хексов/размеров (вне code-span), тексты не скопированы дословно без ссылки, все `block_instructions` перенесены. exit 0/1. |

## Флоу

1. Прочитать активный прототип (по флагу) + просканировать `moods/*` (сколько мудов — столько разделов).
2. **Раздел «КОНТЕНТ ПРОТОТИПА»** — один на все муды: таблица `Cn (role/group) → текст прототипа` (ДОСЛОВНО,
   но как ССЫЛКА на ключ прототипа — не переписывать руками, иначе теряется). Тексты едины (прототип один).
3. **Структура по мудам: МУД 1 (ВСЕ блоки) → МУД 2 (ВСЕ блоки) → …** — каждый мод цельный раздел,
   НЕ «блок → подмуды». Внутри мода — mapping каждого блока.
4. **Mapping блока:** `роль ДС ← C-элемент` + контент-специфика/ПРИЁМ (приём мод-зависим: груминг «бейдж наезжает» /
   деньги «черта-accent» для одной роли quote). Вид/размеры — из `objects.yaml` по ссылке; расположение — из composition.
5. **Инструкции блоков** (`block_instructions` прототипа: карусель/бегущая строка/слайдер) → записать в ТЗ как
   требование к блоку (gen-html сгенерит блок по инструкции).
6. Адаптация (склейки cta+note, чего нет → опустить роль) — в ТЗ, кратко.
7. **ОБЯЗАТЕЛЬНО прогнать гейт** `scripts/verify-spec.py --spec <build-spec.md> --prototype-dir <07_ПРОТОТИП/>
   --moods-dir <…/moods/>`. При FAIL (нет active / лишний хекс-размер / скопированный текст / не перенесённая
   инструкция / мало мудов-разделов) — править ТЗ, не закрывать этап.

## Краевые случаи (как обрабатывать)

- **Заголовок блока отсутствует в прототипе** (нет `section_title`, напр. hero/problem-solution): взять
  `block_label` как заголовок-fallback ИЛИ опустить заголовок — НЕ выдумывать новый текст. В mapping явно
  пометить «← block_label» или «заголовок опущен».
- **Header/Footer не выделены блоками прототипа:** навигация/лого берутся как РОЛИ ДС, контент меню — из
  блоков-якорей прототипа; контакты/соцсети футера — из соответствующего блока прототипа (contacts), если есть.
  Чего нет в прототипе (телефон и т.п.) — НЕ выводить.

## ПРАВИЛА (⛔ нарушение = дефект)

- ⛔ **ТЗ = mapping + только изменяющийся контент** (тексты/надписи/иконка-по-смыслу). Больше ничего.
- ⛔ **В ТЗ НЕТ параметров-размеров и хексов** — они в ДС-токенах. Параметр/hex в ТЗ = баг (→ перенести в metrics/palette).
- ⛔ **Тексты — ССЫЛКОЙ на ключи прототипа**, не копировать вручную (при копии теряются/искажаются).
- ⛔ **Системные правила — ССЫЛКОЙ на стандарт** `reference-driven-rules.md` §6-8, НЕ дублировать в ТЗ.
- ⛔ **БЕЗ историй ошибок** в ТЗ («не телефон», «= баг»). Формулировать как требования, не как разбор косяков.
- ⛔ **Состав блока = строго прототип** (требование 2 стандарта §7). Не добавлять элементы из референса, которых нет в прототипе.
- Структура: МУД 1 все блоки → МУД 2 все блоки. КОНТЕНТ ПРОТОТИПА — общий раздел (тексты один раз).
- Активный прототип — по `meta.active: true`, не по имени.
- ⛔ **Нет заголовка/header/footer в прототипе — НЕ выдумывать.** Заголовок-fallback = `block_label` или опустить;
  header/footer — роли ДС + контент-якоря прототипа. См. «Краевые случаи».
- ⛔ **Перед закрытием этапа — гейт `scripts/verify-spec.py` зелёный.** FAIL = дорабатывать ТЗ.
