# /landing-style

Stage 08b — translate DESIGN.md §5 wireframes into production visual code via the `frontend-builder` agent. Adds per-block CSS to DESIGN.md §5 (fenced ```css blocks under each `### Block N`), rewrites every `wp-theme/blocks/lazyblock-*/block.php` with a layout-aware template, then regenerates `assets/css/main.css` from the updated DESIGN.md.

## Pre-flight

1. Run `bash scripts/setup-flag.sh is_complete`. If exit 1 → reply "Onboarding не пройден. Запусти /landing-onboarding" and stop.
2. Determine project dir from `<project>` argument or current `landing.project` config.
3. Run: `bash scripts/gate-check.sh --stage 08b_style --project <project>`.
   - Expected at this stage: `08_build` must be `approved`. If exit 1 because `08_build` is not approved → reply "Stage 08 (build) not approved — run /landing-build first" and stop.
   - The other hard-checks (`block_php_markers`, `section5_has_css`, `main_css_regenerated`) are expected to FAIL pre-flight if `/landing-style` has not yet run on this project. That's normal — they pass after the agent finishes.

## What I do

### Step 1 — Dispatch `frontend-builder` agent

Invoke the agent defined in `agents/frontend-builder.md`. Pass the project path. The agent:

- Reads inputs (read-only): DESIGN.md §1-§9, brand-kit, landing-structure, block-spec.yaml, each `block.php` skeleton.
- For each block in `block-spec.yaml` (sequentially):
  - Composes per-block CSS from the wireframe + tokens, including media queries from §3.3.
  - Appends a fenced ```css block to DESIGN.md §5 under the matching `### Block N — Name` heading, preceded by a `**CSS:**` line.
  - Overwrites `wp-theme/blocks/lazyblock-<slug>/block.php` with a marker header + layout-aware markup.

The marker that goes in the top of every `block.php`:

```php
<?php
// AUTO-GENERATED by frontend-builder.
// Edits will be overwritten. Modify DESIGN.md §5 or block-spec.yaml instead.
```

Boundaries: agent does NOT touch DESIGN.md §1-§4 / §6-§9, `block-spec.yaml`, `style.css`, `functions.php`, `index.php`, JS, or seed content.

### Step 2 — Regenerate `main.css`

Run the thin CSS regenerator. It re-reads DESIGN.md §3-§9 (including the just-added §5 fenced blocks) and rewrites only `assets/css/main.css`. `style.css` is not touched.

```bash
python3 <landing-system>/skills/wp-gutenberg-block-builder/scripts/extract-main-css.py <project>
```

### Step 3 — HARD GATE (automatic checks)

Run: `bash scripts/gate-check.sh --stage 08b_style --project <project>`.

The four hard-checks must pass:
- `design_md` — DESIGN.md present
- `block_php_markers` — every `wp-theme/blocks/lazyblock-*/block.php` starts with the frontend-builder marker
- `section5_has_css` — every `### Block N` heading in DESIGN.md §5 has at least one fenced ```css
- `main_css_regenerated` — `assets/css/main.css` exists

If any fails, the agent for that specific block needs to re-run (e.g. `/landing-style --block <slug>`); fix the root cause, do not patch around.

### Step 4 — HARD GATE (manual visual approve)

Open the test stand (or local preview) in a browser. Walk the page, compare to DESIGN.md §5 wireframes. Acceptance is "passable", not pixel-perfect:

- Hero: layout matches desktop wireframe; mobile collapses to a stack
- Pricing: 3 cards, middle one with the "popular" modifier visible
- FAQ: `<details>/<summary>` accordion toggles open/close
- Brand colors visible on CTA and backgrounds
- No PHP fatals, no console errors

If passable → run:

```bash
bash scripts/gate-check.sh --stage 08b_style --project <project> --approve
```

This marks `08b_style: approved` in `.landing-state.yaml`, unlocking `/landing-deploy`.

## Usage

```
/landing-style                     # all blocks
/landing-style --block hero        # regenerate one block only (re-runs main.css extract after)
```

## Failure modes

- **08_build not approved** → exit 1 at pre-flight. Run `/landing-build` first.
- **Some `### Block N` in DESIGN.md §5 missing fenced css after agent run** → agent skipped or failed on that block; re-dispatch with `--block <slug>` for the failing one.
- **`block.php` missing marker after agent run** → agent bug; re-dispatch with `--block <slug>` and verify the agent prompt has the exact marker bytes.
- **Missing token** (agent left `/* TODO: missing token --foo, add to DESIGN.md §2 */` in CSS) → designer responsibility; add the token via `/landing-design` on stage 05, then re-run `/landing-style`.

## Requirements

- Stage `08_build` approved (theme scaffold + Lazy Blocks pipeline complete).
- `05_ДИЗАЙН-СИСТЕМА/DESIGN.md` with `### Block N — Name` headings under `## 5. Per-block layouts`.
- `08_КОД/block-spec.yaml` listing every block that needs styling.

## Output

- `05_ДИЗАЙН-СИСТЕМА/DESIGN.md` §5 — fenced ```css blocks appended under each `### Block N`.
- `08_КОД/wp-theme/blocks/lazyblock-<slug>/block.php` — rewritten with marker header + layout-aware markup.
- `08_КОД/wp-theme/assets/css/main.css` — regenerated from updated DESIGN.md.
