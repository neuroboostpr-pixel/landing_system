# Сбор и ведение индекса референсов

## Что делает

Поддерживает файл `03_РЕФЕРЕНСЫ/index.yaml` — единственный источник правды о референсах проекта. Предоставляет пять CRUD-подкоманд: `add`, `update`, `list`, `show`, `remove`. Каждый референс хранится со статусом (`candidate` / `approved` / `rejected`) и типом (`url` / `file`). Если референс содержит указание что именно взять от него — поле `take: design|layout|both` — скилл сохраняет его для block-composer'а. Реализован через `scripts/index.py`. Вызывается агентом `references-curator` на этапе 03.

## Когда вызывается

Вызывается `references-curator` в ходе этапа 03 (сбор референсов), после того как клиент передал материалы в `02_МАТЕРИАЛЫ`. Первичный сценарий — добавление URL или файла со скриншотом со статусом `candidate`, затем обновление до `approved` после ревью.

## Вход → выход

**Вход:** путь до директории `03_РЕФЕРЕНСЫ/`, идентификатор референса (URL или имя файла), желаемый статус и тип.

**Выход:** обновлённый `03_РЕФЕРЕНСЫ/index.yaml` с актуальными записями; при `list` — отфильтрованный список в stdout для агента.

## Failure modes

- **URL добавлен, но сайт за bot-защитой (403/CloudFront):** агент пропускает референс без скриншота → style-extractor выдумывает стиль по тексту вместо пикселей — критический дефект (A3).
- **Палитра снята «на глаз»:** цвета в index.yaml описаны текстом, не hex-кодами с пикселей — неверные дизайн-токены на этапе 05.
- **Статус застрял в `candidate`:** агенты следующих этапов не знают, какие референсы одобрены, и либо игнорируют их, либо используют все подряд.
- **Поле `take` не заполнено:** block-composer не знает, использовать ли раскладку из референса или только стиль — нарушение правил §3 reference-driven-rules.
- **index.yaml разошёлся с файловой системой:** `show`/`remove` падают с KeyError, если файл удалён вручную без обновления индекса.
