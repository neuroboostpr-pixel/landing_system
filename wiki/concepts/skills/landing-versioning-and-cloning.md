# Версионирование и клонирование лендингов (legacy)

## Что делает

Скилл сохраняет снимки состояния проекта-лендинга и позволяет откатиться к предыдущей версии, либо создать полную filesystem-копию проекта под новым slug'ом для A/B-тестирования. Работает исключительно с **single-site** моделью — один проект, один WordPress-инстанс. Для новой мультисайт-модели (один домен = WP Multisite + сегменты ЦА) скилл устарел и заменён `skills/wp-multisite/scripts/clone-subsite.sh`.

## Когда вызывается

Вызывается вручную, когда нужно зафиксировать рабочее состояние проекта перед рискованными изменениями (например, до нового деплоя), откатиться к предыдущему снимку, или сделать независимую копию лендинга для другого сегмента аудитории в рамках устаревшей single-site схемы.

## Вход → выход

**Вход:** директория проекта (`<project-dir>`); опциональная метка версии (`version-label`) для `create-version.sh`; или новый slug (`new-slug`) для `clone-landing.sh`.

**Выход:** при версионировании — папка `09_ВЕРСИИ/<version>/` со снимком проекта; при клонировании — полная filesystem-копия проекта в новой директории с отдельным `.env`.

## Failure modes

- Клонирование запускается на multisite-проекте — clone-landing.sh не поддерживает WP Multisite, итогом будет сломанный инстанс.
- Отсутствует `.env` в исходном проекте — клон создастся без корректных учётных данных БД и SSH.
- Версионирование запускается при незавершённом деплое — snapshot содержит несогласованное состояние между кодом и удалённой БД.
- Снимок версии не включает дамп базы данных — откат восстанавливает код, но не контент WordPress.
- Путь к `new-slug` уже занят — скрипт перезапишет существующий проект без предупреждения.
