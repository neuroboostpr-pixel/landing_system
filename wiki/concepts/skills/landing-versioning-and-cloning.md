# Версионирование и клонирование лендингов

## Что делает

Скилл сохраняет снимки (snapshots) проекта-лендинга в папку `09_ВЕРСИИ/` и создаёт полные filesystem-копии проекта под новым slug'ом. Предназначен **только для legacy single-site проектов** — тех, где каждый лендинг существует как отдельный WordPress-инстанс. Для новой модели (один домен = WP Multisite + сегменты ЦА) клонирование выполняется через `skills/wp-multisite/scripts/clone-subsite.sh`.

## Когда вызывается

Вызывается вручную маркетологом или агентом когда нужно: (1) зафиксировать рабочее состояние проекта перед крупными правками, (2) откатиться к предыдущей версии, (3) создать A/B-вариант лендинга как отдельный проект. Автоматически оркестратором не диспатчится.

## Вход → выход

**Вход:** путь к директории проекта (`<project-dir>`), опциональный лейбл версии или slug нового клона. Проект может быть на любом этапе pipeline.

**Выход:** при версионировании — папка `<project-dir>/09_ВЕРСИИ/<version>/` со снимком. При клонировании — новая директория `~/Lendings/<new-slug>/` как полная копия исходного проекта с отдельным `.env`.

## Failure modes

- **Клонирование в multisite-проекте** — скрипт `clone-landing.sh` копирует файлы, но не создаёт WP subsite; в multisite-среде клон будет неработоспособен без ручной настройки wp-cli.
- **Конфликт slug'ов** — если директория `~/Lendings/<new-slug>/` уже существует, скрипт может перезаписать данные без предупреждения.
- **Неполный снимок** — если `09_ВЕРСИИ/` отсутствует (старые проекты без шаблона PR-E), `create-version.sh` может упасть; нужно создать папку вручную.
- **Рассинхрон `.landing-state.yaml`** — клон копирует state исходника; если запустить `/landing-go` в клоне сразу, оркестратор может принять чужие этапы за выполненные.
- **Зависание deploy после клона** — новый проект наследует `.env` с переменными исходного хоста; без правки `BEGET_*` деплой уйдёт не туда.
