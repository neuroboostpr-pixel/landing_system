# Frontend Builder — визуальный код по макету

## Что делает
Берёт wireframes из DESIGN.md §5 и переводит их в реальный CSS и PHP-шаблоны блоков WordPress. После его работы каждый блок лендинга получает полную верстку — без хардкода цветов и без JS.

## Когда вызывать / в каком этапе
Запускается на этапе **08b**, строго после `/landing-build`. Требует, чтобы `.landing-state.yaml` показывал `current_stage == 08_build`. Если предшественник не закрыт — harness-хук (`enforce_stage_gate.py`) физически блокирует запись файлов.

## Что на вход / на выход

**Вход (только чтение):**
- `05_ДИЗАЙН-СИСТЕМА/DESIGN.md` — wireframes §5, токены §2, брейкпоинты §3.3
- `04_БРЕНД/brand-kit.md` — бренд-контекст
- `01a_АНАЛИЗ_НИШИ/landing-structure.md` — контракт блоков
- `08_КОД/block-spec.yaml` — список блоков, BEM-классы, controls
- `08_КОД/wp-theme/blocks/lazyblock-*/block.php` — скелеты блоков

**Выход:**
- **DESIGN.md §5** — в каждый `### Block N` дописывает секцию ` ```css ` с полным набором правил (BEM, media-запросы, только CSS-переменные)
- **`block.php`** — полная перезапись каждого шаблона с маркером `// AUTO-GENERATED by frontend-builder.` в шапке

## Алгоритм (кратко)
Обрабатывает блоки последовательно по порядку из `block-spec.yaml`. Для каждого: читает запись в block-spec → читает секцию в DESIGN.md §5 → дописывает CSS → перезаписывает block.php. После всех блоков pipeline запускает `extract-main-css.py` и gate-check.

## Ограничения
- Не трогает §1–§4, §6–§9 DESIGN.md, `block-spec.yaml`, `style.css`, `functions.php`, JS-файлы.
- Не изобретает responsive-поведение, которого нет в §5/§3.3 — fallback: одна колонка.
- Только `var(--token)` — никаких хардкодных цветов и размеров.
- Брейкпоинты задаются через литеральные px (`768px`, `1024px`), не через переменные.
- Дочерние `block.php` для repeater-паттернов (sub-blocks) **не** покрываются маркером — известный false positive в `check-block-php-markers.py`.
